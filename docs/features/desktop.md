# Feature notes: Desktop app (M4)

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. Whoever changes the feature adds or updates its entry here in the same step.

Code: `apps/web/src/platform/` (what differs between browser and desktop app), `apps/desktop/` (Electron shell, `apps/desktop/AGENTS.md`). Open work: `docs/PLAN.md`; repository layout: root `AGENTS.md` section 2. **Why Electron (moved from PLAN.md 3.4 on 25 September 2026):** screen share with system audio, global shortcuts, autostart and tray are mature in Electron; Tauri would be leaner but was judged less mature for exactly these (an assessment; the planned prototype was never built).

## Decisions (18 September 2026, user)

The user's wish: "Die Desktop App soll das gleiche UI haben wie wir auf dem Server als Web-App ausspielen", every future UI update must reach both, and the build must work on the GitLab system and on GitHub. Asked and decided:

- **Where:** `apps/desktop` in this public repo, Apache-2.0, Electron. Not a repo of its own.
- **The UI is not moved into a package of its own. `apps/web` is the shared client: one build, two shells.** The desktop app packs exactly `apps/web/dist` and serves it from its own scheme (`app://squorli`); the absolute paths (`/assets`, `/brand`, `/player-window.html`) work unchanged. So a UI change cannot reach one and miss the other, there is no package registry (nothing is published anywhere, the GitHub build runs on a bare checkout), and `tools/`, the Dockerfile and the website's screenshot tools keep their paths. `packages/ui` stays a later option. Rejected: moving the UI to `packages/ui` with two thin shells (two renderer builds that can drift, much churn for no gain).
- **Differences between browser and app** (screen share codec, global push-to-talk, system audio, window background, updates, links) go through the `Platform` interface; the client recognises the app at run time by the bridge of its preload script (`window.squorliDesktop`).
- **Installers and update feed:** the binaries live in the GitHub Releases of `danielklessa/squorli-server`; the app only asks `https://squorli.com/updates/stable/` (generic provider), whose files the website generates with absolute GitHub addresses. The storage stays exchangeable. Rollout switch = the manual website deploy.
- **Platforms first:** Windows (NSIS) and Linux (AppImage, deb), unsigned. macOS later (auto-update there needs signing and notarization).
- **Login:** the directory account at `https://directory.squorli.com` is the default (fixed; a development override only). A server can also be added by address or `squorli://` link, also one without a directory (then with the device's key). Known limit: a server that names another directory works by key only; with `requireAccount` it answers `account_required`.
- **Last viewed server:** per device in localStorage, not in the directory's `AccountSettings` (every rail click would be a signed push, two devices would overwrite each other, and it would tell the directory what the user looks at). A fresh device falls back to the newest `AccountStatus.servers[].lastSeenAt`.
- **Window background:** first decided as Windows 11 `backgroundMaterial` (acrylic/mica) plus an opacity slider; **changed on 18 September 2026 after the user saw it** (entry "Own title bar and background modes"): opaque, mica, or a really see-through window; acrylic dropped.
- **Releases:** tag `desktop-v<semver>` = version of `apps/desktop/package.json`; `v*` stays reserved for the server image. The GitLab push mirror carries tags to GitHub, where the installers are built into a draft release.
- **Links:** `squorli://server/<host>` and `squorli://invite/<host>/<code>`. A link never signs in by itself: an unknown host shows the server first and waits for a click.
- **User agent:** `… Squorli-Desktop/<version> Chrome/<v> Electron/<v> Safari/537.36`; `labelFromUserAgent` learns it (copy rule to `../squorli-directory`).

**A start window with the update in it, and a quieter start of the client (20 September 2026, user's wish: "können wir den Start- und Update-Prozess noch optimieren? Dass ein Splash-Screen beim Starten ist (nicht mehr das 'noch keine Server') und darin auch die Update-Prüfung gemacht wird und ggf. das Update installiert wird, so dass der Benutzer das mitbekommt"):**
- **Where "no server yet" came from:** `Store.init()` set `signedIn` from the device's memory BEFORE the directory had named the account's servers, so for the length of two requests the client showed `NoServers`. **Client:** new state `starting` (true until `init()` is through, at most `START_SCREEN_MAX_MS` = 8 s: a server or directory that does not answer must not hold the screen); App.tsx shows a start screen (`.app-starting`: the mark and "Squorli wird gestartet …") instead of a login or "no server yet" that would only flash by, in the browser too (there it covers the resume of the session), and then calls `platform.window.ready()` (bridge member `clientReady`, IPC `squorli:client-ready`; nothing to do in a browser).
- **Shell:** `splash.ts` opens a small frameless start window before anything else (360 x 300, no preload, sandboxed, refuses every navigation). Its page is a `data:` address built by `splashPage.ts` (pure, tested): **no script in it**, the shell writes status, progress and the one link into it with `executeJavaScript`, every text as a JSON string; the picture is the brand's icon from the client's files. **The shell has no renderer code and the web build carries no page only the app needs**, which is why it is not a file of `apps/web`. Steps: "Suche nach Updates …" -> (update) "Update x wird geladen …" with a progress bar and **"Später installieren"** -> "Update x wird installiert. Squorli startet gleich neu." -> the app closes for the installer (`quitAndInstall(true, true)`: silent, start again afterwards); or (no update) "Squorli wird gestartet …" -> the main window is created HIDDEN and shown when the client says `clientReady` (fallback: `REVEAL_AFTER_MS` = 12 s, or a failed load), then the start window closes. German or English by the system's language, like the tray.
- **`updates.ts` `checkAtStart(splash)`** never rejects and never blocks the start for long: the CHECK has 10 s (`START_CHECK_TIMEOUT_MS`; no network = the client opens), an error at any point opens the client, the download can be left with "install later" (it goes on in the background, and the client offers the restart as before). **No loop (Claude's safeguard):** the version handed to the installer is remembered (`updateAttempt` in desktop-config.json); if the same version is offered again at the next start, the installation did not take, and it is NOT tried again at a start (`mayInstallAtStart`), only from the client's notice or at quit. A deb still cannot install anything (`manual`): it looks and lets the client say so. **A start by the system in the background gets no start window** and no installation at the start (the first check 15 s later, as before): nobody is there to see it, and the restarted app would lose `--autostart` and open its window.
- **"Install later" is a link the window refuses to follow:** `SPLASH_SKIP_URL` (`app://squorli/__install-later`), recognised in `will-navigate`. The first try, a `#fragment` with `did-navigate-in-page`, did nothing: measured, Chromium reports no navigation inside a `data:` page.

**Task bar mark for waiting messages, and starting with the system (20 September 2026, user's wishes: "dass das Icon in der Taskleiste anzeigt, wenn ich eine neue Direktnachricht oder eine Nachricht empfangen habe, in der ich erwähnt bin" and "eine Einstellung unter Ansicht, die mir erlaubt, die App automatisch mit dem System zu starten"):**

The images are generated by `tools/desktop-icon.mjs` (brand coral `#FF7F91` with the tile colour `#0C1424` on it, like the client's counters) and packed through electron-builder `files`. **The digits are placed by their ink box, not by CSS** (user's correction: "die Zahlen sollen horizontal und vertikal zentriert sein"; measured afterwards: equal margins, at most 1 px of 64 apart), **except the 1, whose STEM is centred** (user's second correction: the flag on the left pushed the stem to the right of the middle; measured: stem columns 27–36 of 64).

- **How a start by the system looks is the user's choice (user's decision the same day, after Claude had fixed "always in the background" without asking: "der Benutzer soll entscheiden können, ob er es minimiert/versteckt oder geöffnet starten möchte"):** a second switch under "Systemstart", "Dabei im Hintergrund starten" (`autostartBackground` in desktop-config.json, on by default, disabled while the autostart is off; `DesktopInfo.autostart.background`, bridge member `setAutostartBackground`, IPC `squorli:set-autostart-background`, `platform.window.autostart.background`, null in an app that predates it). In the background = with `--autostart` the first window is not shown: hidden in the tray when `closeToTray` is on, otherwise minimized in the task bar (closing would quit there, so a hidden window would be out of reach). Off = the window opens as at any start. `startsInBackground(argv, stored)` in `autostart.ts` (pure, tested); a start by the user always opens the window. Consequence to know: the client signs in at system start, so the user is online on their servers from then on.
- **Checked** in the unpackaged app (scratch user data folder, DevTools protocol; `--autostart-test`, unpackaged only, registers the development app under the name "Squorli-autostart-test"): the overlay shows "3", then "9+" for 12, then nothing for 0 (screenshots of the real task bar); `setAutostart(true)` writes the `Run` value with `--autostart` and answers true, `setAutostart(false)` removes it and answers false, nothing left behind; started with `--autostart`: window minimized (`IsIconic`), with `closeToTray`: no window at all, with `autostartBackground: false`: window open and not minimized; `setAutostartBackground(false)` lands in desktop-config.json and comes back in `DesktopInfo` at the next start. **Not checked:** the tray icon's dot by eye (the icon sat in the overflow), a packaged app after a real sign-in to Windows, Linux (desktop entry: unit tests only), an update of an AppImage. **The embedded players' sound on the radio's output device (20 September 2026, user's report from the desktop app: "das Audio läuft nicht mehr über die ausgewählte Ausgabe", meaning a YouTube/Twitch source; asked, the user chose "ja, in der Desktop-App"):** the players are foreign iframes, and no page can choose where a foreign iframe plays (`setSinkId` exists per media element, inside the frame; `navigator.mediaDevices.setDefaultSinkId` does not exist in Chrome 153), so they always used the system's default device; for audio stations the choice had always worked, which made it look like a regression. **The shell can reach into the frame:** `PlatformMedia.setPlayerOutput(label | null)` (null in a browser; bridge member `setPlayerOutput`, IPC `squorli:player-output`, guarded by `isClientFrame`; `desktop.ts` tolerates an app older than the client), `App.tsx` tells it the device the radio plays on (`radioOutputDeviceId ?? outputDeviceId`) **by its label, because device ids are hashed per origin** (measured: the frame's id for the same device differs from the client's), again on `devicechange`. `apps/desktop/src/main/playerAudio.ts` (`PlayerAudioOutput`) runs `playerAudioScript(label)` (pure, tested, `playerAudioScript.ts`) with `WebFrameMain.executeJavaScript` in every frame of `https://player.twitch.tv` and `https://www.youtube-nocookie.com` in any window (the client's page, the player's pop-out window): it finds the frame's own id for that label and calls `setSinkId` on every `<video>`/`<audio>` not yet there; every 3 s while a device is chosen, because the players make new media elements (next video, ads), and once with null to go back to the default. **Two conditions Chromium sets, both measured:** (1) the frame only sees labels and may only leave the default device while its origin passes the microphone permission CHECK, so `applyPermissions()` answers that check (and `speaker-selection`) with yes for the two player origins, for audio only, while `granting()` says so (first: only while our script runs; see the correction below); a REQUEST from a player (getUserMedia) stays refused, and without a grant the frame sees no labels (checked: `labelsVisible: 0`). (2) the iframe needs the `microphone` permissions policy, otherwise the check is never even asked: `playerFrameAllow(routable)` in `playerWindow.ts` adds `speaker-selection; microphone` to the iframe's `allow` **only where the platform can route** (in a browser that policy would let the player ask the user for the microphone under our name), and the pop-out page learns it from `route=1` in its address (child windows have no bridge). **Decision inside this (Claude's, at first confirmed only as the user's yes to "the app runs a small script of its own in the YouTube/Twitch frame"; the audio-device permission for the players, device labels readable, confirmed by the user on 25 September 2026):** the script is ours, runs in the frame's main world for a moment and leaves nothing behind; a player's own scripts could in theory read device labels if they asked in exactly that moment. The settings hint says in the app that the choice applies to Twitch and YouTube too (`app.de.ts` / `app.en.ts`). **Corrected the same day (user's report: "nach dem Wechsel des Videos in einer Playlist ist kein Ton mehr zu hören"):** the check was first answered with yes only during our own call. Chromium asks it again whenever a media element starts a new video (a queue's `loadVideoById`), and after a "no" the element keeps its `sinkId` but plays into nothing; reproduced in the test app with `webContents.isCurrentlyAudible()` (audible, then silent from the second video on; never silent on the default device). `granting()` is now also true for as long as a device is chosen, at the price that the players' scripts could read audio device names during that time (nothing is granted while no device is chosen; a microphone REQUEST is refused as ever). Checked: audible through three videos of a queue on the chosen device. **Checked** in the unpackaged app (scratch user data folder, fake devices, DevTools protocol, a harness page with the real `EmbedPlayer` served from `app://squorli`): YouTube and a live Twitch channel each move to "Fake Audio Output 1" within 3 s (`sinkId` read inside the frame), back to the default with null, an unknown label changes nothing and is logged; labels invisible to the frame outside our call. **Not checked:** real output devices by ear, the pop-out window's frame (same code, other window), a packaged app, Linux. Needs a new app release; a newer client in an older app simply keeps the default device.

**P4: auto-update, update feed and download page, "open in the app" (18 September 2026, after release `desktop-v0.1.0` was published):**
- *App:* `apps/desktop/src/main/updates.ts` with electron-updater 6.8.9 (pinned, bundled into `main.cjs`, which grew to about 770 kB): the feed address is the one baked in at packaging (`https://squorli.com/updates/stable`), nothing at run time can change it. `updateMode.ts` (pure, tested): Windows installer and AppImage update themselves (background download, install on "Neu starten" or at quit), a deb only learns that a version exists and links to the download page, an unpackaged app has no updates. **Keys in `safeStorage` (25 September 2026, `docs/PLAN.md` 2.1, the security review of the sign-in path):** until then the identity key (`chat.identity.v1`) and the server accounts' keys and tokens (`chat.serverAccounts.v1`) lay unencrypted in the origin's localStorage, readable by anything that reads the user's profile folder. Now the shell keeps them in `<userData>/secrets.json`, each value encrypted with Electron's `safeStorage` (Windows: DPAPI of the signed-in user; macOS: Keychain; Linux: the desktop's secret service), written through a temporary file and a rename.
- *Bridge:* `DesktopBridge.secrets` (`available`, `get`, `set`), synchronous IPC (`sendSync`), because the client reads its keys synchronously in many places; only the keys of `SECRET_KEYS` (`platform/bridge.ts`), only from the client's main frame (`isClientFrame`). `Platform.secretStore` is null in the browser, in an older shell and where the encryption is not real (Linux without a keyring falls back to `basic_text`: then everything stays in localStorage, a plain file would be no better).
- *Client:* `identity.ts` reads and writes through `setSecretStore()` (set in `main.tsx` before the store starts). A value still found in localStorage is moved over at the first read: written to the store, read back, and only then removed from localStorage; if the store refuses, localStorage keeps it.
- *Consequences:* the key is no longer tied to the origin's localStorage (the "`app://squorli` is final" rule still holds for the session tokens of directory servers, which stay there). **No downgrade:** an older app finds no key in localStorage any more and starts with a new device key; a directory account signs in again with its password, a device key without a directory account is lost for the older app. Not protected against: malware running as the same user (DPAPI decrypts for any process of that user), as with every such store.
- *Checked:* typecheck, unit tests (`identitySecrets.test.ts`: the move from localStorage, a store that refuses to write, new secrets only in the store and forgotten there, the browser without a store); the unpackaged app driven twice over the DevTools protocol with its own user data folder: a fresh key lands in the store and not in localStorage; a key left in localStorage by an "older app" is moved at the next start and gone from localStorage; foreign keys are refused both ways; `secrets.json` contains no key in plain text. Found on the way: Electron sends `event.returnValue` at its **first** assignment, so a default assigned before the real answer was all the page ever got (pitfall in `apps/desktop/AGENTS.md`). Not checked: a packaged app, Linux with and without a keyring, a user upgrading from 0.6.0 with a real account (the same path as the test's "older app").

**The leave cue when the app is closed in a voice channel (30 September 2026; user: "wäre es noch wünschenswert, wenn beim Schließen der App wenn man auf einem Voice Kanal eingeloggt ist auch noch der verlassen sound kommt"):** until now the page died with the window and the leave cue never sounded; the server and LiveKit only noticed the drop. Now the shell holds the first close or quit for a moment (`src/main/quitHandoff.ts`, pure and tested): it sends `IPC.quitRequest` with an id to the client, the client leaves its voice channel (App.tsx `leaveVoiceBeforeQuit`: `leaveVoice()` plays the cue at once and tells the server, then it waits `VoiceClient.leaveCueMs()`, the cue's length from `cueDurationMs` in `voice/sounds.ts`, about 0.4 s, or nothing when the cue would stay silent: not joined, deafened, the cue switched off) and answers `IPC.quitReady`; the shell then repeats the close or the quit. The shell waits at most 1.5 s, so a client that does not answer (crashed, still loading) never keeps the app alive; it asks only after `IPC.clientReady`. Both ways in are covered: the window's `close` (the title bar's x, Alt+F4) and `before-quit` (the tray's "Beenden", the appearance's relaunch, the system). Closing into the tray does not ask: the app keeps running and the voice channel stays connected, as the setting says. The update's install (`quitAndInstall`) must not be held, so the client leaves the channel before it asks for the install (after the existing confirmation) and the shell's `beforeInstall` calls `skip()`. Platform: `window.beforeQuit` (null in a browser and for an app older than this client); bridge members `onQuitRequest`/`quitReady`, guarded with `typeof` in `platform/desktop.ts`. A browser tab still just closes: there is no reliable way to play a sound from `beforeunload`.
- *Checked:* typecheck of web and desktop; `quitHandoff.test.ts` (held once, answered, timed out, wrong and late ids, a second attempt swallowed, no client to ask, skip); `sounds.test.ts` knows the cue's length (380 ms, well under the shell's limit). **Not checked:** the app itself with a real voice channel (needs the user's ear; the harness recipe of this file works with `--use-fake-device-for-media-stream`). Needs a new desktop app release; an older app with the new client, or the new app with an older server's client, simply behaves as before.
