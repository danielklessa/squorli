# Feature notes: plugins the server runs itself

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. Standing rules live in the `AGENTS.md` of the area. Whoever changes the feature adds or updates its entry here in the same step.

Code: protocol `packages/protocol/src/plugins.ts` (manifest, wire types), `Message.plugin`, `ServerState.plugins`, `ServerStructure.plugins`, `LimitsReport.plugins` in `index.ts`; server `apps/server/src/plugins/` (`sandbox.ts`, `prelude.ts`, `wire.ts`, `runner.ts`, `manifest.ts`, `scheduler.ts`, `service.ts`), `src/plugin-worker.ts`, `src/routes/plugins.ts`, `src/events.ts`, `src/memberRoles.ts`, tables `plugins`, `plugin_storage`, `plugin_jobs`, `plugin_log` and `messages.plugin` (migration 0045); the two plugins that ship `apps/server/plugins/timed-roles.ts` and `birthdays.ts`; for authors `packages/plugin-api/` (`index.d.ts`, `check.ts`, `reference.json`) and `examples/plugins/hello/hello.js`; client `apps/web/src/Plugin*.tsx`, `CommandSuggest.tsx`, `pluginFields.ts`, `duration.ts`; the operator's command in `deploy/install.sh` and `deploy/windows/squorli.ps1`; tests `apps/server/src/plugins/*.test.ts`, `apps/server/scripts/smoke-plugins.mjs`. The public guide: `../squorli-website`, `/docs/plugins/`.

## Built (15 November 2026, user's wish)

"eine Plugin Schnittstelle bauen über die man verschiedenste Sachen als direktes Plugin auf seinen Server einbinden kann (z.B. zeitlich beschränkte Rollen), das ist nicht das gleiche wie eine Bot API sondern eine möglichkeit Plugins direkt vom Server ausführen zu lassen."

A plugin is one `.js` or `.ts` file with its manifest as JSON in a leading block comment. The server stores it in the database, runs it in a sandbox of its own and hands it events; the plugin calls functions of the object `squorli`. It has no token, no network endpoint and no process of its own, which is the difference to a bot API (`docs/PLAN.md` 1.3 keeps that unplanned).

### The user's decisions (15 November 2026)

1. Third-party plugins run in a sandbox (QuickJS compiled to WebAssembly, in a worker thread), not built-in modules only and not Node modules with full access.
2. Installation both ways: an upload in Verwaltung by an owner, and the operator's command `squorli plugin`.
3. The first version covers members, roles, schedules, storage, settings and a log, and also channel messages and slash commands.
4. The reference plugin (time-limited roles) takes a duration per assignment, in a dialog on the member.
5. `PLUGINS` defaults to `owner`; `operator` allows only the command, `off` nothing.
6. The reference plugin ships with the server and is not installed ("Verfügbar").
7. Plugins may be written in TypeScript ("auch typescript zulassen").
8. Everything was built in one go.

### Decisions made by Claude (confirmed by the user on 15 November 2026: "deine Entscheidungen sind abgenommen")

Made while building without asking; the user read them the same day and accepted them as they stand here, the ones of the birthdays plugin and the date field further down included.

- **The file format:** the manifest sits in a `/* squorli-plugin { … } */` comment at the very top, so it is read without running code and can never differ from what a run would declare. A JSON envelope with the code as a string was the other candidate; nobody can write that by hand.
- **TypeScript:** the server only removes the types (Node's `module.stripTypeScriptTypes`, mode `strip`), it does not check them. `enum`, `namespace` and parameter properties are refused at installation with the parser's sentence. Lines and columns stay where they were, so a logged error points into the source. The function is still marked experimental in Node 26 (it prints a warning once per thread, which the worker that calls it drops); it lives in one place (`sandbox.ts` `prepare`) with tests. `sucrase` would be the fallback.
- **One worker thread per plugin**, started at the first event and stopped after five minutes without one. The plan said one worker for all; the spike changed that (below).
- **The scope:** a plugin touches only the roles and channels an admin picked in its settings fields of type `role(s)` and `channel(s)`. `saveSettings` checks the saving admin per added role as a reaction rule does (`canTouchRole`, `canGrant`, never the default role) and keeps the role's permission mask; at run time a role that gained permissions since is refused until the settings are saved again, and a role that carries `ADMINISTRATOR` is never in a scope, not even an owner's. A channel is added only by somebody who sees it.
- **Who may do what:** owners install, enable, disable and remove; `MANAGE_SERVER` sees the tab, the log and the views and edits settings (within the rank rule above).
- **Enabling grants.** A plugin is installed switched off. Enabling sends the capabilities the owner saw; when they are not exactly what the manifest asks for, the server answers 409 `capabilities_changed` with the list. An update that asks for more stops the plugin (`needs_approval`) until an owner confirms.
- **Messages:** the author of a plugin's message is a `users` row of its own (`public_key` = `plugin:<id>`), never a member; the message carries `plugin: { id, name, by?, command? }`. It goes out with `notice: true`, so an app from before shows a notice line instead of "Ehemaliges Mitglied". No link previews for them (a way to make the server fetch addresses). *(Since the section below: previews for the messages of a plugin that holds `net.fetch`.)* Removing a plugin keeps its messages unless the owner asks otherwise; the roles it gave always stay.
- **Commands answer in two ways:** what the handler returns goes to the caller only (in the REST answer; nothing is posted), and `messages.send` into the channel the command was run in is allowed during that event even outside the scope, when the caller may write there.
- **No new moderation log actions** (`ModLogAction` is a strict enum in older apps): a role a plugin gave or took is a line in the plugin's own log.
- **No signature on plugin files:** there is no author identity to check, and the release key must not sign other people's code. The SHA-256 of the file is stored and shown. *(Replaced the same day, see "Signed plugins, the network and the game news plugin" below: a plugin key of its own signs Squorli's plugins and, after a review, submitted ones; the release key still signs no plugin.)*
- **The operator's routes need a secret of the machine, not loopback.** The plan said loopback as for `squorli doctor`. A proxy on the same machine that forwards without a forwarding header arrives from 127.0.0.1 too, and these routes install code: the server writes a random token to `DATA_DIR/operator-token` at every start (the wrapper reads it inside the container), or takes `DOCTOR_TOKEN` where one is set (the package for Windows).
- **No presence, no game, no key** in what a plugin learns about a member; attachments only as a number.
- **The types for authors live in the repository only** (`packages/plugin-api/index.d.ts`), not on npm. `packages/plugin-api` has no `package.json` on purpose: a workspace package would have to be named in the Dockerfile's install step.
- **Texts of a plugin carry no control characters** and none of the characters that turn the direction of text around (`PLUGIN_TEXT_FORBIDDEN` in the protocol): a manifest with one is refused, an answer a plugin gives while running is cleaned (`cleanPluginText`; a line break stays). Found by the wrapper's test: a name with an escape sequence installed and would have drawn over the terminal in `squorli plugin list`.
- **A report of a plugin's message names the plugin and no person** (`reportedUserId` null): the queue then offers deleting the message and nothing against a member. Found by the client's walk: the queue offered kick and ban against the plugin's author.
- **In the client** (`apps/web/AGENTS.md` has the rules): every dialog a plugin causes carries a fixed line "Plugin: name"; plugin texts are text nodes only; one fixed icon for all plugins; an unknown field type is one line "needs a newer app"; a command or action whose permission, input kind or target rule this client does not know is hidden; consecutive messages of one plugin group only when the same member caused them; a typed `/name` with files attached goes out as a message; commands ignore slowmode.
- **The command `squorli plugin`** asks before it switches a plugin on (the capabilities in the installation's language, `--yes` skips the question), installs only when nobody can be asked, and strips control characters from everything a plugin wrote. On Windows the options are spelled `-Yes`, `-Bundled`, `-DeleteMessages` like the rest of that script; the Linux spellings are understood too.
- **Dropped from the plan:** a JSON schema of the manifest (the manifest sits in a comment, no editor applies a schema there); `commands.reply` (a handler's return value does the same).

### The spike (15 November 2026)

Run in a scratch folder with `quickjs-emscripten-core` 0.32.0 and `@jitl/quickjs-singlefile-mjs-release-sync` 0.32.0 (both MIT; QuickJS 2025-09-13, the WebAssembly embedded in an ES module), on Node 24.21 on Windows and on `node:26-alpine` (26.13.1) with a read-only root, `--cap-drop ALL` and the user `node`.

- **Loading:** the first module about 20 ms, each further one 3 ms; ten instances are ten separate memories. quickjs-ng has no single-file build and is not used.
- **Isolation:** no `process`, `require`, `fetch`, `setTimeout`, `console` or `WebAssembly`; `Function("return this")()` is the sandbox's own global; `import` of anything rejects.
- **`runtime.setMemoryLimit` is not the wall.** It stops strings and plain arrays, but typed arrays went to 2,042 MB under a 32 MB limit. A `WebAssembly.Memory` with a `maximum`, handed in through `newVariant(base, { wasmMemory })`, holds: the bomb gets "out of memory" after 25 MB and a neighbour answers. `initial` must be at least 256 pages (16 MB).
- **The interrupt handler is not the wall either.** It ends bytecode loops, loops inside `try`, regular expression bombs and sorts at the deadline. Native functions never ask it: `JSON.parse(JSON.stringify(big))` in a short loop ran 12 s, `new Array(2**27).join(…)` 2.5 s, a recursion that catches its own stack overflow 3.8 s.
- **The watchdog is the wall:** the worker writes "inside the engine since" into a `SharedArrayBuffer`, the main thread terminates a worker that stays inside past the budget plus a second. Killed after 1.2 to 1.3 s; `terminate()` took 2 to 4 ms.
- **Hence a worker per plugin:** a kill then never cuts a neighbour's handler in half. 11 to 14 MB per running worker, 50 ms (Windows) to 180 ms (the container) to start; twenty at once were 244 to 303 MB, which is why they start on demand and stop when idle.
- **Type stripping** keeps every line and column, refuses `enum`, `namespace` and parameter properties with `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`, strips 540 KB in 55 ms and answers a type nested 20,000 deep with a caught error within 4 ms.

### How it runs

- **`sandbox.ts`** is the inside of a plugin's worker: the engine with a capped memory, the prelude (`prelude.ts`) that builds `squorli` over one native function `__host(fn, json)`, then the plugin. A host call returns a promise the main thread's answer resolves; only JSON text crosses, 64 KB at most per argument and answer. One event at a time. CPU time is summed over every entry into the engine of one event.
- **`runner.ts`** (main thread): a worker per plugin, the queue (100 events), the wall time (10 s), the host calls per event (50), the watchdog, the idle stop, and `prepare` = reading a file in a worker of its own without running it (types off, the engine compiles the result). A context after a CPU or memory failure is not trusted: the next event gets a fresh worker.
- **`service.ts`** (`Plugins`): installation, the scope, the host functions with their capability and rate limits (per minute: 300 calls, 60 role changes, 20 messages, 120 storage writes, 60 log lines), the events (`serverEvents.listen`), member actions, commands, views, the failure count (5 within 10 minutes suspend the plugin) and the log (2,000 lines and 30 days per plugin).
- **`events.ts`** tells inside the process what the routes did; every event carries its origin and depth. A plugin never gets what it caused itself, and nothing deeper than 3 reaches a plugin. **`memberRoles.ts`** is the one path that changes a member's roles (the route, reaction roles, plugins).
- **`scheduler.ts`:** one timer armed to the next due job; a job is claimed in the database, handed over, deleted when the handler finished; a failed one comes again after 2 min, 10 min and 1 h, then it is dropped with a log line. At least once. Jobs of a plugin that does not run wait.
- **Workers start lazily, also after a restart:** nothing runs at the server's start, and `enable` is not sent then. A plugin whose worker never started is assumed to listen to every event, so its first event starts it; afterwards events it has no handler for start nothing.

### Protocol and compatibility

No `PROTOCOL_VERSION` bump and no new WebSocket event. `ServerState.plugins` (the feature flag; the commands and member actions of the enabled plugins, the same for every member, each naming the permission it needs) also rides on `structure`. It is parsed with `.optional().catch(undefined)` and lists that drop unreadable entries, because a plugin is installed at any time and must never cost a client its welcome. Field types, permissions and states are plain strings on the wire for the same reason; the manifest itself is parsed strictly, once, by the server.

| Surface | New server, app from before | Server from before, new app |
|---|---|---|
| The flag | stripped | missing: no plugin interface anywhere |
| A plugin's message | a notice line (the server sends `notice: true`) | none exist |
| Slash commands | a typed `/x` goes out as a message | no list |
| Member actions | missing; the server's own web client has them | none |
| Verwaltung > Plugins | missing; `squorli plugin` or the browser | hidden |

### The plugin that ships: timed roles

`apps/server/plugins/timed-roles.ts`, copied to `dist/plugins/` by the build (`tsup.config.ts`), so the image and the package for Windows carry it without a line of their own. Settings: the roles that may be given for a time. Member menu: "Rolle auf Zeit…" with the role and a duration. ### The second plugin that ships: birthdays (15 November 2026, user's wish)

"Können wir noch eins machen bei dem ein Benutzer sein Geburtsdatum anzeigen kann und er dann zum Geburtstag Gratuliert bekommt in einem gegebenen Kanal? Wenn er das Jahr mit angibt, dann mit alter?" and, the same hour: "Beim Geburtstags-Plugin soll man auch die nächsten Geburtstage anzeigen können. Wenn ein Mitglied den Server verlässt soll auch sein Geburtstag gelöscht werden. Das Mitglied kann sein Geburtsdatum auch wieder aus der Liste nehmen."

`apps/server/plugins/birthdays.ts`. A member enters their birthday with `/geburtstag` or `/birthday` (one form, two names: a command has one name and the product speaks two languages; the form is one `date` field whose year may be left out), takes it out again with the form's last field, and sees the next eight with `/geburtstage` or `/birthdays` (an answer only the caller gets). Once a day at the hour of the settings the plugin writes one line per birthday into the channel of the settings and mentions the member (`<@id>`), with the age where a year was given. `member.leave` removes the entry (told for a kick, a ban and an account's deletion, the three ways a membership ends). Verwaltung shows "Eingetragene Geburtstage".

*Decisions made by Claude (confirmed by the user with the others, 15 November 2026):* the sandbox has no time zones, so the settings offer Central, Western and Eastern Europe (summer time by the European rule, computed in the plugin) and fixed offsets from UTC-11 to UTC+12 (no summer time there; the help text says so); the day that counts is the one the job was due on, so congratulations after a night of downtime are late but right, and a job that comes twice congratulates once (`lastRun`); 29 February is congratulated on the 28th in a year without one; at most ten congratulations a day and 1,200 entries (one storage value, one event's limits); the list of the next birthdays names the age where a year was given, as the congratulation will; the language of the congratulation is a setting, German by default; no custom text yet.

*The field type `date` (the user, the same hour: "kann das Plugin einen Datepicker für das Modal bereitstellen?"):* a plugin cannot bring a control of its own, so the interface got an eleventh field type the app draws as a date picker. Its value is `YYYY-MM-DD`, or `--MM-DD` where the field has `yearOptional` and the member left the year out (the form a vCard uses; Claude's choice); `parsePluginDate` in the protocol is the one reading of it for server and client, and the server lets through only days the calendar has. Added to version 1 itself, which nothing has been released of yet.

*What it showed about the interface:* apart from that field type, nothing had to be added to version 1 for it. Missing for a nicer plugin: a form cannot be filled with what is stored (the fields are the manifest's), a command has one name, and a plugin cannot learn a member's or the server's time zone.

### The user's decisions (15 November 2026)

1. Plugins are signed with a key of their own, not with the release key; its private half lives in a GitHub environment `signing` with an approval per run.
2. The game news plugin ships with the server ("Verfügbar") **and** is offered as a signed file for download, so a source that changes its interface needs no server release.
3. Sources of the first version: Steam, free games, graphics drivers. No feeds an admin types in, hence a fixed list of hosts.
4. Plugin authors can submit plugins to be signed, by pull request in a public repository of its own (`squorli-plugins`).
5. Signed plugins are listed in that repository's releases and on a page of squorli.com.

### Decisions made by Claude (in the approved plan of 15 November 2026 under "Was ich festgelegt habe"; the user approved the plan as a whole)

- **The network only with Squorli's signature**, also for a plugin that ships with the server, and no operator switch that gives it to an unsigned plugin. `PLUGIN_NET=false` takes it from all of them.
- **The signature is the last block comment of the file** (`/* squorli-signature {"v":1,"key":"…","kind":"…","sig":"…"} */`), so a plugin stays one file. Signed is `squorli-plugin-signature-v1\n<kind>\n<sha256>` over the file without that comment in one form (no byte order mark, `\n` line ends, nothing blank at the end): a checkout that turns line ends around must not break a signature. The manifest is part of the file, so capabilities, hosts, author and version are signed with it and every version needs its own signature. A comment at the end that starts like a signature and is none refuses the file; it is never read as "unsigned".
- **Two kinds, inside the signed text:** `official` (Squorli's own) and `reviewed` (somebody else's that Squorli read). The client shows "Von Squorli" and "Von Squorli geprüft".
- **Interface version 2** for `network`, `net.fetch` and `squorli.net`: a server from before answers such a plugin "update the server" instead of "unknown key". Version 1 plugins are untouched (`PLUGIN_API_MIN` stays 1), and the prelude is the same for both: `squorli.net` exists everywhere, the capability decides.
- **`net.get` and nothing else:** one GET over https on the default port to a host the manifest names exactly (1 to 20 full names in lower case; no wildcard, port, IP address or bare name). No headers, no body, no cookies: the address is all a plugin can send. It runs through `safeGet` of the link previews (public addresses only, checked again at the connect), with `allowHost` asked for every redirect. Text, JSON or XML up to 512 KB within 5 s, 30 requests a minute; anything else is "no usable answer". The answer of this one function may be larger than the 64 KB of the others (`answerMax` in `runner.ts`, 1 MB as JSON).
- **What keeps an installed plugin from running is never stored** (`gates` in `service.ts`): it follows from the file, the keys, the revoked hashes and `PLUGIN_NET` at every start. Such a plugin shows as "suspended" with the reason as `lastError` for apps from before, and `PluginInfo.blocked` names the code for the app that knows it.
- **Revocation by a list in the server release** (`REVOKED_PLUGIN_HASHES`, copied from `squorli-plugins/revoked.json` before a release). No server asks anybody: **a revoked plugin runs on a server until that server's next update.** That is the price of servers that phone nowhere; the guide says so.
- **Link previews for the messages of a plugin that holds `net.fetch`** (changes a decision the user had confirmed the same day for plugins in general: "no link previews, a way to make the server fetch addresses"). ### Decisions made by Claude while building (not confirmed one by one)

- **The server asks nobody by itself.** The list is fetched when somebody with `MANAGE_SERVER` opens the catalogue in Verwaltung > Plugins (the client shows a button "Katalog öffnen" first, so opening the tab asks nobody) or installs from it; never at start, never on a timer. A fetched list is served for ten minutes, "Neu laden" asks again at the earliest after 30 seconds, and when GitHub does not answer the last list that could be read is served as `stale`. Nothing about the server goes along: one GET for `catalog.json` at `raw.githubusercontent.com`, one for a release's file at `github.com` (which redirects to GitHub's asset hosts). Both addresses are fixed in `catalog.ts` and `catalogAllowed` is the `allowHost` of both fetches; a release's address is built from the entry's id, version and file name, the list's own `download` field is never read.
- **The list is trusted for nothing.** A downloaded file must carry Squorli's signature like an uploaded one, its kind and its hash must be the entry's, and its manifest's id and version too; anything else is `catalog_mismatch` and nothing is installed. The list's texts are an author's texts: cleaned like a manifest's, a homepage only as an https address. An entry this server cannot read is left out alone; one written for a later plugin interface is listed as "needs a newer server" and cannot be installed.
- **Installing from the catalogue is installing**: an owner, `PLUGINS=owner`, the plugin switched off afterwards, an update through the same request (the capabilities are confirmed again when they changed, as after an upload). `installed_via` is `catalog`.
- **`PluginsResponse.catalog`** tells the client whether to draw the catalogue at all; a server from before has no such field and an app from before draws nothing.
- **The field type `list`** (interface version 2, in the settings only, not in a dialog or a command's form): entries an admin adds and removes, each made of one to four simple fields (`text`, `number`, `boolean`, `select`; no roles, channels or members inside a list, so a list never widens a plugin's scope), at most `maxItems` entries (default 50, never more than 100), a text of an entry at most 200 characters. The value is a list of objects. **A row counts only when something was typed into a text or number field of it**; a row where only a select was changed or a switch flipped is dropped, so "Eintrag hinzufügen" pressed once too often never costs a "required" error (a list without any text or number field keeps every row). An app from before shows "Dieses Feld braucht eine neuere App." in its place and leaves the stored value alone.
- **The event `settings.check`**: before settings are saved the server asks the plugin, if it runs, with what would be saved (already checked against the fields) and who saves. No answer lets it pass; `fieldErrors` refuses fields with the plugin's own sentences (400 `invalid_values`, nothing saved); `values` hands fields back in another form, checked like the admin's. A value for a role, channel or member field is never taken from the plugin: the saving admin's rank was checked for those. A plugin that throws or runs out of time fails the save (502 `plugin_failed`, 504 `plugin_timeout`). A plugin that is switched off is not asked: the values are saved as typed.
- **No version 3 for this.** The list field and the event were added to interface version 2, which no released server carries yet (0.14.0 has version 1).
