# Feature notes: game detection and game display

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. Whoever changes the feature adds or updates its entry here in the same step.

Code: shell `apps/desktop/native/system-watch/main.cpp` (the `game` lines and the watch list on stdin), `apps/desktop/src/main/gameWatch.ts`, `games/launchers.ts`, `games/scan.ts`, `games/match.ts`, `games/icons.ts`, `systemWatch.ts`; bridge `apps/web/src/platform/bridge.ts` (`DetectedGame`, `RunningGame`, `CustomProgram`, `GameWatchSettings`, `DesktopInfo.gameDetection`), `platform.games`; client `apps/web/src/gameDetection.ts`, `gamePresence.ts` (what goes out, what a viewer shows), `GameLine.tsx` (the display), `GamesTab.tsx`, the tab "Spiele" in `SettingsDialog.tsx`. The library and the decisions behind it: `../squorli-directory/docs/features/games.md`; open work of the directory: `../squorli-directory/docs/PLAN.md`.

**The user's decisions (20 September 2026):** others shall see which game somebody plays, with the game's icon. Off by default; one switch turns it on, and then friends and server members see it ("show on servers" is an opt-out inside the feature, one switch for all servers at first). Games come from the launchers: the client reports the launcher's id (`steam:730`), and name and icon come from the directory, never from the playing user or a foreign chat server; everything else shows a name only. The user can hide single games ("never show this one"); that list fills from what is installed, not from what was played, so an embarrassing game can be hidden before its first start, and it is kept per device (changed on 21 September 2026: it follows the account inside the sealed settings, last entry). The game display and the AFK state stay independent: ten minutes without input or speech is away, even while a game runs. Fullscreen plays no part. Windows first, Linux within stage 2. Three stages: AFK signals (`docs/features/afk.md`), local detection (this entry), display for others.

**Stage 2, Windows part: local detection, nothing is sent (21 September 2026).**
- **What is installed.** `games/scan.ts` reads, without writing anything: Steam (`SteamPath` from the registry, `steamapps/libraryfolders.vdf`, every `appmanifest_<id>.acf`), the Epic Games Launcher's `.item` manifests (whole games only: `bIsApplication`, category `games`, not an add-on of another game, not unfinished), GOG's registry entries (not those that depend on another), and the Xbox app's folders (each drive's `.GamingRoot` names the folder, which the user may have renamed; `Content\MicrosoftGame.config` gives store id and name; add-on packs have nothing to start and are left out). Parsers in `games/launchers.ts` (pure, tested): Valve's text format, `reg query` output, the Epic JSON, the Xbox XML. Ids: `steam:<appid>`, `epic:<AppName>`, `gog:<id>`, `xbox:<StoreId>`, never an executable's name (names like game.exe collide). Not read yet: Ubisoft, EA, Battle.net, Riot.
- **What runs.** The shell hands the system watch helper a watch list on its stdin: the folders of the installed games and the executables the user added (`games/match.ts` `watchLine`). Once a second the helper walks the visible top-level windows from the top of the z-order down (no owned windows, no tool windows) and prints `game <path>` for the first one whose program lies in the list, which is the game used last, and `game` alone when none has a window any more. **The helper never reports a program outside the list**, and while detection is off the list is empty and the launchers' files are not even read. A program counts while it has a window of its own, minimized or behind other windows too, so a game that ran before the app or before the switch is found; a service that merely runs (Wallpaper Engine draws into the desktop's window and has none of its own) does not count. What is known about a process is asked once and forgotten every minute and at every new list. `gameOfPath` maps the path to the game (an added program by its exact path, else the deepest installation folder that holds it). Install paths stay in the main process; the client gets id, name and source.
- **Settings, per device** (`gameDetection.ts`, `chat.games.v1`: the switch, the hidden ids, the added programs; pure parts tested). Einstellungen > Spiele (only where `platform.games` exists): the switch with a text that says what is read and that nothing is shown to others yet; "Gerade erkannt"; the list of installed games and added programs with a tick each (no tick = never shown), a search from 12 entries, "Programm hinzufügen" (the system's file dialog through the shell, then a name) and "Neu einlesen". The shell checks added paths once more (`readGameWatch`: a full path of an .exe on a drive, no tabs or line breaks, at most 100). The list is read again when the tab opens, on "Neu einlesen" and hourly. When the display for others comes, the switch moves to the account's settings; the hide list stays on the device.
- **The build** of the helpers moves a running helper aside (`.exe.old`): Windows lets a file in use be renamed but not overwritten, and a developer's running app holds the helper. `electron-builder.yml` packs `*.exe` only.

Checked: typecheck, tests (desktop 49: `launchers.test.ts`, `match.test.ts`, the game lines in `systemWatchLines.test.ts`; web 295: `gameDetection.test.ts`), build, both helpers compile without warnings. The helper alone: a watched executable in front is reported within a second, a folder entry too (with umlauts elsewhere in the line), an empty list ends it, a folder that does not hold it reports nothing. The real scan on the user's computer: 33 games in 30 ms (Steam 26, Epic 2 of 8 manifests, Xbox 5 on two drives, one of them with a renamed folder, add-on packs left out; GOG is not installed there). The unpackaged app with a scratch profile over the DevTools protocol: `info.gameDetection`, no list while off, the app's own executable added as a program is reported as running, a malformed entry is dropped, no paths in what the client gets, switching off ends the running game. The tab by headless Chrome screenshots of a harness page (on, hidden game, off, end of the list with a long name and an added program). **Not checked: a real game in front** (Steam, Epic, Xbox: whether the path Windows reports for an Xbox game lies under its `Content` folder is open), a game protected by anti-cheat, the file dialog, GOG on a real installation, a packaged app.

**The user's first test and two fixes (21 September 2026):** "Ich habe ein Spiel im Vordergrund, es wird nichts angezeigt" (`pnpm dev:desktop`, Aviassembly from Steam, which the scan knew). **Stage 3, step 1: the directory's game library and its protocol part (21 September 2026).** `packages/protocol/src/directory.ts` (copied to the directory repo): `LibraryGameId` (`steam:<app id>`, `gog:<product id>`, `xbox:<store id>`; the ids the detection here produces for those launchers fit, Epic and added programs have no catalog and stay local with a name), `DirectoryGame` (`id`, `name`, `show`, `iconUpdatedAt`), `directoryGameUrl`, `directoryGameIconUrl`, `features.gameLibrary`. The directory answers `GET /api/games/<id>` with what the launcher's own catalog says, public and cacheable like avatars; `show: false` marks what is no game (Steam tells applications such as Wallpaper Engine and tools apart from games), so the playing client will not report it and viewers will not show it. No client code uses it yet. Checked here: typecheck, protocol tests 61 (2 new); the service side in the directory repo's notes.

**Stage 3, step 2: reporting the game (21 September 2026).** From here on something leaves the computer, so the texts of Einstellungen > Spiele say so. How it works:
- **Protocol** (`friends.ts`, copied to the directory repo; `index.ts`): `GamePresence` = `{ id?, name }`, `id` a `LibraryGameId` only, `name` one line of at most 64 characters (`GameName`). It rides on the `activity` report of both sockets as an optional `game` (a game, null = none, left out = the message says nothing about it, which is what clients from before send); `Member.game`, `Friend.game` and `friends.presence.game` default to null. No version bump and no new flag: servers and directories from before it drop the unknown field unread, older clients drop `game` from what they receive. The two switches are user settings and follow the account: `AccountSettings.games` = `{ enabled (false), servers (true) }`, optional without a default on purpose, like the message cue: an account from before it, or a directory that does not know the field, says nothing and the device's value stays (`accountSettings.ts`, all three functions; `VoiceSettings.games`).
- **What goes out** (`gamePresence.ts`, pure, tested): an id leaves the computer only when it is a launcher's id the directory's library can know; **the id of an added program contains its path and never goes anywhere**, such a game and an Epic one go out by name alone. The playing client asks the directory's library first (`directoryGameLookup`, once per id and session): `show: false` = nothing is reported (Wallpaper Engine, tools, the operator's word), an id the catalog does not know goes out by name alone, and when the directory cannot be asked, id and local name go out. The name is the directory's when it has one. The hide list and the switch are applied before all that (`GameDetection.state.shown`).
- **Who gets it:** `Store.setGame(game, onServers)` hands it to the directory socket always (friends) and to every chat server connection only while "Auch den Mitgliedern meiner Server zeigen" is on; fresh connections learn it after their welcome. The store stays free of the platform: App.tsx feeds it from the detection and the account's switch turns the detection on (`GameDetection.setEnabled`; the switch is no longer stored in `chat.games.v1`, which keeps the hide list and the added programs per device).
- **Chat server:** `Hub` keeps the game per connection like the idle state; a member's game is the last report among their connections and goes with that connection; presence listeners fire on a change, so the member list is broadcast (`state.ts` `Member.game`). The server only relays: it checks the schema and nothing else, viewers ask the directory. A connection's changes take effect at most every 5 s (`GAME_CHANGE_MS` in `ws/handler.ts`; each is a broadcast to everybody), what arrives in between waits and the last one counts. AFK and the game are independent. The directory does the same for friends and additionally drops a report whose id its library knows as "not shown".
- **A consequence of the user's decisions to know about (no longer true where the directory keeps sealed settings, last entry):** the switch follows the account, the hide list stays on the device. Switching the display on at one computer turns it on at every computer with the app, and a game hidden here is not hidden there. The settings' texts say both.

Checked: typecheck, tests (protocol 66 with `games.test.ts` 5; server 62 with 3 new in `hub.test.ts`; web 303 with `gamePresence.test.ts` 5, the rewritten `gameDetection.test.ts`, 1 new in `accountSettings.test.ts`; desktop 49), build. Smoke test on :3001 against a fresh scratch database without a directory: 121 green (4 new: a reported game reaches every member next to the afk state, an id that is no launcher's is refused while a name alone is relayed, a report without the field leaves the game alone, null removes it). The directory's side: its notes. **Not checked: the whole way from a running game in the desktop app to another client** (the pieces are tested one by one; nothing displays a game yet, that is step 3), two real people, a client and a server of different ages together (only by the schema tests).

**Stage 3, step 3: the display (21 September 2026).** "Spielt X" with the game's icon, in every client, the browser too (only the desktop app can report, everybody can see). Where: the member list (the line under the name; it takes the place of the handle line while somebody plays, the handle stays in the member's menu, which shows the game as well), the friends list (a second line under the name) and the head of a conversation with a friend. Offline members and friends show none.
- **What a viewer shows** (`gamePresence.ts` `shownGameOf`, pure, tested): a game with a launcher's id shows **the directory's name and icon**, whatever name the playing client sent along; what the directory does not call a game shows nothing, also when a client that did not ask reports it; while the directory's answer is still out nothing shows, so a hidden program never flashes up. A game by name alone (Epic, an added program), an id the catalog does not know and a directory that cannot be asked show the reported name, which is the playing user's own text like a display name, with a gamepad instead of an icon. Without a directory, or with one that has no library, every game shows by its reported name.
- **How** (`GameLine.tsx`): App.tsx hands the one `directoryGameLookup` it also reports with down through `GameLibraryContext`, so an id is asked once per session for both sides; `peek` answers what is known without a render in between, so a list drawn again does not blink; a failed request leaves its id alone for a minute (`GAME_LOOKUP_RETRY_MS`), since every row of a member list asks for the same game. The icon is a plain `<img>` from the directory (`directoryGameIconUrl`, cacheable for good through `?v=`), without a referrer, and gives way to the gamepad when it does not load. The full text is the line's tooltip, long titles are cut with an ellipsis.
- **What a viewer gives away:** asking for name and icon tells the directory this viewer's address and the game's id, not who plays it; the same as with avatars.
- **Not built, on purpose (the icons from the computer itself came on 21 September 2026, entry further down):** icons in the list of Einstellungen > Spiele from the directory. Asking the library for every installed game would hand the directory the list of a user's games, and the settings promise that only the running game is sent; icons there have to come from the computer itself (open in stage 2).

Checked: typecheck, tests (web 306: 3 new for `shownGameOf`, the lookup's test now covers `peek` and the minute after a failure), build. A harness page under the user's Vite with the real `MemberList` and `HomeSidebar`, by headless Chrome screenshots at 1500 and 700 px, **asking the public directory** (which carries the library since the user's update): Counter-Strike 2 shows the directory's name and its icon although the harness reported another name, a game by name alone and an id Steam does not know show the reported name with the gamepad, Wallpaper Engine and an app from the Microsoft Store (`show: false`) show the handle line and no game, an away friend shows moon and game, offline rows show none, a long title is cut; the member's menu by a DOM dump after a click. The harness was removed afterwards. **Not checked: the whole way with two real clients** (a running game in the desktop app, seen by another account), the head of a conversation (markup only), a phone's width beyond the friends list.

**Icons in the list of Einstellungen > Spiele, from the computer itself (21 September 2026, user's wish: "wollen wir noch die lokalen Icons einbauen für das settings menü?"):** never from the directory (see "Not built, on purpose" above: that would hand it the list of installed games). Nothing new leaves the computer.
- **Where they come from** (`launchers.ts`, `InstalledGame.icons` = sources, best first; like `dir` they stay in the main process): Steam keeps every library app's pictures in `<Steam>\appcache\librarycache\<appid>\`, where the small icon is the one picture named by its 40-hex hash (`steamIconFile`; before 2024 it was `<appid>_icon.jpg` next to the others, which is the second source); Epic: the executable the launcher starts (`LaunchExecutable` of the manifest); GOG: `goggame-<id>.ico` in the game's folder, then the registry's `exe`; Xbox: the logo pictures `MicrosoftGame.config` names (`Square44x44Logo`, `Square150x150Logo`, `StoreLogo`), then the executable; an added program: its own executable (`match.ts` `iconSources`). A file a manifest names relative to its folder is only taken when it stays inside (`fileInside`: no drive, no `..`).
- **How they are read** (`games/icons.ts`, `GameIcons`): a picture goes through Electron's decoder (`nativeImage.createFromBuffer`, at most 1 MB), an executable or `.ico` through `app.getFileIcon` (only for a file that exists, or Windows answers with its blank sheet); everything leaves as a PNG of at most 32 px in a data URL, so the client never gets a file's bytes as they are. 3 s per source, the next source when one gives nothing. An icon found is kept for the session, one not found is looked for again at the next request. Only the list for the settings gets icons (`IPC.gamesScan`); the hourly scan and the running game need none.
- **Client:** `DetectedGame.icon` (optional: an app from before it sends none), `GamesTab.tsx` shows it at 20 px between tick and name, a gamepad where there is none, and takes nothing but `data:image/`. The app's CSP already allowed `data:` pictures.
- Checked: typecheck, tests (desktop 55: the sources per launcher, `fileInside`, `steamIconFile`, `iconSources`), build. **The real scan and the real icon reader in Electron on the user's computer:** 35 entries, an icon for all 26 Steam games, both Epic games, all 5 Xbox games and an added program, none for a program that does not exist; 110 ms for all (1 ms the second time), 94 KB of data URLs together; looked at as a picture: the right icon next to every name. The list's markup with the built CSS by headless Chrome screenshots: icon rows, the gamepad row, a long name cut. **Not checked:** GOG (not installed there), the tab inside the running app, a packaged app.

**The line shows the game's name only (21 September 2026, user's wish: "ich möchte bei game.playing nur noch den Namen des Spieles haben, nicht mehr 'Spielt ' davor"):** `GameLine.tsx` shows icon and name, the tooltip is the name too (long titles are cut); the key `game.playing` is gone from both catalogs. Where older entries here say "Spielt X", the line now reads "X". Checked: typecheck, web tests, build; not looked at in a browser.

**The hide list follows the account, sealed (21 September 2026, user's decision: "Wir könnten in der verschlüsselten Variante dann auch aufnehmen welche Spiele der Benutzer nicht anzeigen möchte, dann muss man das nicht mehr auf jedem Client einzeln machen. Ich würde nur das nicht anzeigen übertragen, installierte Spiele ändern sich zu häufig. Generell sollte der Client bei jedem Start einmal die Listen aktualisieren."):** the reason for a list per device was that a readable list in the account tells the directory's operator what somebody owns and hides. The account's settings are now a blob only the user's key opens (`docs/features/settings.md`), and the list rides inside it (`SealedSettingsContent.hiddenGames`).
- **What travels** (`gameDetection.ts` `syncedHidden`): launcher ids of at most 64 characters, at most 1000. Never the id of an added program (it is its path; those marks and the programs themselves stay on the device) and never what is installed.
- **Merging** (`mergeHidden`, `GameDetection.adoptHidden`, `GameSettings.hiddenSynced`): while a device's list holds something the account has not seen (a device that meets the account's list for the first time, or a change made here that has not come back from the account yet) both lists are joined, so a game hidden here is never suddenly shown; otherwise the account's list replaces the device's launcher ids, so a tick set on another computer arrives. The cost of erring on the hidden side: a tick set again while the push failed is undone by the next status.
- **Who moves what:** App.tsx hands the account's list (`State.accountHiddenGames`) to the detection and the device's list to the store (`Store.setLocalHiddenGames`), which pushes it when it differs; after a successful push the list comes back through the state and marks the device as in step. A client without detection (a browser) never reports a list, and the store passes the account's on unchanged, so a browser's settings change cannot drop it. A push that waited for the first status joins the account's list in instead of overwriting it.
- **"Once per start":** both lists are refreshed at every start without new code: the account's status (and with it the hide list) is read after the directory lookup and after every fresh connection to a server, and the shell reads the launchers' installed games at the first `setWatch` with the switch on, which is the app's start (`gameWatch.ts`, then hourly, when the tab opens and on "Neu einlesen").
- **Only with sealed settings:** against a directory without `features.settingsSealed` the list stays per device, and Einstellungen > Spiele says which of the two applies (`games.listHint` / `games.listHintAccount`). The account's text says outright that the list of hidden games is stored at the directory, encrypted on the device first (user's wish the same day), and the tab's first hint no longer promises "never the list of your games" but "never which games are installed", which is true in both cases.
- Checked: `docs/features/settings.md`, same entry (tests, and the run of the real `Store` and `GameDetection` against a directory instance with two devices and a browser). Not checked: the tab's text in the app, two real computers.

**The screen share uses the detection (21 September 2026):** the share dialog marks a detected game's windows and preselects the codec for moving pictures for them (H.265 or H.264, `docs/features/voice-video.md`), and the dock shows "Quick Share" while a game is detected (`GameDetection.state.running`, a game hidden from others included: sharing it is the user's own click). The shell asks the helper which program a window belongs to (`windows` question) and matches the path like the running game (`GameLookup.gameOfProgram` in `gameWatch.ts`). Notes: `docs/features/voice-video.md`.

**Open in stage 2:** Linux (no helper there: Steam's `SteamAppId` in a process' environment is the likely way), more launchers, a small maintained list for programs that hide behind another executable (Minecraft Java is `javaw.exe`).

**Who may see my game (14 November 2026, user's wish: "Bei den Spielen soll man eine Blacklist und/oder Whitelist mit Benutzern machen können die es nicht sehen dürfen oder sehen dürfen"; the user's answers the same day: one rule for all games, not one per game; and yes to the keys of the chosen people passing through the directory and the chat servers).**
- **The rule** (protocol `directory.ts`): `GameAudienceSetting` = `{ mode: all | only | except, only: keys, except: keys }`, at most 200 keys per list (`GAME_AUDIENCE_MAX`). "Nur ausgewählte" with an empty list shows the game to nobody; both lists are kept so that switching the mode loses nothing. People are public keys: a directory account has the same key at the directory and on every server, a server account (`~name`) its own per server. The rule applies on top of the two switches: friends through the directory, members through each chat server.
- **Enforced at the relay.** Only the directory and the chat server know who receives a presence message, so the rule travels with the game: the `activity` report of both sockets takes an optional `gameAudience: { mode: only | except, keys }` (`gameAudienceOf(setting)`; left out = everybody; it counts together with `game` and is replaced with every report that names a game or none). No `PROTOCOL_VERSION` bump. Chat server: `Hub.setGame(ws, game, audience)` keeps it per connection **in memory only, never stored, never logged**; `Hub.gameFor(userId, viewerKey)` answers one viewer, and `membersFor()` in `state.ts` masks `Member.game` per recipient in the welcome, in `GET /api/state` and in every `structure` broadcast (the player always sees their own game; without any rule in the hub the list goes out unmasked as before). A changed rule alone fires the presence listeners. The status API carries no games. The directory does the same for friends (its notes).
- **Fail closed against relays from before it:** they drop the unknown field and would show the game to everybody. A chat server announces the ability in its state (`ServerState.gameAudience`, in every welcome), the directory in `features.gameAudience`; while a rule is set, `ServerConnection` and `DirectoryLink` report **no game at all** to a relay without it, and Einstellungen > Spiele names those relays.
- **Client:** `gameAudience.ts` (pure, tested: `withAudiencePerson`, `sameAudienceSetting`, `suggestAudiencePeople`, the names remembered on the device in `chat.gameAudienceNames.v1`); `VoiceSettings.gameAudience`, which follows the account inside the sealed settings only (`SealedSettingsContent.gameAudience`, cleaned by `cleanGameAudienceSetting`; the account's wins on a device, a device's change is pushed); `Store.applyGame()` hands every socket the game with the rule and runs on every settings save. `GamesTab.tsx`: "Wer mein Spiel sehen darf" with the three modes, the list of the mode with a remove button each, and a search over the friends and the members of every connected server (App.tsx builds them, without the user's own keys).
- **What it costs in privacy, said in the settings' text:** the chosen people's keys reach the directory and every chat server the game goes to with each report, for as long as the connection lasts. Nothing of it is stored there, but an operator could read it from memory. The alternative (the game encrypted per recipient) would work for friends with the direct messages' pair keys but not for server members; not built.
- Checked: typecheck, tests (protocol 158 with 5 new in `games.test.ts` and the sealed content's test, server 217 with the hub's, web 593 with `gameAudience.test.ts`), build. `pnpm smoke` on :3001 against a fresh database: 7 new checks (the state announces it; a game for selected people stays hidden from another member in the event and in the state; the player sees their own; the rule alone changing shows it; a deny list takes it away; a report without a rule shows it to everybody; a rule with mode "all" is refused). The tab's new section by headless Chrome screenshots of a harness with the real `GamesTab` (list, search hit, the privacy text). **Not checked:** the whole way with two real clients and a running game, the account round trip of the lists with two devices (the path is the one `cameraMirror` and the server order use), a server account's key picked from a member list in practice.
- **The entry in a person's menu (the same day, on the user's "kannst du die offenen Dinge nicht selbst erledigen?"):** `GameAudienceMenuItem.tsx` in the member list's menu and the friends list's menu, only while the game display is on: "Mein Spiel verbergen" / "wieder zeigen" under "Alle" and "Alle außer", "Mein Spiel zeigen" / "nicht mehr zeigen" under "Nur ausgewählte" (`audienceMenuAction`, pure, tested). Hiding under "Alle" switches to "Alle außer", so the people kept on that list from before are excluded again (Claude's decision). Not looked at in a browser.
- **Open (`docs/PLAN.md` section 4):** a rule per game, a test with two real clients.
