# Notifications of the operating system

Direct messages and mentions as notifications of the operating system, with a click that opens the conversation. Code: `apps/web/src/notifications.ts` (settings per device, text, tag), `apps/web/src/NotificationSettings.tsx` (Einstellungen > Töne), `store.ts` (`incoming`, `dmNote`, `mentionNote`), `App.tsx` (shows them, handles the click), `platform/types.ts` (`Platform.notifications`), `platform/web.ts` (Notification API), `platform/desktop.ts` + `platform/bridge.ts` (`notify`, `onNotificationClick`), `apps/desktop/src/main/notifications.ts` + `main/index.ts` (`showNotification`), `apps/desktop/src/preload/index.ts`.

## Built (27 September 2026)

From `docs/PLAN.md` 3.3 (user: "erledige alle Punkte aus 2"): "Desktop notifications (operating system notifications for mentions and direct messages; today only the taskbar mark and a sound), and browser notifications as an opt-in."

- **When:** exactly when the message sound plays (`attention.ts` `seesIncoming`): a direct message, or a live message that mentions the user, which the user does not see right now (window hidden, without the focus, or another conversation open). A blocked person's messages never get there (stage 3 of the reports). Channels that notify on every message do not notify here; that is the same rule as the sound.
- **What:** title = who (a direct message), or "who · #channel (server)" (a mention); body = the text as one plain line, mention tokens as @Name, Markdown's marks dropped, at most 180 characters (`notificationBody`), or "Neue Nachricht" when the preview is switched off. `tag` = `dm:<peer>` or `mention:<host>:<channelId>`: a browser replaces an older notification of the same conversation, and a click opens it (`parseNotificationTag`: the conversation in the home view, or the server and the channel).
- **Desktop app:** the client sends `{ title, body, tag }` over the bridge (`IPC.notify`); the main process checks it (`readNotification`: strings, cut to 120/300 characters) and shows an Electron `Notification`, silent (the client plays its own sound), with the app icon (Windows takes it from the AppUserModelID, Linux gets `build/icon.png`, now packaged). A click restores and focuses the window and sends the tag back (`IPC.notificationClick`). Notifications are kept referenced until clicked or closed (Windows loses the click handler of a collected one). Permission: "granted" at once; an app older than this client has no `notify` and shows none ("unsupported", the settings say an update brings them).
- **Browser:** the Notification API, only on a secure page and never on a phone (mobile browsers need a service worker for it). Off until switched on; the switch asks for the permission inside its click. "denied" explains the site settings.
- **Settings:** Einstellungen > Töne, section "Benachrichtigungen": on/off, "Nachrichtentext in der Benachrichtigung zeigen", "Test-Benachrichtigung". A choice per device (`chat.notifications.v1` in localStorage), not of the account.

### Decisions made by Claude, confirmed by the user on 27 September 2026

- Per device, not in the account's sealed settings: whether the system may show them is a property of the device and of the browser's permission, like the output device.
- On by default in the desktop app, off in a browser (the plan's "opt-in").
- The switch for the text in the notification (for a screen others see), on by default.
- Only what makes the sound: no notification for every message of a channel set to "all".
- The shell's notification is silent; the client's own message sound stays the one sound.

### Checked

- `notifications.test.ts` (3: the body text, title and tag, the tag read back), desktop `pure.test.ts` (`readNotification`).
- The unpackaged Electron app (44.4.2) driven over the DevTools protocol with a test page under `app://squorli`: platform "desktop", permission "granted", a notification sent over the bridge without an error in the main process; the settings block rendered (screenshot).

### Not checked

## 27 September 2026, later: the sender's name and full screen

The user's report after desktop app 0.8.1: the test notification came "from electron", and a wish: "Ich sollte in den Einstellungen auswählen können, ob die Benachrichtigungen auch kommen dürfen, wenn ich in einer Vollbildanwendung bin (z.B. Spiele)".

- **Sender "electron":** Windows names a toast after the Start menu shortcut that carries the app's id (`com.squorli.desktop`); without one (the unpackaged app, an installation whose shortcut lacks the id) it falls back to the program's file name. The registry key `HKCU\Software\Classes\AppUserModelId\com.squorli.desktop` was missing on the user's machine. The shell now writes it at every start (`main/index.ts` `registerAppId`, `main/notifications.ts` `appIdRegistration`, `reg add`): `DisplayName` "Squorli" and `IconUri` = `build/icon.png` copied out of the app's archive into userData (Windows cannot read inside the archive).
- **Full screen:** Einstellungen > Töne, "Auch bei Spielen und Anwendungen im Vollbild", off by default, shown only where the shell can tell (`Platform.notifications.knowsFullscreen`: the desktop app on Windows with the system watch helper). The client sends `inFullscreen` with each notification (the test notification always true); before showing one without it, the main process asks the helper (`busy<TAB><request>`, `systemWatch.ts` `fullscreenBusy`, 400 ms, unknown = show): Windows' `SHQueryUserNotificationState` (2 full screen application, 3 Direct3D exclusive full screen, 4 presentation mode, 7 Store app in full screen) or a foreground window that covers its monitor (a borderless game; the desktop and the task bar do not count). A notification held back this way is dropped, the sound and the task bar mark stay.

**Decisions made by Claude, confirmed by the user on 3 October 2026:** off by default (games are the case the user named); a notification held back is not shown later; the test notification ignores the setting; the registry key is written at every start.

**Uninstall (user's wish, same day: "bei einer Deinstallation alle Registry-Einträge löschen"):** `apps/desktop/build/installer.nsh` (`customUnInstall`) deletes every entry the app writes itself: this AppUserModelId key, `HKCU\Software\Classes\squorli` (the `squorli://` links, `setAsDefaultProtocolClient`) and the value "Squorli" under `Run` and `Explorer\StartupApproved\Run` (start with the system). Not on an update (`${isUpdated}`: the new installer runs the old uninstaller with `--updated`). It works from the first installation made with the release that brings it (an older installation still runs its old uninstaller). The app's data folder stays (`deleteAppDataOnUninstall: false`, unchanged). **Checked:** the NSIS installer builds with it. **Not checked:** a real uninstall (it would have removed the user's installed app).

**Checked:** desktop `pure.test.ts` (`inFullscreen`, `appIdRegistration`, `readNotification` with the flag), typecheck, web tests; the rebuilt helper answers `busy\t7` with `busy\t7\t5\t0` (accepts notifications, nothing in full screen); the unpackaged app wrote the registry key with "Squorli" and the copied icon (the test's key was deleted afterwards). **Not checked:** a toast on screen with the new name, a real game in full screen (exclusive and borderless), Linux (no full screen check, the setting is not shown).

**After 0.8.2 (same day):** the installed 0.8.2 still showed "electron". Cause, on the developer's machine only: a Start menu shortcut `Electron.lnk` (created 27 September 2026 13:21, not by the repo's code or by Claude; most likely by Electron for the notifications of the unpackaged app) pointed at the development `electron.exe` and carried the id `com.squorli.desktop`; `Get-StartApps` named the id "Electron", and a shortcut wins over the registry key. The unpackaged app now uses an id of its own, `com.squorli.desktop.dev` ("Squorli (dev)" in the registry), so a development app never names the installed one again; the shortcut was deleted and the key's `IconUri` pointed back at the installed app's copy (the development app had overwritten it). A machine that never ran the development app is not affected; 0.8.2 itself needs no new release for this. **Checked:** `Get-StartApps` names `com.squorli.desktop` "Squorli" afterwards. **Not checked:** the toast on screen (the user's next test).

**Direct messages show no text in a notification until the user says so (2 October 2026, security audit C7):** direct messages are end-to-end encrypted, but the system may keep a notification's text in plain text (Windows keeps them in a database that outlives the window). The setting `preview` stays for mentions in channels (their text is plain on the server anyway); a new setting `dmPreview` (Einstellungen > Töne, "Text von Direktnachrichten ... zeigen") is **off by default, also for a device whose stored settings predate it**, so a direct message notifies with "who wrote" and "Neue Nachricht". Decision, Claude's and unconfirmed: privacy over convenience as the default; the user may want the text on again by default. Checked: the setting's default and a stored one without the field (`notifications.test.ts`), typecheck, both catalogs. Not checked: the toast on screen. Needs a new app version.
