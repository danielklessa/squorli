# Feature notes: updates that restart only what changed, `squorli update --check`, automatic updates (`squorli autoupdate`)

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. Standing rules live in the `AGENTS.md` of the area (`deploy/AGENTS.md`, `deploy/windows/AGENTS.md`). Whoever changes the feature adds or updates its entry here in the same step.

Code: `apps/server/package.json` (`squorli.autoUpdateFrom`), `.github/workflows/stable-image.yml` (the tag `stable`), `deploy/install.sh` (the helper inside `write_helper`: `app_image`, `wanted_ref`, `use_stable`, `changed_services`, `server_says`, `by_hand`, `backup_to`, `server_up`, `auto_words`, `auto_hours`, `auto_off`, the commands `update` and `autoupdate`), `deploy/windows/install.ps1` (`$Programs`, `$ServiceNeeds`, `Read-Changes`, `Stop-Running`, `Stop-Changed`, `Copy-Programs`, `Write-Configuration`), `deploy/windows/build-package.ps1` (the mark in `manifest.json`), `deploy/windows/check-versions.mjs` (the mark is a version), `deploy/windows/squorli.ps1` (`Invoke-UpdateSteps`, `Get-ReleaseRule`, `Get-Rule`, `Test-ByHand`, `Stop-ByHand`, `Write-AutoLog`, `Start-AutoRun`, `New-AutoTaskXml`, `Register-AutoTask`, `Get-AutoTask`, `Invoke-AutoUpdate`), `deploy/windows/uninstall.ps1`, `deploy/windows/test/acceptance.ps1` (`New-TestPackage`, `Test-Update`, `Test-AutoUpdate`). ## Built (28 September 2026)

**The user's wishes.** First a question: "kann ich unter Windows und linux einen job anlegen, der 1x pro Stunde prüft ob es eine neue Version gibt und nur die Teile Updatet (stoppt und wieder startet), die eine neue Version haben?" The answer named what existed (Linux: Compose recreates only the containers with a new image; Windows: an update stopped all four services) and four things to build; the user: "alle Punkte, wenn autoupdate eingeschaltet wird soll ein interval in Stunden zwischen 1 - 24 abgefragt werden (gerne mit Warnhinweis)".

1. **`squorli update --check`** (Windows also `-Check`): looks and changes nothing that runs. Exit code 10 when something is new, 0 when not, 1 for an error.
2. **An update on Windows stops only what changed.** The setup compares the versions of the programs in the installation's and the package's `manifest.json`. With a new version of Squorli alone, PostgreSQL and LiveKit keep running; the app server and, in the bundled mode, Caddy (which needs the app server) restart.
3. **A backup before the update on Linux,** as on Windows: `squorli update` backs up when it found a new image; a backup that fails stops the update.
4. **`squorli autoupdate on [hours] | off`,** without a word the state: a job that runs `squorli update --auto` (Windows: `-Auto`) every 1 to 24 hours. It shows a warning and asks for the hours; the default is 24.

### Decisions of the user (28 September 2026)

- **The job runs at minute 17** ("Minute 17 finde ich gut").
- **A version that asks for work by hand must not install itself** ("die Markierung bitte noch baue"): the section "The mark" below.
- **The bundled Caddy** was not run with the partial update, and it restarts with the app server; the user: "Mit Caddy ist in Ordnung".

### Decisions made by Claude, not confirmed by the user

- **What "new" means on Linux:** after a pull, a service is new when its running container has another image than the one its tag names now. The registry is not asked directly, so `--check` downloads the new images (it starts none of them). Reason: it works with every registry, with a sign-in and with both image stores of Docker, and the job needs the pull anyway.
- **On Linux a fixed version in `APP_IMAGE` never gets a new Squorli** by this way; `autoupdate on` says so when the tag is not `latest`. The images of PostgreSQL and Caddy have moving tags (`16-alpine`, `2-alpine`) and come along; LiveKit is pinned.
- **What "new" means on Windows:** a release on GitHub with a package whose version is higher than the installed one (as `squorli update` decided before). Which services stop is decided by the versions `manifest.json` names, not by comparing files. The same version once more replaces everything, which keeps `squorli update -Version <the installed one>` a repair.
- **A service whose configuration changed restarts too** (a template of the new version fills differently), also when its program did not change: it would not read the new file otherwise.
- **The exit code 10** for "something is new".
- **When the job runs** (the minute is the user's decision, above)**:** every 24 hours means 04:17, every n hours means counted from 00:17 by the clock of the machine, not from the moment it was switched on. A run that was missed because the machine was off is made up (`Persistent=true`, `StartWhenAvailable`).
- **Where the job lives:** Linux: a timer of systemd when systemd runs, else a file in `/etc/cron.d`, else `autoupdate on` refuses and names the line for root's crontab. Windows: the task `SquorliAutoUpdate`, run by SYSTEM, never twice at once, ended after four hours at the latest.
- **The job never starts what somebody stopped,** as long as nothing is new: on Linux a service without a running container is not looked at and the job runs no `up`, on Windows nothing is touched. When there is a new version, the update starts every service, as `squorli update` does.
- **No way back on Linux:** an update that fails stays; the log names the backup. Windows brings the program files of before back, as before.
- **The warning** comes every time `autoupdate on` runs, also when the hours are given on the command line. It says: the app server restarts whenever a version appears; a version that asks for work by hand is not installed by the job; backups stay and take space; what happens when an update fails; 24 hours are recommended. Linux adds the moving tags of PostgreSQL and Caddy. There is no second question (yes or no): the question for the hours is the place to stop (Ctrl+C).
- **The logs:** `autoupdate.log` (Linux: in the installation's folder; Windows: in `logs`) holds one line per run that found nothing, with the time in front, and the lines of an update; above 1 MB it is cut to its last 2000 lines. On Windows a run that updates also writes a transcript `logs\update-<time>.log`.
- **`--no-backup`** on Linux for an update without the backup (a broken database that cannot be dumped must not keep the fix away). Windows has no such option; its update stops when the backup fails.
- **`-Check` refuses `-Version` and `-Package`.**

### The mark: a version that asks for work by hand (28 September 2026, user's wish)

`apps/server/package.json` carries `"squorli": { "autoUpdateFrom": "<version>" }`: **the version from which on an installation may update to this one by itself.** It travels with the server: in the image as `/app/package.json`, in the package for Windows as `autoUpdateFrom` of `manifest.json`. The first value is `0.6.0` (the release that renamed the Compose service).

- **The rule,** the same on both systems (`Test-ByHand`, `by_hand`): the step asks for a person when the installed version is older than the new version's mark **and** the installation does not carry the same mark itself. The second half is for images of the default branch, which keep the last release's version number until the next release is prepared: a change there that needs work by hand raises the mark to the version that comes next, and an installation that took it by hand carries that mark too.
- **The run of the job** leaves such a version alone, writes a line into `autoupdate.log` that names the release notes, and ends with code 10. On Windows it asks before the download (it reads `apps/server/package.json` at the release's tag from raw.githubusercontent.com; when that cannot be read, the run changes nothing and ends with code 1) and again after it, from the package's own manifest, whose checksum was checked. On Linux it asks the two images (`docker run --rm --entrypoint node <image>`), the running one and the one the tag names after the pull.
- **`squorli update` by hand** names the release notes and asks "Read and done? Then type yes"; `-Yes` (Linux: `--yes`) answers it. **`--check`** says that the version asks for work by hand.
- **A version without a mark** (every release up to 0.6.0) asks for nobody.
- **Decisions made by Claude, not confirmed by the user:** the mark is a version in `package.json`, not a line in the release's text (one source for image, package and job; the text of a release can be edited on GitHub); the question for a run by hand; code 10 for the job that leaves a version alone; an image that cannot be asked (no `node`, no `package.json`) counts as without a mark; when the mark blocks the server's image on Linux, the new images of the other services wait too.
- **What it does not do:** it keeps no installation from a version whose notes nobody marked. Whoever prepares a release decides (skill `server-release`, step 5). On Linux the pull has happened when the job stops: whoever runs `squorli up -d` afterwards starts the new image without being asked.

### The tag `stable` (28 September 2026)

Claude had named it as open: on Linux the job follows the tag in `APP_IMAGE`, the install script enters `latest`, and `ci.yml` publishes `latest` with every push to the default branch, a commit for the desktop app included. A server with automatic updates would restart for every push and run what no release names. The user: "sollten wir stable schon jetzt einbauen bevor wir den release machen? Wenn du das für besser hältst, dann tue das." Built before the release, so nobody has to change over later.

- **`ghcr.io/danielklessa/squorli-server:stable` names the newest published release.** `.github/workflows/stable-image.yml` runs when a release is published on GitHub (not a draft, not a prerelease, a tag `v<version>`; the desktop app's releases are left out) and gives the image `:v<version>`, which `ci.yml` built when the tag was pushed, the second name (`docker buildx imagetools create`). A release that is not the newest published one (a fix for an older version) leaves `stable` where it is. It can be started by hand with a tag.
- **Published, not tagged:** `stable` moves when the release is published, which is also what `squorli update` on Windows looks at. Between the tag and the publication the package for Windows is built and tested.
- **`squorli autoupdate on`** says what `latest` means when `APP_IMAGE` names it, and asks "Switch to stable?" (default yes). With yes it pulls `<image>:stable`; only when that works it writes `APP_IMAGE` (the old `.env` is kept as `.env.bak.<time>`), else it says so and leaves the file. With the hours on the command line it asks nothing: `--stable` switches, `--latest` keeps, without either it names `--stable`. A fixed version is named as before; the text now points to `stable`.
- **The server's wanted image is the one `.env` names** (`wanted_ref`), not the one its container was made from: after the switch the next run finds `stable` new and installs it.
- **Decisions made by Claude, not confirmed by the user:** the workflow of its own instead of a tag in `ci.yml` (published instead of tagged); the question with the default yes; the install script still enters `latest`, and README, website and `portainer.yml` still show it (open in `docs/PLAN.md`: `stable` does not exist before the first release is published with this workflow, and the install script is live with the push); nothing for the registry of GitLab.
- **What an operator should know:** the switch takes the server to the newest published version with the next update. Whoever runs a newer state of `latest` than that goes back to it; migrations of the database are not undone.

### Consequences

- **Release notes and the mark belong together:** a version whose "Before you update" asks an operator to do something gets the mark, or it installs itself where automatic updates are on.
- **Existing installations:** on Linux the helper is written by the installer, so the new commands arrive when the installer runs again ("Update"); on Windows they arrive with the package, that is with `squorli update` to the first release that carries them. The update from 0.6.0 is already a partial one: the new package's `install.ps1` decides, and 0.6.0's `manifest.json` names the versions.
- **`squorli backup` on Linux** removes half a backup now and ends with code 1 and a text when it fails (it left the folder before).
- **The website's guide** describes the commands; it may go live when the server is pushed (Linux) and a release carries them (Windows).
