## Built (25 and 26 September 2026, the user's decision of 25 September 2026 in the plan cleanup: "yes")

The plan (`docs/PLAN.md` 2.1 until then): a `squorli doctor` in the installer's wrapper and a check in Verwaltung > Server that test what fails most often, with messages that name the likely fault. The known faults are the ones of `deploy/AGENTS.md` ("Known pitfalls: LiveKit connectivity") and `deploy/proxies/README.md`.

### Three viewpoints

A machine cannot tell whether its own ports are open from the internet, and nothing but a real WebRTC connection tells whether UDP arrives. So the check runs from three places and says which one is speaking:

1. **The server itself** (`GET /api/doctor`): fetches `https://PUBLIC_DOMAIN/api/health` (DNS, certificate, the proxy's target; the answer must carry this server's own key, else "another Squorli server answers here"), opens a WebSocket to `/api/ws` (the proxy passes the upgrade), fetches `/rtc/validate` where `LIVEKIT_PUBLIC_URL` points (401 = the proxy forwards `/rtc` to LiveKit; in dev that is LiveKit itself on 7880), asks LiveKit internally with the API key (`RoomServiceClient.listRooms`: "unreachable" or "auth"), connects to `PUBLIC_DOMAIN:LIVEKIT_TCP_PORT` (a warning only when it fails: from the machine's own address this can be hairpin NAT), and registers at the directory afresh (a success proves the directory reached `DIRECTORY_PROOF_URL` from outside; a failure is classified: unreachable, `host_unverified` with the directory's detail, 429, other). The request that asked for the report adds its own view first: the `Host` header against `PUBLIC_DOMAIN` (else sign-ins fail with `signature_invalid`), whether `X-Forwarded-For` came from a proxy in `TRUSTED_PROXIES` (else every member shares the proxy's address in the rate limits and the log), and whether the scheme survived (`X-Forwarded-Proto`).
2. **The directory from outside** (`POST /api/servers/probe` with the server's token, when the directory answers `features.probe`): repeats health (with the key), WebSocket, `/rtc/validate` and one TCP connect to the media port from where the directory stands. The origin comes from the `proofUrl` proven at registration, never from the request; in production the TCP connect is skipped when the host resolves to a private address (no port scan of the directory's network); one probe per host and `REGISTER_RATE_LIMIT` window. An older directory without the route makes the server say "no check from outside".
3. **The administrator's browser** (`POST /api/doctor/rtc-token`, room `doctor-<userId>`, nothing published, two-minute token): a real LiveKit connection with a 12 s peer-connection timeout, then the selected ICE candidate pair out of the subscriber transport's stats (`selectedPath`): UDP to a public address = fine; TCP = UDP does not get through from that network (the TCP fallback works, quality suffers); a relay = TURN; a private announced address = `LIVEKIT_NODE_IP` missing; no media connection at all = the ports or `LIVEKIT_NODE_IP` (the "participant drops after 15 s" case); a signal failure = `/rtc` not forwarded or `LIVEKIT_PUBLIC_URL` wrong; a refused token = key and secret. `roomsByIdentity()` skips `doctor-*` rooms, so the test room never becomes a voice presence.

Every check is `{ id, status: ok | warn | fail | skip, text: { de, en }, detail }`. The texts come from the server in both languages so that the wrapper on the host and the admin panel say the same thing, and the web client shows `text[locale]` (a deliberate exception from "UI texts come from the catalogs": the diagnostic vocabulary lives in one file, `doctor.ts`, and the terminal has no catalog). The browser's own media result uses the catalogs (`admin.doctorMedia.*`), because only the client knows it.

### `squorli doctor`

The wrapper the installer writes (`deploy/install.sh`, `write_helper`) gets `doctor`: it lists the containers, resolves `PUBLIC_DOMAIN` on the host, then asks the server container over the loopback address (`docker compose exec server node -e ... http://127.0.0.1:3000/api/doctor`) and prints each check with a mark in the installer's language (`# lang:` line in the wrapper, next to `# setup:`); exit 1 when a check failed; a closing line says that only a browser can check UDP. The loopback exception of `GET /api/doctor`: no session needed when the request comes from 127.0.0.1/::1 without any forwarding header (`isLoopback`); a proxy on the same host forwards from the Docker network, never from loopback. In development the Vite proxy is loopback, which is the developer's own machine.

### Without containers (28 September 2026, the package for Windows, `docs/features/windows.md`)

The command of a Windows installation (`deploy/windows/squorli.ps1`, `doctor`) lists the services, resolves `PUBLIC_DOMAIN` and asks `GET /api/doctor` where the app server listens (`LISTEN_HOST`: 127.0.0.1, or the machine's LAN address with a proxy on another machine). The loopback exception proves nothing there: a proxy on the same machine arrives from 127.0.0.1 like the command does. So the server knows a second rule (`isLocalCaller`, tested): **with `DOCTOR_TOKEN` set, a request without a session reads the report only when it carries that value in the header `x-squorli-doctor`**, from whatever address; loopback alone is refused then. With the variable empty (Docker, development) the loopback rule holds as before. The value is compared through hashes of the same length. The setup for Windows makes it like the other secrets.

The texts that name what to look at have two wordings, chosen by `process.platform` (`onPlatform` in `doctor.ts`, tested): "the livekit container" and `squorli up -d`, or "the service SquorliLiveKit" and `squorli restart`. Verwaltung > Server shows the same texts.

Both are decisions made by Claude, confirmed by the user on 28 September 2026. The smoke test takes `SMOKE_DOCTOR_TOKEN` for a server that has the variable set. Checked: `docs/features/windows.md`, phase 4.

### Decisions made by Claude, confirmed by the user on 3 October 2026

- Texts in both languages from the server (above), a stable `id` per check for scripts.
- The directory probes TCP and never UDP (nothing answers a bare UDP packet on LiveKit's port); UDP is the browser's job. The plan had left this open ("the directory could offer an echo, to decide when building").
- `LIVEKIT_TCP_PORT`/`LIVEKIT_UDP_PORT` are passed to the server container too (`compose.yml`; defaults 7881/7882 in `config.ts`) so the report names the right numbers.
- Since 30 September 2026 (`docs/features/limits.md`) the TCP media check resolves the media node's address, not always `PUBLIC_DOMAIN`: `LIVEKIT_NODE_IP` when set (the server reads it now too), else the host of `LIVEKIT_PUBLIC_URL` when it names another machine, else `PUBLIC_DOMAIN` (`mediaHost()`, tested). A media node on another host than the app server was probed at the wrong address before.
- Since 3 October 2026 (`docs/features/dynamic-ip.md`) `mediaHost()` ignores `LIVEKIT_NODE_IP` when `LIVEKIT_DYNAMIC_IP` is set: the job changes `.env` and restarts LiveKit, not the app server, so the value in the process may be stale; `PUBLIC_DOMAIN` (dynamic DNS) decides then.
- One doctor run at a time per server (a second caller shares the running one), 10 runs per IP and minute (`ipDoctor`), because every run opens connections outward and re-registers at the directory (its registration limit is 10 per minute and IP).
- A failed TCP connect from the server itself is a warning, not a failure (hairpin NAT is common); the directory's and the browser's verdicts are the ones that count.
- The wrapper's texts are the server's; the wrapper adds only the container list, the host's DNS view and the closing line about UDP.
