# Feature notes: Global hotkeys, push-to-talk across the system, control from outside (desktop app)

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. Whoever changes the feature adds or updates its entry here in the same step.

Code: `apps/web/src/platform/hotkeys.ts` (the rules both sides share, DOM-free, tested), `bridge.ts` (the types and IPC channels), `HotkeysTab.tsx` (Einstellungen > Tastenkürzel), the capture in `SettingsDialog.tsx`, `applyControl` in `App.tsx`, `voice/sounds.ts` (`FEEDBACK_TONES`), `voice/settings.ts` (`VoiceSettings.hotkeys`); shell `apps/desktop/src/main/hotkeys.ts`, `controlArgs.ts`, `keyCodes.ts`, `systemWatch.ts` (`setKeys`, `onKey`), the helper `apps/desktop/native/system-watch/main.cpp` (`keys` command, `key` lines).

## Built (22 September 2026, user's wish: "Die app soll globale Tastenkürzel registrieren können, auch für Systeme wie Elgato SteamDeck oder LG Hub soll es die Möglichkeit geben das Mikrofon oder die Lautsprecher zu muten", and while it was built: "push to talk soll natürlich auch global möglich sein")

Three things, all desktop app only (a browser cannot see keys outside its tab):

- **Global shortcuts** for "Mikrofon stumm / an" and "Ton aus / an": Einstellungen > Tastenkürzel (a new category, shown where `platform.hotkeys` exists). A binding is captured like the push-to-talk key (`KeyboardEvent.code` plus the modifiers held), shown as "Strg+Umschalt+M"; the shell turns it into Electron's accelerator (`hotkeyAccelerator`) and registers it with `globalShortcut`, which the system delivers whichever window has the focus and **takes from every other program** while the app runs (the settings say so). The shell answers per binding whether it is registered, held by another program (`taken`: `register` returned false) or impossible (`invalid`), and the tab shows it. **Rule (Claude's decision): a key without Ctrl, Alt, Shift or Win is accepted only for the function keys, the number pad and the media keys** (`bareKeyAllowed`): a bare letter or Space would be taken from every program; F13 to F24 are what a Stream Deck or G Hub sends and no keyboard has them. A refused key leaves the old binding and shows why. Escape cancels a capture; a modifier alone waits for the key. While a capture runs the shell lets all shortcuts go and watches no key (`suspendHotkeys`), because a registered shortcut never reaches the window; the dock's push-to-talk listener stays quiet like for the push-to-talk key.
- **Push-to-talk across the system (Windows):** the push-to-talk key needs its release too, which a global shortcut never reports, and it must not be taken from the game. So the system watch helper (`squorli-system-watch.exe`) watches it: the client names the key (`HotkeyRequest.pttKey`, only while in a voice channel with push-to-talk chosen and not the AFK channel), the shell maps the code to Windows' scan code (`keyCodes.ts`, Chromium's own table, E0-prefixed keys marked) and sends `keys<TAB><hex>` to the helper, which registers the keyboard with Raw Input (`RIDEV_INPUTSINK`, delivered whatever window has the focus) **only while a key is named**, reports **only the named keys** as `key <hex> 1|0` (a held key once), and takes them from nobody. Input made by a program without a scan code (some macro tools) is mapped from its virtual key. The client applies `setPttHeld`; a press while this window has the focus and a text field is being typed in is ignored like in the window's own listener, a release always counts; the shell releases when the watch changes or the helper ends. **The helper's promise changed from "reads no keyboard" to "of the keyboard only the keys the app names, while it names them"** (its header, `apps/desktop/AGENTS.md`). No switch: in the app the push-to-talk key simply works system-wide; the texts under Sprache und Audio and Tastenkürzel say so, and on a system without the helper (Linux, an app without the native build) that it works in the window only. **Not built:** mouse buttons as the push-to-talk key (a Raw Input mouse watch would be the same pattern; a G Hub can map a mouse button to a key meanwhile).
- **Control from outside** for a Stream Deck, G Hub or any macro tool, two ways: (1) the device sends one of the shortcuts (Stream Deck "Hotkey", G Hub key assignment); (2) it opens `squorli://control/<action>` (Stream Deck "System > Website") or runs `"<Squorli.exe>" --control=<action>` (G Hub "launch application"); actions `mic-toggle`, `mic-on`, `mic-off`, `deafen-toggle`, `deafen-on`, `deafen-off` (the explicit ones for buttons without a state of their own). The second start hands its arguments to the running app (single-instance lock, `findControl` in `controlArgs.ts`), which carries the command out **without bringing its window to the front** (`second-instance` returns before show/focus); a start with a control argument while the app is not running only starts it (nothing to control yet). The tab lists the links with a copy button each and, in a packaged app, the command line with its own path (`DesktopInfo.hotkeys.executable`). `deepLinkArgs` ignores control links (they fail `parseDeepLink`), and `parseControlAction` ignores everything but the six actions.
- **Feedback:** every command from outside plays a short tone (`FEEDBACK_TONES`: rising for on, falling for off; `VoiceClient.playFeedback`), because whoever pressed it may not see the window; it follows the common volume of the cues and, unlike the cues, sounds deafened too (the user asked for the state). Mute and deafen follow the buttons' rules (`voice/AGENTS.md`: unmuting while deafened lifts both, the AFK channel refuses); outside a channel a command does nothing.
- **Storage (Claude's decision, confirmed by the user on 25 September 2026):** the bindings are **per device** (`VoiceSettings.hotkeys`, `chat.voice.v1`, like the microphone boost) and not part of the directory account: a combination that is free on this computer may be held on another, and a Stream Deck's configuration lives on one computer too. The tab says so. The push-to-talk key stays where it was (account).
- **Linux:** `globalShortcut` works with X11 only (the tab says so); the push-to-talk watch needs the helper, which is Windows only.

**Checked (22 September 2026):** root typecheck; tests (web 354 with `platform/hotkeys.test.ts`, desktop 61 with `findControl`, `scanCodeOf`, `keysLine` and the `key` lines). The helper alone, driven by a Node script with `SendKeys` (`SendInput`): nothing before keys are named, `key 39 1` / `key 39 0` for Space once named, nothing after `keys` cleared them, F13 (sent by virtual key) reported as `key 64`. The unpackaged app over the DevTools protocol through the real bridge: `setHotkeys` with F13 and Ctrl+Shift+M and the push-to-talk key Space answers all `ok`, the three keys sent with `SendKeys` arrive as `mic-toggle` (hotkey), `deafen-toggle` (hotkey) and `ptt` down/up; suspended nothing arrives, after the resume F13 does again; Ctrl+Pause answers `invalid`, a bare `KeyM` `invalid`, push-to-talk key `Pause` `invalid`; a second start with `squorli://control/mic-toggle` and one with `--control=deafen-on` each exit 0 and reach the client as external commands, `squorli://control/quit` does nothing. The tab rendered with the built stylesheet in headless Chrome (screenshot looked at). **Not checked:** a real Stream Deck or G Hub; the tone by ear; the mute really toggling in a voice channel from a shortcut (the test client was on the login screen: `applyControl` is the same code as the buttons); a packaged app (the `executable` line); Linux; a key held while the app quits; two keyboards. **Needs a new desktop app release** (shell, helper and client changed); a newer client in an older app shows no Tastenkürzel category (`info.hotkeys` missing), an older client in this app registers nothing.

## Keyboard layout (24 September 2026, user's report: "Beim Einstellen von Tastenkürzeln soll die Tastatursprache beachtet werden, wenn ich strg + ö binden möchte steht da bisher \"Strg+Semicolon\"")

Two faults, one visible: (1) the label came from `KeyboardEvent.code`, which names the key's position on a US keyboard, so a German Ö showed as "Semicolon"; (2) worse, the shortcut registered was the wrong key. Windows registers a shortcut by virtual key, and Electron turns the accelerator ";" into VK_OEM_1, which is **Ü** on a German keyboard (Ö is VK_OEM_3, Electron's "`"); the same for Y and Z, whose positions are swapped. Checked with a bare Electron app on this German Windows: `SendKeys` Ctrl+Ö fired the registered "Control+`", not "Control+;"; Ctrl+Y fired "Control+Y", which the code `KeyZ` would have registered as "Control+Z".

- **Registration:** on Windows the capture keeps the layout's virtual key of a letter, digit or punctuation key (`HotkeyBinding.vk` = `KeyboardEvent.keyCode`, `hotkeyFromKey(e, true)`); `hotkeyAccelerator` names such a binding by its virtual key (`vkAcceleratorKey`: letters, digits and the eleven OEM keys Electron has characters for). A virtual key without such a character (the German `<` key, VK_OEM_102) is `unknownKey` as before. Bindings stored before keep working as they did (no `vk`: by position). Linux and a browser store no `vk` (X11 maps an accelerator differently; not examined).
- **Label:** `keyName(code, layout)` shows what the layout writes with a letter, digit or punctuation key, upper case (`Ö`, `Y`, `ß`), from `navigator.keyboard.getLayoutMap()` (`keyboardLayout.ts`, `useKeyboardLayout`, read again on window focus); without the Keyboard API (Firefox, Safari) the code's label as before. Used for the shortcuts and for the push-to-talk key (Sprache und Audio, Tastenkürzel), which kept its physical code (Raw Input watches the scan code, so it is right in every layout).
- **Consequence (Claude's decision):** a binding keeps the virtual key of the layout active at the capture; after switching the layout the label follows the new layout while the registered key stays the old one. Capture the key again after a layout change.

**Checked (24 September 2026):** root typecheck; web tests with `platform/hotkeys.test.ts` (German layout: Ö -> "Control+`", KeyZ with VK_Y -> "Control+Y", ß -> "Control+[", labels "Strg+Ö", "Y", "ß"). In Electron 44 under a privileged `app://` scheme on the German Windows: `getLayoutMap()` answers `ö`, `y`, `ß` for Semicolon, KeyZ, Minus; Ctrl+Ö arrives with `keyCode` 192, Ctrl+Y with 89. **Not checked:** the real settings tab with a physical key press (SendKeys events carry no `code`); another layout (French, US-International). Needs a new desktop app release (client).

**Control links carry the installation's key (25 September 2026, security review, group D; the user chose this over links for the safe actions only):** any web page can open a `squorli://` link, and a browser can be told to always allow it, so `squorli://control/mic-on` (or `mic-toggle`, `deafen-toggle`, `deafen-off`) from a page could open the microphone. The desktop app now makes a random key once per installation (`controlKey` in `desktop-config.json`, `apps/desktop/src/main/index.ts`) and hands it to the client (`DesktopInfo.hotkeys.controlKey`); the tab's links carry it as `?k=<key>` (`controlLink(action, key)`, `parseControlLink` in `platform/hotkeys.ts`), and `findControl(argv, key)` carries out a link only with the right key. `mic-off` and `deafen-on` (`KEYLESS_CONTROL_ACTIONS`) stay keyless: they only close things. The command line (`--control=`) needs no key, since only a program on this computer can start it. **Consequence:** links for the other four actions set up before this version stop working and must be copied again from the tab (release notes). Checked: tests (`findControl` with and without the key, a wrong and a shortened key; `controlLink`/`parseControlLink`). Not checked: a real Stream Deck, the tab's look.

**Every control link carries the key (5 October 2026, security audit of that day, L-8; the user's decision, which replaces the exception of 25 September 2026):** a web page could open `squorli://control/mic-off` or `deafen-on` without the key, also in a loop that keeps the microphone closed while the user talks (harassment, not a leak: the microphone can only be closed, never opened). A throttle for keyless links was built first and taken out again on the user's word: there are no keyless links any more. `controlLink` in `platform/hotkeys.ts` puts `?k=<key>` on every action (`KEYLESS_CONTROL_ACTIONS` is gone), `findControl` in `controlArgs.ts` carries out a link only with the right key, the command line (`--control=`) still needs none. **Consequence:** links for `mic-off` and `deafen-on` set up before this version stop working and must be copied again from the tab (release notes); the tab's note (`hotkeys.externalKey`) says so for all links now. Checked: tests (`controlLink` with every action, `findControl` with and without the key for the two former exceptions). Needs a new desktop app release (shell and client).
