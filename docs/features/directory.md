- **Account page of the service (`../squorli-directory/apps/directory/web/`):** deliberately without a framework (one script file, tsup), same colors as the client, German texts with umlauts, no browser dialogs. "Konto anlegen" (create account) first registers the handle and then stores the backup; if only the backup fails, the key stays in page memory and the next click repeats only the backup step; afterwards you are directly in the account area. "Anmelden" (sign in; handle + password, code if needed) fetches the seed into page memory only (never localStorage) and signs the account actions with it; "Abmelden" (sign out) nulls it. The chat client links the page in the login ("Noch kein Konto?", "Konto verwalten" with `?handle=`) and in Einstellungen > Konto and signs in with "Mit Konto anmelden": `api.directoryRestore()` fetches and decrypts, `store.loginWithHandle()` replaces the device key (with a confirmation via `askConfirm` if the previous one has a handle) and then logs in normally.
- **Second factor (M6c):** TOTP per RFC 6238 (own implementation `../squorli-directory/apps/directory/src/totp.ts`, no library) or recovery code; the service recognizes the form (6 digits = TOTP). Required, if `totp_enabled`, for `POST /api/backup/fetch`, `PUT /api/backup`, `totp-disable` and `recovery-regenerate`; **never at chat login by key** (the key is the factor). `totp_required` (401) comes only after a correct password or valid signature, so that nobody learns without the password whether an account has an authenticator; public responses (`/api/handles`, `/api/keys`) reveal nothing. Each TOTP step is valid once (`totp_last_step`, otherwise 401 `totp_reused`), window +-1 step; recovery codes are consumed atomically (`used_at`). Only failed attempts count against `BACKUP_RATE_LIMIT` per account (`RateLimiter.blocked()/hit()`), likewise only wrong passwords per IP/handle. The secret is stored AES-256-GCM-encrypted in the DB (`secrets.ts`, key `DIRECTORY_SECRET_KEY`, AAD = account ID); without the key `features.totp=false` and 503 `totp_unavailable`, recovery codes (SHA-256 only) keep working. Setup: `totp-setup` generates the secret (only with a backup, otherwise 409 `no_backup`), it becomes active only with `totp-enable` + code, which at the same time returns the 10 recovery codes (shown once). Signed account actions: `directoryActionMessage(host, action, nonce, code)`, body `SignedActionRequest`/`CodeActionRequest`; the code is part of the message so that it cannot be swapped.

**A refused sign-in listed the server for the account (22 September 2026, user's report):** "ich sehe dort noch die Server auf denen mein 'normaler' Account angemeldet ist in der Serverliste", and on the directory's account page the server showed for an account that was never a member. Cause: `POST /api/auth/verify` looked the key up at the directory (with the server token, which the directory records as a sign-in on this server) before the membership decision, so a sign-in refused for want of an invite put the server on the account's list; the client then showed it in the rail and kept trying to sign in there, refreshing the entry. Fix: the membership is read first and `directory.refresh(user, member)` sends `?member=0` for a non-member (the directory then records nothing and drops an existing entry, its change of the same date in `../squorli-directory/docs/features/servers.md`); a new member gets a second lookup with `member = true` after joining; `GET /api/me` passes the membership too (a kicked user's session). Older directories ignore the parameter. Checked: typecheck, tests, build; the directory's smoke test with its new checks against a directory instance on :3101 (see the directory's `docs/VERIFIED-STATE.md`); not run: a chat server against that directory (the parameter is one string, read in `lookup()`).

**A foreign server's sign-in signs the host actually connected to (25 September 2026, security review, critical):** the multi-server client signed a foreign server's challenge over the domain that server named itself in `/api/health`. A malicious server could name another one (`victim.example`), fetch a challenge there for the user's key, and pass the signature on: a login relay that gave it the user's session on the other server, roles and all, even without a click once its entry was in the user's server list. Now `signDomainOf()` (`apps/web/src/store.ts`) signs `connectedHost(base)` (`apps/web/src/serverHost.ts`: the host of the address the client connects to, with a port other than the default) and refuses the sign-in with a message (`err.foreignDomainMismatch`) when the server's `domain` differs; `connectForeign` goes through it too, and the per-server display name at the directory only for a verified domain. The own server keeps signing the address bar's host. Consequence for operators: a server's `PUBLIC_DOMAIN` must be the address clients reach it at (it always had to be for the own server's web client). Needs a desktop app release. Checked: typecheck, a unit test of `connectedHost`. Not checked: a real relay attempt against two servers.

**The server list needs the user's proof (25 September 2026, security review, group B):** any registered chat server could add itself to any account's server list at the directory by looking the key up with its token, and clients connected to every listed server by themselves (with the sign-in relay closed in group A that exposed the address and invited a sign-in). Now the chat server passes the user's signature of this sign-in on (`nonce`, `sig` on `GET /api/keys/:key`; `checkChallenge` returns the nonce, `DirectoryClient.refresh(user, member, proof)`), and the directory adds a new entry only with it (`chatLoginMessage` in the protocol's `directory.ts`, the same text as `challengeMessage`); an existing entry is refreshed on the token alone. The client connects by itself only to listed servers it has a session or a server account for on this device; the others show in the rail and connect at the first click (`connectAccountServers` in `store.ts`). Consequence: a server that runs an older version adds no new entries to its members' lists until it is updated (existing entries stay). Checked: the directory's smoke test (no entry without the proof, none with another key's proof), a real chat server and directory together: a directory account signing in on the chat server is listed afterwards.

**Security review group D (25 September 2026):** (1) the client's signatures for the directory (register, backup, profile, avatar, settings, link lookup, DM blobs, leave, account status, the WebSocket's auth) were bound to the host the directory reports in `/api/health` or its challenge; now to the host the client connects to (`signingHealth` in `api.ts`, the check in `directoryLink.ts`), and a directory naming another host is refused (`dir.hostMismatch`), like the chat servers since group A. (2) The chat server takes a directory answer only for the key it asked about (`refresh`, `syncOne` in `directory.ts`). (3) A lookup starts a registration at most once a minute after a failure (`ensureToken`): unauthenticated `notify` pushes had each started one. (4) `/api/directory/leave` answered `409 founder` for the owner's key to anyone; now only while the user's request is really pending at the directory, `not_pending` otherwise. Checked: with an unreachable directory, 30 forged notify pushes for a known key started no further registration, and a forged leave push for the founder got `not_pending`. Not checked: a real pending leave of the founder (it still answers `founder`), a directory reporting another host in the running client.
