# Operator limits

Built on 30 September 2026 from `docs/PLAN-limits.md` (written the same day; the plan file is gone, this note replaces it). Generic settings for anybody who runs a Squorli server for other people and wants to bound what it uses. **Every limit is off (unlimited) when its variable is unset**, so nothing changes for an existing installation. The public repository names only these settings; why an operator sets them is their business.

## The settings

| Variable | Meaning | Where it takes effect |
|---|---|---|
| `STORAGE_QUOTA_MB` | the bytes of every file the server keeps for its members: attachments, link preview pictures, report copies, the server accounts' avatars, the server icon | `src/limits.ts` `StorageMeter`; `routes/attachments.ts` (413 `storage_full`, before and after the upload), `routes/settings.ts` (the icon, 413), `auth/local.ts` (the avatar, 413; the picture it replaces gives its bytes back), `previews/service.ts` (a picture that does not fit is left out, the preview keeps its texts), `reports.ts` (copies that do not fit are left out with a warning in the log, the snapshot stays) |
| `VOICE_SEATS_MAX` | how many people may sit in voice channels at the same time, the whole server | `livekit/routes.ts` `POST /api/rtc-token` 409 `voice_seats_full` with `max`; `ws/handler.ts` `voice.join` error `forbidden` with message `voice_seats_full` (the backstop; the client asks for the token first) |
| `MEMBER_MAX` | how many members the server admits | `admit()` in `auth/routes.ts`: 403 `server_full` with `max` for a new member, the first owner excepted; no invite use is burnt by the refusal; a server account that was being registered is removed again (the caller's rule) |
| `DB_POOL_MAX` | the PostgreSQL connection pool (default 10, the fixed value before; 1 to 200) | `db/index.ts` `createDb(url, onNotice, max)`; postgres-js opens lazily up to it and never closes, so it is what one server holds at PostgreSQL for good. 4 is plenty for a small server |
| `LIVEKIT_NODE_IP` | now also read by the app server: the address LiveKit announces for media | `doctor.ts` `mediaHost()`: the setup check probes the TCP media port there; without it at the host of `LIVEKIT_PUBLIC_URL` when that names another machine than `PUBLIC_DOMAIN`, else at `PUBLIC_DOMAIN` |

Also, from the same plan:

- **`GET /api/ready`** (`routes/ready.ts`): 200 `{ ok: true, database: "up", ms }` only while one round trip to the database answers within 3 s, else 503 `{ ok: false, database: "down", error }` with `cache-control: no-store`. What a scheduler or a proxy asks before it routes anything here. `/api/health` keeps answering `ok: true` on a database error on purpose: the login page reads name, icon and version from it and must not vanish with the database.
- **The directory registration tries again by itself** (`directory.ts`): until now `register()` ran once after listen and then only when a lookup needed a token, at most every minute and only every five (`syncAll`). Behind a proxy that routes only to a ready instance the first attempt got `proof_unreachable` (the directory called `/api/health` before the proxy let it through) and the server stayed unregistered until somebody signed in. Now a failure schedules the next attempt: 5 s, 15 s, 30 s, 60 s, 2 min, then every 5 min (`registerRetryDelayMs`); a 429 waits what `Retry-After` says (`retryAfterMs`, at most ten minutes, 60 s without the header); an operator's refusal (`server_blocked`) keeps its hour. A success ends the retries; `close()` at shutdown stops them. The first registration after the start waits a random moment of up to three seconds (`registerStartDelayMs`, in development at once), so many servers starting at once behind one address do not hit the directory's registration limit (10 per minute and IP) together.
- **The server accounts' per-address limits follow `RATE_LIMIT_FACTOR`** (`auth/local.ts`: registrations 20, backup parameters 30, backup fetches 10 per minute at factor 1; 0 = off), as `docs/features/rate-limits.md` promises for every rate limit. The per-account ones (per handle, per user) stay fixed. Found by the smoke test's limits section, whose registrations ran into the fixed 20.

## The installers set a storage quota (4 October 2026, security audit S13)

Without `STORAGE_QUOTA_MB` one member with `ATTACH_FILES` can fill the disk. Since 4 October 2026 a **fresh installation gets `STORAGE_QUOTA_MB` = 80 % of the space free at that moment**: `deploy/install.sh` (`default_quota_mb`, `df -Pk` of the installation folder, set in `write_env` only when the `.env` has no value) and `deploy/windows/install.ps1` (`Get-DefaultQuotaMb`, `DriveInfo` of the data folder's drive, set in `Write-Env` the same way). Both summaries show the value before the confirmation ("Speicher für Dateien"). A value the operator set stays, a value from an earlier run stays, and an **update never adds one**: an installation from before keeps running without a quota until the operator sets `STORAGE_QUOTA_MB` in the `.env` (the website's guides say so). The number is the free space at installation, not a live measure: a disk that fills up for other reasons is not seen by it. Also from S13: **the server icon's bytes decide its type** (`routes/settings.ts` `sniffIconMime`: PNG, JPEG, WebP by the protocol's avatar sniffer, GIF by its header), a file that only claims to be an image is refused with `bad_type`, a declared type that does not match is corrected to what the bytes are, and that is what is stored and served. Checked: `pnpm smoke` (a text declared `image/png` refused, a GIF declared PNG served as `image/gif`), the installers' helpers run by hand on this PC (`default_quota_mb` and `Get-DefaultQuotaMb` give 80 % of the free space, nothing for a path whose drive cannot be asked), `shellcheck` clean but for the known note, the PowerShell parser clean. **Not run** then: a whole installation with either installer after this change (the acceptance test on the CI runner covers `install.ps1`), and that cost a fresh Linux installation on 5 October 2026: `default_quota_mb` asked `df` about the installation folder before `download_files` creates it, `df` failed, and with `pipefail` and the `ERR` trap the installer aborted at the quota question with `x Abgebrochen (line 123): awk ...`. Since then the function walks up to the nearest existing parent and a failing `df` yields no value (`|| true`) instead of an abort; an update of an existing installation never hit this because the folder exists. The fix is in the script on `main`, which every installation downloads, no release needed.

## What the admin area shows

Verwaltung > Server > **Grenzen** (`AdminPanel.tsx` `LimitsSection`, shown when `ServerSettings.limits` is true): storage for files, seats in voice channels, members, each as "used of max" or "used · unbegrenzt", the size per file (`MAX_UPLOAD_MB`), and a refresh button. Read only: the values come from the environment, the hint says so; a value at its limit is drawn in the warning colour. The numbers come from `GET /api/settings/limits` (`routes/limits.ts`, MANAGE_SERVER, protocol `LimitsReport`), fetched only there and never part of the settings every member gets: the storage total walks the data folder. No `PROTOCOL_VERSION` bump: a new route, an optional flag in `ServerSettings`, new error codes; an older client simply does not show the section, an older server does not send the flag.

The client's words for the refusals: `err.serverFull` (sign-in and registration), `voice.joinErr.seatsFull` (`apiErrorText.ts`), `upload.storageFull` and `upload.tooLarge` (`api.uploadAttachment`, until now a refused upload showed the bare request line), `local.storage_full` (the avatar).

## How the storage total is measured

`StorageMeter` (`src/limits.ts`) adds the attachments' bytes as the database records them (`sum(attachments.size)`, the files are not walked for that), the files below `DATA_DIR/previews`, `DATA_DIR/reports` and `DATA_DIR/avatars`, and `DATA_DIR/server-icon`. The total is trusted for 10 s (`STORAGE_CACHE_MS`); every store that wrote or removed something calls `invalidate()`, and one that is about to write asks `room(bytes)`. Without a quota nothing is measured. An upload's size is only known after it was written, so the attachment route refuses before the upload when the quota is already reached and after it when the file would cross it (the file is removed again). Something removed frees its bytes at once for the stores that call `invalidate()` (attachments through `removeAttachmentFiles`, the icon, the avatar) and within 10 s for the rest (the sweeps).
