Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. **Channel permissions (23 September 2026; user's wish: "im squorli-server sollen auch Kanäle und Kategorien Berechtigungen bekommen. Ein Kanal wird bearbeitet indem man einen Rechtsklick darauf macht und aus einem Context-Menü den Punkt 'Kategorie bearbeiten' bzw. 'Kanal bearbeiten' wählt. [...] Man kann wählen ob ein Kanal Privat ist [...]. Man kann Rollen und Benutzer einstellen die den Kanal einsehen bzw. bei Sprachkanälen betreten können. Man kann einstellen, dass ein Sprachkanal sticky ist (wer rein geschoben wird kommt aus eigener Kraft nicht mehr raus). Ein Benutzer mit dem Recht andere Mitglieder zu verschieben kann jemanden auch in einen Kanal verschieben den er normalerweise nicht sehen und oder betreten kann. Es muss sicher gestellt sein, dass Kanäle nur an den Client übertragen werden wenn er sie auch sehen kann (gleiches gilt für Inhalte). Rechte sollen beim Discord import beachtet werden."):** This replaces the decision of 13 September 2026 that permissions apply server-wide only.

The user's decisions, asked one by one:

| Question | Decision |
|---|---|
| Model | Discord-style: any number of overwrites per channel *and* category, for roles and members, every permission three-valued (allow / deny / neutral = inherit) |
| Categories | Live inheritance: a category's entries apply to every channel inside, a channel deviates per entry; a channel moved to another category takes that category's entries at once |
| Transmission | Hard: an invisible channel does not exist for the client (no object, no name, no voice presence, no messages, no events) |
| Moving | Its own right `MOVE_MEMBERS`, split off `MODERATE_VOICE` (migration 0028 gives it to every role that had `MODERATE_VOICE`) |
| Sticky: who | Whoever sits in a sticky channel is held (joined by themselves or moved there); released by a move of somebody with `MOVE_MEMBERS`, or when the channel stops being sticky |
| Sticky: how long | Per channel (`stickyPersist`): whether the hold outlives the member's voice presence (reload, restart) |
| Sticky: hiding | Per channel (`stickyHideVoice`, on by default): while held, the other voice channels leave the member's channel list; text channels always stay so they can ask for help |
| Sticky: exemption | A right the admin gives (`BYPASS_STICKY`, by role or per member, server-wide or per channel), never a personal setting |
| Bypass of private channels | Owners and `ADMINISTRATOR` only; `MANAGE_CHANNELS` alone does not |
| Verwaltung > Kanäle | Stays an overview (create, sort, delete, AFK channel); name, topic, category, bitrate, stereo moved into the dialog, every row has a pencil |
| Extra settings | Read-only/announcement channel, user limit (voice), slowmode (text), notification suggestion, topic in the dialog, per channel: radio, camera/screen, bitrate, stereo |
| Attachments | Closed on 25 September 2026 (user's decision: signed links for 7 days): an attachment's address carries an expiry and a signature (`src/attachmentLinks.ts`), so whoever loses the channel gets no fresh links and keeps an old one for a week at most; a link passed on dies the same way. `apps/server/AGENTS.md`, pitfalls |

**How a permission resolves (`channelPermissions.ts`, the client's `channelPerms.ts` mirrors it):** owner or `ADMINISTRATOR` = everything, whatever the overwrites say. Otherwise the server-wide mask of the roles (`Actor.permissions`) is the base; then the category's entries, then the channel's, each in Discord's order: the default role's deny, its allow, the union of the denies of the member's other roles, the union of their allows, the member's own deny, their allow. Only `CHANNEL_OVERRIDABLE` bits ever change (`VIEW_CHANNELS`, `SEND_MESSAGES`, `ATTACH_FILES`, `MANAGE_MESSAGES`, `MANAGE_CHANNELS`, `CONNECT_VOICE`, `STREAM_VIDEO`, `VIEW_VIDEO`, `CONTROL_RADIO`, `MODERATE_VOICE`, `MOVE_MEMBERS`, `BYPASS_STICKY`); an overwrite naming another bit is refused (400 `not_channel_permission`), so `ADMINISTRATOR`, `MANAGE_SERVER`, `MANAGE_ROLES`, `KICK_MEMBERS`, `BAN_MEMBERS`, `CREATE_INVITES` stay server-wide. With no overwrite rows every resolution is the base, bit for bit what the server did before: existing servers change nothing. `VIEW_CHANNELS` is the per-channel view right (no new bit): the roles' value is what overwrites start from, as Discord does it.

**One mechanism, several switches (Claude's decision, not asked):** "privat", "Nur-Lese-Kanal" have no columns. Each is a shortcut in the dialog for an entry of the default role ("Gast"): `deny VIEW_CHANNELS` resp. `deny SEND_MESSAGES | ATTACH_FILES`. The switch is on when that entry denies the bit. Turning "privat" on also allows the editor themselves to see it (`withEveryoneDeny` with `keepFor`), and the server refuses any list that would take the editor's own view or management away (409 `would_lock_out`). `Channel.private` on the wire is derived per structure load and only draws the lock; the server filters, never the client. It means *set to private here or on the category* (`markedPrivate` in `channelPermissions.ts`), not "the default role happens not to see it": the resolution starts from a default role that may see everything, so only an overwrite can take the sight away. What the status API leaves out and what the AFK guard refuses is the wider `privateChannels` (the default role's real resolution). `allowRadio` and `allowVideo` are columns on purpose: they hold for everybody, administrators included.

**Hard visibility (`visibility.ts`):** one snapshot of roles, memberships, overwrites, channels and holds per structure version (`invalidate()` at the top of `broadcastStructure()`, the one place every change of roles, members, channels, categories and overwrites passes, plus the few seat and hold changes in `voice/sticky.ts`); a member's masks are pure arithmetic over it and cached until the snapshot or their seat changes. `broadcastStructure()` sends the channel and category lists per recipient, filtered, and only when the recipient's visible set changed or the lists were explicitly asked for (`changedSince`: the hub's presence hook broadcasts "members" on every connect, disconnect and AFK change, the full list on each of those would multiply the traffic). `Hub.broadcastToChannel()` carries `message.*`, `typing`, `voice.state`, `radio.meta` (the track title is content) and `radio.playback` to those who may see the channel; `index.ts` installs `visibility.canSee` as the hub's predicate. The welcome's `voice.state`/`radio.meta` run over the visible channels only; `myChannelPermissions` names visible channels and categories only (a mask for a hidden one would give its id away). `GET /api/read-state` counts over the visible channels in both of its queries. `GET /api/status` shows what one role would see (the key is a read key, not a membership) and no member sitting in a channel that role may not see; which role is a server setting, `statusApiRoleId`, null = the default role (`docs/features/status-api.md`). A category is left out when the member may not see the category itself, whatever it holds.

**404, never 403 (standing rule, `apps/server/AGENTS.md`):** a route asked about a channel the member may not see answers `404 unknown_channel`, the same as for an id that does not exist; `channelActor()` in `channelGuard.ts` does that, then the caller checks the specific right with `canIn(ctx.perms, Permission.X)` and answers 403.

**The seat exception:** the channel a member sits in, was just moved to (voice/confine.ts grant), or is held by, is always in their list with `VIEW_CHANNELS | CONNECT_VOICE`, whatever the overwrites say: otherwise a member moved into a channel they may not see could not render it. Voice channels have no messages, so only the name of the room they sit in anyway becomes visible.

**Moving (`POST /api/members/:id/move`):** the mover needs `MOVE_MEMBERS` resolved in the destination (server-wide or by overwrite there, so an overwrite can also take it away), neither `VIEW_CHANNELS` nor `CONNECT_VOICE` there; the moved member's own rights at the destination are not asked (the user's decision). Because the move is advisory (the client joins by itself), the route leaves a one-minute grant (`MoveGrants`) that lets exactly that channel through the token and the join, sends the member their channel list first (the client cannot join an id it does not know), then `voice.moved`. The join marks the seat `placed` (`VoicePresence`): a member a moderator placed is not thrown out by a later permission change. The AFK mover places too (a grant before its `voice.moved`). A user limit does not stop a move. `moderationTarget()` in `routes/members.ts` takes the right as a parameter now: `MOVE_MEMBERS` for the move, `MODERATE_VOICE` for stopping streams and the stream block; both count server-wide or in the channel the target sits in.

**Eviction (`syncVoiceAccessOf`, the renamed `syncStreamGrantsOf`):** whoever loses `VIEW_CHANNELS` or `CONNECT_VOICE` in the channel they sit in (not placed there) gets `voice.moved { channelId: null }` and is removed from the LiveKit room (`removeParticipant`; a token's grants are checked only at the join, without the removal they would keep hearing the channel). Camera and screen grants follow the channel-resolved `STREAM_VIDEO` and the channel's `allowVideo`. Called by the overwrite routes, the role and member routes, `PATCH /api/channels/:id` on a category change or `allowVideo`, the category deletion, and the AFK channel change. The restored presence at the hello (`ws/handler.ts`) checks the rights too and drops from the room whoever lost the channel while away (a placement does not survive a restart; the moderator moves again).

**Sticky (`voice/confine.ts`, `voice/sticky.ts`):** `members.confined_channel_id` = where a member is held; written by `holdOnJoin()` when they take a seat in a sticky channel (unless they resolve `BYPASS_STICKY` there, or are an owner or administrator), cleared by a move, by the channel turning non-sticky (`releaseAll`), by its deletion (FK), by a kick/ban, and, without `stickyPersist`, when their voice presence ends (`releaseOnLeave`). Held: `POST /api/rtc-token` answers `403 { error: "confined", lock }` for every other channel and `voice.join` refuses with `forbidden`; with `stickyHideVoice` the other voice channels leave the member's list, so they answer 404 like any invisible channel. The state carries `myVoiceLock` (`ServerState`, `me`); the client disables the hang-up button (not hidden, with the reason), refuses a switch with a notice, and with `stickyPersist` rejoins the holding channel after a reload with a notice (`App.tsx`). The AFK channel may be neither sticky nor private (409 `afk_channel_sticky` / `afk_channel_private` in both directions), and the AFK mover leaves held members alone. **Honest limit:** a client can always disconnect from LiveKit or close the tab; the server cannot force presence. Sticky means "no other voice channel", not "cannot leave"; with `stickyPersist` a cooperating client returns.

**The other settings:** `userLimit` (voice, best effort: `VoicePresence` is advisory, two simultaneous token requests can both pass; 409 `channel_full`, a seated member and a move excepted), `slowmodeSeconds` (text: 429 `slowmode` with `retryAfter`, exempt with `MANAGE_MESSAGES` in the channel; the composer counts down and takes a 429 as the clock), `defaultNotify` (stored and shipped; the client's own mute wins, `channelPerms.effectiveNotify`), `allowRadio` (409 `radio_disabled`), `allowVideo` (no camera/screen grant in the token, `VoiceStage` hides the buttons). `POST`/`PATCH /api/channels` answer the protocol's `Channel` (the column `default_notification` is `defaultNotify` on the wire).

**Routes:** `GET`/`PUT /api/channels/:id/overwrites` and `/api/categories/:id/overwrites` (`MANAGE_CHANNELS` in that channel/category; the whole list, like `PUT .../roles`). Rules in order: allow and deny never share a bit (400); only `CHANNEL_OVERRIDABLE` (400 `not_channel_permission`); targets must exist (400 `unknown_target`); `canGrant` over the actor's channel-resolved mask, since 6 October 2026 only over the bits an entry changes against its stored row, a dropped entry in every bit it had (403 `cannot_grant`; until then over each whole entry, so a list with one entry holding a right the editor lacked could not be saved at all, see `docs/features/ui-admin.md`); a role only below one's rank (403 `role_above_you`); a deny for a member only when one outranks them (403 `target_above_you`), both since 8 October 2026 only for an entry the list changes or drops, an unchanged one passes through (until then an entry for the editor's own role, as a Discord import leaves it, made the whole list unsaveable, see the entry of that day); never one's own lock-out (409 `would_lock_out`). A kick deletes the member's overwrite rows (the users row stays, no cascade); a deleted role or user takes its rows with it (FKs).

**Protocol:** no `PROTOCOL_VERSION` bump. `structure` keeps its wire shape (whole lists), only the contents differ per recipient; every new field has a default (`Channel.sticky`, `stickyPersist`, `stickyHideVoice`, `userLimit`, `slowmodeSeconds`, `defaultNotify`, `allowRadio`, `allowVideo`, `private`; `ServerState.myChannelPermissions`, `myVoiceLock`, the same two on `me`). `myChannelPermissions` present = the server does channel permissions: the client offers the dialog and the menu entries only then and falls back to `myPermissions` elsewhere (`ServerConnection.channelPermissions()`). New error codes come on REST answers only (`ServerError.code` is a fixed enum older clients would drop).

**Client:** right-click on a channel (any kind now) opens mute (text), "Kanal bearbeiten" and "Kanal löschen" (with `MANAGE_CHANNELS` in the channel); a category's heading is a button inside the `<h3>` (keyboard reachable) whose click or right-click opens "Kategorie bearbeiten", "Kanal erstellen" (text/voice by `askInput`) and "Kategorie löschen"; at narrow widths a channel row gets an `ellipsis-vertical` button (no right-click on a phone). `ChannelDialog.tsx`: categories on the left (Übersicht, Berechtigungen, Sprache / Text + Benachrichtigungen), a save button per tab for the plain fields, the permissions tab writes every switch at once; the answer stands next to the switches in the editor's header: "Speichert …", then a check with "Gespeichert" for 1.5 s (a text that stayed showed nothing on the next save; user's report), "Nicht gespeichert" with the reason below on an error. The overwrite editor: the entries (the default role always first and fixed), `EntityPicker` (a `ContextMenu` with a search field, `pickerEntries.ts` ranks roles before members with the mention list's rule), per permission a `TriState` radio group (x / minus / check; the inherit segment's frame shows what a neutral line resolves to and the hint names the source: the category's entry or the roles), a channel line that deviates from the category has a brand-coloured left edge, "Einfach"/"Erweitert" (simple = three checkboxes, allowed or nothing set; an entry with a deny forces the advanced view), "Rechte der Kategorie übernehmen" empties the channel's list, the effect line "X darf hier: …" (`channelPerms.resolveIn`). Rights one does not hold in the channel are disabled with the reason. Who may watch camera/screen in a voice channel follows the overwrites since 25 September 2026 (the gap until then: `videoAccessOf()` went by the roles' server-wide masks, so a `VIEW_VIDEO` overwrite never reached the senders' per-member list): the server resolves `VIEW_VIDEO` per seated member (`voiceStateEvent`, `visibility.resolvedMask`) and sends it as `VoiceMember.viewVideo`; it sends every occupied channel's `voice.state` again after a change of roles, members or overwrites (`permissionListeners` in `state.ts`); the client's `channelVideoAccess()` restricts to those members (not yet listed = microphone only), my own watching follows `myChannelPermissions` (`mayViewIn`). A server from before (no field) keeps the server-wide rule. Checked: unit tests, a smoke check (deny for a member -> `viewVideo: false` at once, cleared -> true). Not checked: two real clients watching each other's camera across such an overwrite.

**What the lock means (23 September 2026, user's rule: "das Schloss vor dem Kanal soll nur sein wenn der Kanal oder die übergeordnete Kategorie auf privat gestellt sind", "bei Sprachkanälen"):** a voice channel's leading icon is a lock instead of the speaker exactly when the channel or its category is set to private; a sticky channel carries a pin (`pin`) beside the name, not the second lock it used to (`lock-keyhole`, since dropped from the icon subset), because a lock must mean one thing. The derivation was narrowed with it (`markedPrivate`, above): a default role without `VIEW_CHANNELS` server-wide is a role matter and locks no channel any more, and a category deny that the channel allows again is no lock either. Checked: `channelPermissions.test.ts` (six cases), and in headless Chrome against the test server a private channel, a channel in a private category, a sticky one and a plain one side by side (lock, lock, speaker + pin, speaker), with the default role's `VIEW_CHANNELS` taken away and given back in between (no change); screenshot looked at. **Extended on 6 October 2026 (user's wish: "Das Schloss würde dann in der Liste rot bei Räumen anzeigen die der Benutzer (mit seinen Rollen) sehen aber nicht betreten kann"):** a voice channel one sees but may not enter (`CONNECT_VOICE` missing there) shows a red lock in place of the speaker (`.channel-icon.no-entry`), whether private or not; such a row is no longer dimmed, only a sticky hold dims. Text channels keep the plain lock: "betreten" is a voice matter, a text channel one may not write in is read, not entered (Claude's reading, not asked). The channel dialog lists the roles in the hierarchy's order as the Roles tab shows it, the default role last (user's wish of the same day; until then it stood first).

**Reload into a held channel (23 September 2026, user's report: "wenn ich in einem Kanal dauerhaft festgehalten werde bekomme ich beim Neu laden der Seite diese Fehlermeldung: Client initiated disconnect"):** the client's sticky return (`App.tsx`, effect on `myVoiceLock`) runs on every server state change, and at startup those come in a burst (welcome, structure, me, presence). Between the token request and the connection nothing of the first join shows in the voice state yet (`voiceHost` is set only after the join), so the effect started a second `joinVoice()`, whose `client.join()` disconnected the room that was still connecting; LiveKit's `connect()` then failed with "Client initiated disconnect", which the client showed as a connection error with the proxy hint. Fix: `joinVoice()` keeps the join under way in a ref (`joinInFlight`) and a second call for the same host and channel waits for it instead of starting over (every caller, not only the sticky return); the sticky return itself tries a lock once (`stickyTried`, reset when the lock ends or changes) so that a refused or failed attempt does not repeat on the next presence event. Checked: the built client against a test server on :3001 (smoke database, dev LiveKit) in headless Chrome with fake media: a guest (the owner is never held) joins a `stickyPersist` channel, the page reloads: back in the channel with exactly one rtc-token request, no error dialog, only the notice "hält dich weiterhin fest", the other voice channels hidden; the screenshot looked at.

**Join and move refusals as sentences (23 September 2026, user's report: "wenn ich ohne Berechtigung einen Kanal betreten möchte sollte eine sinnvolle Meldung kommen, kein Fehlercode POST /api/rtc-token -> 403 (forbidden)"):** `apps/web/src/apiErrorText.ts` maps the codes of `POST /api/rtc-token` (`forbidden`, `confined`, `channel_full`, `unknown_channel`, 401) and of the move route (`forbidden`, `confined`, `target_above_you`, `not_in_voice`, `not_found`, `channel_full`) to catalog texts (`voice.joinErr.*`, `members.moveErr.*`); an unknown code stays readable behind "Beitritt nicht möglich: …". Used by the join dialog (`reportJoinError`), the sidebar's drag error and the member list's move menu. A voice channel the member may not enter (no `CONNECT_VOICE` there) is dimmed in the sidebar like a locked-out one, with the same sentence as title; the click still asks the server. Checked: a guest with an everyone deny on "enter" clicks the channel in headless Chrome: the dialog reads "Du darfst diesen Kanal nicht betreten. Dafür fehlt dir das Recht „Diesen Kanal betreten“." Unit test `apiErrorText.test.ts`.

**Rank rules over the changed entries only (8 October 2026, user's report: with administration rights short of `ADMINISTRATOR` on a server imported from Discord, every switch on the default role's entry of a channel answered "Diese Rolle steht über deiner."):** the import copies Discord's overwrites, so a channel usually carries an entry for the editor's own top role (there "Le Chef"); `check()` in `routes/overwrites.ts` asked `canTouchRole` for every role entry of the list, that one included, and the member rank for every member deny, and so refused the whole list. Now the rank rules follow the rule `canGrant` got on 6 October 2026: only an entry whose bits differ from its stored row, or one the list drops, is checked; an unchanged entry is nobody's doing. Changing or removing an entry for a role at or above one's rank stays refused (403 `role_above_you`), as does a new or changed deny for a member one does not outrank (403 `target_above_you`). The dialog shows such a role entry locked (`topPositionOf` from `memberRank.ts`; owners never): its switches disabled with the reason as title, a lock in place of the remove button, and the sentence `chan.rankLocked` above the switches, so nobody runs into the server's refusal by accident. Checked: typecheck and unit tests of server and web, the smoke check "an entry for a role at one's own rank stays untouched" (B holds Smoke-Mod: another entry changed 200, the role's bits changed 403, the entry dropped 403). Not checked: the dialog against a real imported server with several entries above the editor.
