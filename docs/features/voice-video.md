## Screen share audio: browser and system matrix (moved from PLAN.md 3.6 on 25 September 2026)

Screen share with audio is part of the product, but the browsers impose limits no code gets around. State of September 2026 from public sources plus what was measured; rows marked **verify** are open. The instrument for them is the test page `/test/screenshare.html` (shipped with the client; in dev http://localhost:5173/test/screenshare.html): per browser and operating system try tab, window and entire screen, then replace the row here with the result and the date. The open rows are listed as open work in `docs/PLAN.md`.

| Environment | Video | Audio | Confidence |
|---|---|---|---|
| Chromium (Chrome, Edge, Brave) – share browser tab | yes | yes, tab audio, all operating systems | confirmed |
| Chromium – entire screen, Windows | yes | yes, system audio after opt-in in the dialog | confirmed |
| Chromium – entire screen, macOS / Linux | yes | unclear, depending on the source now possible | **verify** |
| Chromium – single window | yes | to my knowledge no | **verify** |
| Firefox | yes | no, rated low priority by Mozilla | confirmed |
| Safari | yes | no to my knowledge | **verify** |
| Desktop app, Windows | yes | yes: one window's audio, or the system's audio without the app, through a native helper (WASAPI process loopback, Windows 10 2004+); Chromium's loopback only as the fallback | signal measured in the app (18 September 2026, `docs/features/desktop.md`); a listener's side not yet checked |
| Desktop app, macOS | yes | system audio needs an additional path (ScreenCaptureKit or virtual audio device) | **verify**, considerable effort possible |
| Desktop app, Linux | yes | conceivable via PipeWire/PulseAudio monitor, Wayland complicates video capture | **verify**, can be documented as a limitation |

What follows from it:

1. **Officially supported:** screen share with audio in Chromium browsers and in the desktop app on Windows. Everything else shares video without audio, with a clear notice in the UI (the stage's notice, `apps/web/src/voice/AGENTS.md`), never silently.
2. **The share's audio is a separate audio track,** not mixed into the microphone: listeners control it separately (own volume, own output device) and the presenter does not hear themselves twice. That LiveKit handles several audio tracks per participant cleanly was an assumption of the plan ("to my knowledge yes"); a listener's side is part of the open rows.
3. **macOS system audio in the desktop app** is the most expensive row. If verifying it turns out costly, it becomes a documented limitation instead of blocking a release (open decision in `docs/PLAN.md`).
4. Status of 15 September 2026: the picture of a screen share was tested end to end; the per-browser audio rows were not filled in.

**Joining a second voice channel opens its stage too (24 September 2026, user's report):** "Wenn ich einem Sprachkanal beitrete (auf den Sprachkanal klicke) soll auch immer der Sprachkanal im main Bereich zu sein, das funktioniert im Moment nur beim ersten mal, danach wird bei jedem Kanalwechsel immer auf den obersten Eintrag der Kanalliste gewechselt".
- *Cause:* `VoiceClient.join()` leaves the old room first, and `leave()` set the status to "disconnected" for a moment. The effect on `voice.status` in `App.tsx` took that for an unexpected end of voice: it closed the stage just opened by `joinVoice`, sent `voice.leave` and cleared `voiceHost`, so the main area fell back to the first text channel. A join on another server went through `leaveVoice()` and hit the same effect.
- *Built:* `leave()` reports "connecting" instead of "disconnected" while `switchingRoom`; `joinVoice` no longer calls `leaveVoice()` for a channel on another server, it fetches the token, withdraws the presence at the old server (`voice.leave`) and lets `client.join()` switch the room. A token refused by the new server now leaves the old connection standing.
- *Checked:* root typecheck, tests and build. *NOT checked:* a real channel switch in a browser or the desktop app (same server and across servers).

**The viewer's statistics of a share, and the plan for a share that adapts by itself (22 September 2026, user's report and wish):** a member shares a game with H.265 and the user, watching, sees a lagging picture on every share of that member. Wish: "erstmal eine Möglichkeit einbauen, dass man als Zuschauer Statistiken zu einer Bildschirmübertragung ansehen kann und einen Plan erstellen, wie man die Auflösung automatisch anpassen kann und andere Optimierungen on demand automatisieren kann."
- *Built:* a button (activity icon) in the actions of a received share's tile on the stage and in its pop-out window shows a box in the top left corner (`VideoStatsOverlay.tsx`, `.tile-stats`, takes no clicks so the tile still enlarges; it stays in fullscreen since it lives inside the tile): codec and decoder with hardware/software, picture size, fps decoded and received, bitrate, loss in percent, round trip, jitter buffer, decode time per frame, spread of the frame spacing, freezes with their duration, dropped frames, keyframes, and one diagnosis line. Read every second from the receiver's raw `getStats()` report (`VoiceClient.videoReceiveSample(tileId)`), because LiveKit's `getReceiverStats()` leaves out freezes, the jitter buffer, decode time, the round trip and `powerEfficientDecoder`. `voice/videoStats.ts` (pure, tested): `readInboundVideo` (the inbound-rtp report, its codec, the transport's selected candidate pair or else the nominated succeeded one), `deriveVideoStats` (the interval's rates; counters that went backwards start over), `diagnose`.
- *The diagnosis is my first guess, not measured against real cases:* network for loss of 1 % and more, a jitter buffer of 200 ms and more, or a freeze with retransmits; decoder for over 25 ms per frame or a tenth of the frames dropped; sender for an H.264/H.265 share (moving pictures by the desktop app's choice) arriving under 20 fps while the path is clean; a VP8 share is never blamed on the sender, a still desktop legitimately sends few frames. Network comes before decoder before sender. Only received screen shares get the button (the own share has no inbound side; cameras were not asked for).
- *Plan:* `docs/PLAN-share-adaptation.md` (what adapts today, where a lag can come from, stages: sender-side governor over `setParameters` without a republish, simulcast or quality reports from the viewers, one-click optimisations on demand, an automatic codec switch only if the data asks for it; open decisions for the user). Open decision in `docs/PLAN.md`.
- *Checked:* typecheck, tests (web 338), build; the overlay's look on a static page with the built stylesheet in headless Chrome. *Not checked:* the numbers against a real lagging share (the user is to open the box on the reported share), the pop-out window and fullscreen in a browser, Firefox's report (it lacks some of the fields; those show "?").

**A game's share: smooth motion, and H.265 on the graphics unit (21 September 2026, evening; user's report and wish):** "die Übertragung auf H.264 über den Schnellbutton ist im Moment sehr laggy und hat Artefaktbildung", then: can it be encoded on the GPU to spare resources, and would H.265 be better.
- *Cause, measured* (a test window in the app's Electron 44.4.2 / Chrome 152, RTX 4080, 1080p30 of a moving test picture over a loopback connection; `encoderImplementation` only shows in `getStats` while a `getUserMedia` capture runs): every share was captured with `contentHint: "detail"` and LiveKit's "maintain-resolution". With that hint Chromium runs OpenH264 in its mode for screen content: 13-14 frames per second at 16-17 ms per frame; with "motion" 28-30 at 1.7 ms. The 5 Mbit/s limit did the rest with fast pictures.
- *Which encoders the graphics unit gets* (same test): H.264 baseline, main and high and H.265 go to `MediaFoundationVideoEncodeAccelerator` (NVIDIA MFT, about 3.4 ms per frame); H.264 constrained baseline (all LiveKit negotiates, entry below) is OpenH264; AV1 is libaom in software, also with the feature `MediaFoundationAV1Encoding`; VP8/VP9 are libvpx. So the way to the graphics unit through LiveKit is H.265.
- *Built:* `voice/screenShareOptions.ts` (`screenSharePublish`, pure, tested) makes the publish options and the content hint from the picked codec. VP8 as before (detail, no simulcast, 5 Mbit/s). H.264 and H.265 are the user's choice for moving pictures: hint "motion" (set on the captured track before publishing; the capture still asks for "detail" because the codec is only known after the picker), `degradationPreference: "maintain-framerate"`, limit 8 Mbit/s (H.264) or 6 Mbit/s (H.265), VP8 as LiveKit's backup codec with its default policy: once a viewer cannot decode the codec, the whole share regresses to VP8 (one encoder at a time, the resource-friendly choice; whether it returns to H.265 when that viewer leaves was not checked). **The limits are my choice (not confirmed by the user beyond "about 8 Mbit/s"); the regression policy is my choice too, confirmed by the user on 25 September 2026.**
- *Found on the way:* for a track of the source screen share LiveKit reads the limit from `screenShareEncoding` only; the `videoEncoding` the share passed until now was ignored (the room's `publishDefaults.screenShareEncoding` applied, the same 5 Mbit/s, so nothing was wrong before). The options now carry `screenShareEncoding`; a test pins that.
- *Which codec:* `ScreenCodec` is `"vp8" | "h264" | "h265"`. `movingCodec(h265)` (`screenPick.ts`): H.265 where `VoiceClient.supportsH265()` says yes (LiveKit's `supportsH265()`: the sender's capabilities; Chromium ships no software H.265 encoder, so the codec is on offer only with one in the graphics unit), else H.264. "Quick Share" and the dialog's preselection for a game's window use it; the dialog's second radio button is "H.265" or "H.264" by computer, each with its hint (H.265: encoded by this computer's graphics unit, less bandwidth, falls back to VP8 for everyone when a viewer cannot play it). The dock's tooltip no longer names a codec. The shell is unchanged (`codec` stays in the client).
- *Seeing it (user's question the same evening):* the debug view's rows for sent video name the codec really sent and its encoder, read from the raw reports of every sender of the track, the backup codec's included (LiveKit's `getSenderStats()` knows neither); a share that fell back shows the idle H.265 row next to the VP8 one. Typecheck, tests and build ran; the rows were not looked at in the running app.
- *Checked:* typecheck, tests, build. A harness with the real `livekit-client` and the real `screenSharePublish` in Electron against the dev LiveKit (`livekit-server:latest`): H.265 is negotiated, sent by the NVIDIA HEVC encoder at 1080p30 and 6 Mbit/s (`qualityLimitationReason: none`), hint "motion" and "maintain-framerate" in the sender's parameters, a second participant decodes it in hardware; a third one started with `--disable-gpu` (no H.265 among its codecs, as in Firefox) gets VP8, the H.265 sender goes inactive and the first viewer moves to VP8 too. H.264: OpenH264 at 30 frames per second, where the (noise-like, worst case) test picture is scaled down to stay within 8 Mbit/s, as "maintain-framerate" asks. *Not checked:* a real game in the running app, the dialog's new text on screen, a real Firefox or Safari viewer, AMD and Intel graphics units (which generations encode H.265 is from the vendors' lists, not measured: NVIDIA from GTX 900, AMD from RX 400, Intel from the 6th Core generation), a packaged app.

- **Measured, and it limits what H.264 is good for:** LiveKit's client prefers H.264's constrained baseline profile (`profile-level-id=42e01f`) for compatibility and the LiveKit server (1.13 dev container) negotiates nothing else, also when baseline, main or high are offered first. **No channel could be joined from the iPhone's home screen app (19 September 2026, user's report):** "wenn ich die app über iPhone Safari auf den Homebildschirm lege (als PWA), kann ich keinem Kanal beitreten", error "Mikrofon: The request is not allowed by the user agent or the platform in the current context", and "ich wurde nie nach einer Mikrofonfreigabe gefragt".
- *Cause (from WebKit's rule and the missing prompt, not reproduced on a device):* WebKit shows the microphone prompt only while the tap counts; `join()` asked after the token and the LiveKit connection. Safari had the site's permission stored and needed no prompt, the home screen app has its own, empty storage and has to ask.
- *Fix:* `VoiceClient.prepareMic()` asks inside the tap (`App.joinVoice()`, before the first `await`, not for the AFK channel); `join()` takes that capture over or releases it; a failed token or connection releases it. Consequence (decided by Claude): on every browser the permission prompt now comes with the click and no longer after a successful connection, so a connection error can cost a prompt.
- *Checked:* typecheck, tests, build. The real `VoiceClient` against the dev LiveKit in headless Chrome with a counted `getUserMedia`: prepared and joined 1.5 s later = one request, the capture is published and live, ended after leaving; prepared and released = track ended; prepared for stereo and joined in mono = released, the join opens its own, no error.
- *Second report the same day, after the fix:* "neue Fehlermeldung: The request is not allowed by the user agent or the platform in current context, possibly because the user denied permissions", now without the "Mikrofon:" prefix: the mobile join sheet showed the bare error and the dock the explained one, so it is the same refusal, read in another place. Whether the home screen app ran the new client (iOS keeps a web app's old page in memory) and whether a prompt appeared is not known. Done: the microphone request is now the very first thing in the tap, before the audio context and the silent sound; a refusal is explained from the browser's permission state (`voice/micPermission.ts`: "denied" = stored refusal with the way to the iPhone's setting, "prompt" = refused without asking, otherwise the system keeps it back), so the next report names the case; the sheet shows that text. Checked in headless Chrome without the fake permission UI: state "denied", the sheet's text is the explained one. The cause on the iPhone is still open.
- *Third report the same day:* the permission prompt now appears in the home screen app and the others are heard, but "ich sehe beim iPhone Mikrofon jetzt gar keinen Pegel mehr". Cause as read from the code (not reproduced): iOS puts the AudioContext into the state "interrupted" when its prompt shows and the capture starts, and the client resumed only "suspended" (pipeline, `prepareAudio()`, the gesture fallback, the cues), so the microphone ran through a standing context. In Safari with a stored permission no prompt appeared, which is why it had worked there. Fixed with `contextNeedsResume()` (`gate.ts`) in all those places plus a resume from the context's `onstatechange` while a microphone runs. If the level stays at 0: the debug view's "Audio" line names the context's state, and "Eingang" says whether the capture itself delivers anything (a capture muted by iOS would be the next suspect).
- *Fourth and fifth report the same day, stereo channel:* "ein Benutzer sagt, wenn ich mit meinem iPhone im Kanal (Stereo Kanal) bin, hört er mich nur auf einem Ohr" and "außerdem hören sich die Benutzer doppelt, wenn ich mein iPhone mit Lautsprecher verwende". One cause: a stereo channel captures two raw channels without echo cancellation. Fixed twice. (1) Phones and tablets never capture raw stereo (`VoiceClient.capturesStereo()`): they get the browser's echo cancellation, noise suppression and gain control in every channel, the channel's Opus settings stay; decided by Claude, not confirmed by the user (a phone has one microphone next to its loudspeaker, raw stereo gains nothing there). Side effect: the quiet raw level on the iPhone in stereo channels is gone as well, because the system's gain control works again. (2) For computers, where an audio interface with the microphone on input 1 gives the same one-ear effect: `voice/oneSided.ts` finds a stereo capture with the signal on one channel only and `micPipeline.ts` puts that channel on both sides, and takes it back when the second channel comes alive. Checked in headless Chrome with the real `MicPipeline` and a synthetic two-channel capture: tone left only = output left only at first, on both sides at equal level after half a second (verdict "left"), tone on both = verdict "stereo" again. The echo on the iPhone in a MONO channel was not reported and not checked.
- *NOT checked:* the iPhone itself, in Safari or from the home screen. The client has no web app manifest and no Apple home screen tags; iOS runs it as a web app anyway, with storage of its own (another identity than in Safari unless signed in through the directory account).

**Camera picked in the dialog was ignored; phones and tablets recognised (19 September 2026, user's report and wish):** "auf meinem iPhone erreiche ich den Pegel nie, generell sollten wir mobilgeräte besser erkennen und dann auch die dazugehörigen Einstellungen anpassen (Video, Audio). Generell gibt es einen Bug bei der Kamera Auswahl. Wenn ich eine Standardkamera ausgewählt habe wird immer diese genommen, auch wenn ich in dem Dialog eine andere Kamera wähle."
- *Camera bug, cause:* a camera switched off is a muted track that stays published, and LiveKit's `setCameraEnabled(true, options)` (livekit-client 2.22.3, read in its source: `if (track) await track.unmute()`) then ignores the options and reopens the track with the constraints it was created with. So the first camera of a connection stuck until the user left the channel; the preselected "Standardkamera" is simply the one that gets opened first. A changed send resolution while the camera ran was ignored the same way.
- *Camera bug, fix:* `voice/cameraSwitch.ts` decides from what the published track was opened with: same camera and resolution = unmute as before (same publication, so the receivers' "camera off" choice stays); another one while off = unpublish and open fresh (one camera open, which matters on Firefox; the receivers see a new feed, a camera they had turned off shows again); another one while running = `restartTrack()` on the same publication.
- *Mobile devices:* `platform/mobile.ts` tells a phone or tablet by the device (not by the narrow layout), `Platform.mobile` / `PlatformMedia.mobile`. Audio: the boost gets the limits x40 and speech from a raw level of 0.0006 there (a computer: x12 and 0.003). The assumed cause of the iPhone report: iOS delivers its voice-processed capture so low that speech stayed under the 0.003 the automatic takes for the quietest speech, so it never started, and x12 would not have reached the threshold of 0.04 anyway. The hand slider goes to 4000 % there. Video: 360p as the send resolution, applied once per device also to stored settings (`withDeviceDefaults`, `VoiceSettings.mobileDefaults`; the settings say so, and 720p chosen afterwards stays); the own rear camera is not mirrored in the picker's preview, the stage and pop-outs; no screen share button where the browser has no `getDisplayMedia`. Debug view: the raw level in front of the boost ("Eingang").
- *Decisions made by Claude, not confirmed by the user:* the phone limits (x40, 0.0006) and 360p as the phone's default; the voice activation threshold and push-to-talk are unchanged on phones (a phone has no key for it, but an iPad with a keyboard does).
- *Checked:* typecheck, web tests 259 (`cameraSwitch.test.ts` 5, `mobile.test.ts` 5, 3 new in `micBoost.test.ts`, 1 each in `settings.test.ts` and `videoDisplay.test.ts`), build. The real `VoiceClient` against the dev LiveKit in headless Chrome with two fake cameras (`--use-fake-device-for-media-stream=device-count=2`, own room, token minted in the script): on with A, off, on with B opens B on a new publication (the bug), off and on with B keeps the publication, 360p while running gives a 360 px track on the same publication, A while running switches the device on the same publication, no error.
- *NOT checked:* anything on a real iPhone or Android phone. Whether the boost now reaches the threshold there is open; if not, the debug view's "Eingang" while speaking is the number needed (below 0.0006 the automatic still does not start, and then the capture itself is the problem, not the limits). Firefox with the republish path (its late camera release is covered by `retryCameraBusy` as before, but was not run).

**Watching video is each user's choice; hide participants without video (19 September 2026, user's requirement):** "wenn ein Desktop Share gestartet ist sollen nicht automatisch alle Clients ihn anzeigen, man soll ihn für sich aktivieren können. genauso soll man auch das Ansehen des Streams für sich ausschalten können. man soll generell die Möglichkeit haben Videoübertragungen einzeln für sich abschalten zu können, Webcam soll aber automatisch aktiviert werden. Einstellungen > Sprechen: "Leises Mikrofon automatisch anheben" (default on) or a slider 100-600 %, the gain applied right now is shown there and in the debug view ("Pegel / Tor · x..."). Per device and NOT in the directory account (decision by Claude, confirmed by the user on 25 September 2026: how quiet a microphone is belongs to the computer, like the device selection). Stereo channels stay unboosted.

**Cause found: stereo channel (18 September 2026, user's answer: "Pegelanzeige ist niedrig und Schwellwert muss nach ganz links gedreht werden. Die anderen hören sie auch sehr leise. **Screen audio on its own device pulled every voice along (26 September 2026, user's report: "Ich habe jeweils unterschiedliche Ausgabegeräte für Voice, Radio und Screen-Share eingestellt. Wenn ich einem Radio zuhöre funktioniert auch alles wunderbar. Wenn ich aber einen Screen-Share angucke wird meine gesamte Voice Ausgabe auf die Ausgabe des Screenshares umgestellt statt nur den Screen-Share auf einem anderen Gerät auszugeben."; their guess was LiveKit migrating every connection):**
- *Cause:* not LiveKit (livekit-client 2.22.3 sets the sink per element, and `applyScreenSink()` only touched the share's track) but Chromium: `media_stream_renderer_factory.cc` gives every remote WebRTC stream of a frame the same `WebRtcAudioRenderer` ("using existing WebRtcAudioRenderer for remote stream"), each element only a `SharedAudioRenderer` proxy, and `WebRtcAudioRenderer::SwitchOutputDevice` replaces that renderer's single `sink_`. So `setSinkId` on ANY element playing a remote track re-routes all of them, the last call wins: the join put the voice device on every element, then the share's `setSinkId(screen device)` ran last. The radio is a plain HTTP stream with a renderer of its own, which is why it kept working; the desktop app is the same Chromium. Firefox/Safari have no `setSinkId` at all. Discussed publicly: https://groups.google.com/g/discuss-webrtc/c/lMH3hS5wY_8. This also explains the "voices get quieter" report of 24 September 2026 above: the voices had moved to the speakers.
- *Fix:* `applyShareAudio()` in `voiceClient.ts` (rule in `apps/web/src/voice/AGENTS.md`): with a separate device the share's audio runs through its own `AudioContext` (`screenCtx`, `setSinkId` = the device; source -> gain -> destination, the gain carries the volume, deafen and "not listening"), and LiveKit's element keeps playing at volume 0 so Chromium keeps feeding the track into Web Audio; no `setSinkId` on a remote track any more. The context is made when a device is chosen and resumed with every gesture like the shared one; while it is suspended, or when the browser refused the device (`screenSink.error`), the share plays through its element on the voice device and moves over once the context runs. The share's volume lives in `shareVolumes` (memory), `getVideoAudioVolume` reads it (a fresh share starts at 100 %, not at whatever the element had). `join()` now takes the screen device BEFORE the voice device (it was set after the first routing). The debug view's "Bildschirm-Ton Ausgabe" names the path ("eigener Audiokontext" / "über das Element").
- *Checked:* root typecheck; web tests 436 (`videoAudio.test.ts`, 7 new: the route through a fake context with the voices' sink untouched and no `setSinkId` on any track, the gain following deafen, listening and the slider, the element path without a device and where a context cannot choose one, the switch between the paths keeping the volume, a suspended context, a refused device, leave dropping the routes); headless Chrome (two peer connections in one page, an oscillator at 440 Hz, `webaudio-flow.html` in the scratchpad driven over the DevTools protocol): the remote track's RMS in a second AudioContext was 0.71 with the element at volume 0, 0.71 muted, 0.00 with the gain at 0, and 0.71 with the element paused or playing, so Chromium delivers the frame to Web Audio regardless of the element and volume 0 is more than enough; `pnpm build`. Not checked: two real output devices (headless Chrome has none). That is the user's test: voices in the headset, the share on the speakers, the debug view saying "eigener Audiokontext" and "1 Spur(en)".
