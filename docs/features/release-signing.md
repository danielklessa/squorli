# Feature notes: signed releases (the image signed with cosign, the Windows package's checksum file signed with the release key)

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. Standing rules live in the `AGENTS.md` of the area (`deploy/AGENTS.md` "Signed releases", `deploy/windows/AGENTS.md`). Whoever changes the feature adds or updates its entry here in the same step. The desktop app's code signing is a feature of its own (`docs/features/desktop.md` "Code signing").

Code: `.github/workflows/server-release.yml` (job `sign`: the environment `signing`, the checksum file's signature, `cosign sign` of the tag's image), `.github/workflows/ci.yml` (job `image`: GitHub's build provenance attestation), `deploy/install.sh` (`COSIGN_IMAGE`, `SIGNER_IDENTITY`, `SIGNER_ISSUER`, `signed_ref`, `verify_image`; the check in `start_stack` and in the helper's `update`), `deploy/windows/squorli-server-releases.pub` (the release key's public half), `deploy/windows/verify-signature.mjs` (the check of an Ed25519 signature with Node's own modules), `deploy/windows/squorli.ps1` (`Test-Signature`, the check in `Invoke-UpdateSteps`), `deploy/windows/build-package.ps1` (both files into the package), `deploy/windows/test/acceptance.ps1` (the checks of a wrong and a right signature). For operators: README ("Signed releases"), the website's installation guide (both languages), `.env.example` (`APP_IMAGE`, `IMAGE_VERIFY`).

## Built (4 October 2026, security audit S9, measure 3.2)

**Why.** Installations took whatever lay under the image tag or in the GitHub release: `squorli update` on Linux pulled the tag and started it, on Windows it checked a SHA-256 file that lay next to the package, which proves a complete download and nothing about who built it. Whoever took over the GitHub account, a token of the CI or the rights at GHCR could hand every installation with automatic updates a manipulated version within hours (audit S9). The base images had been pinned by digest on 3 October 2026 (Renovate keeps them current); the signatures are the rest of the measure.

**What exists.**

- **The image of a release is signed with cosign, keyless.** The job `sign` of `server-release.yml` runs in the GitHub environment `signing` (the owner approves every run, as for the desktop app's code signing), waits for the image `ci.yml` built for the tag, signs it by digest (`cosign sign --yes <image>@<digest>`; the signature goes to GHCR next to the image, the certificate and the entry in the transparency log to Sigstore's public services) and verifies at once what every installation verifies: the certificate's identity is this repository's `server-release.yml` at a tag `v<version>` (`SIGNER_IDENTITY` in `install.sh`, a regular expression), issued through GitHub's OIDC (`SIGNER_ISSUER`). The images of the default branch (`latest`, `main`, `sha-*`) are not signed: they are the development's, and an attacker with the CI's token must not be able to get a signature for one of them. `stable` is a copy of the release's manifest with the same digest (`stable-image.yml`), so the signature holds for it too.
- **The installer and the helper check it before anything of the new image runs.** `verify_image` (one function in `install.sh`, copied into the helper with `declare -f` together with the three constants) takes the pulled image's digest from `docker image inspect` and runs cosign in its own container, pinned by digest (`COSIGN_IMAGE`, cosign 3.1.3; Renovate keeps the digest current through a regex manager in `squorli-renovate`). `start_stack` of the installer checks after the pull and before the first `up`; the helper's `update` checks a new server image right after the pull and before `by_hand` asks the image's node for its version (that was the first code of the new image to run). A failed check ends the run with the last lines of cosign's answer; what ran keeps running (the container holds the old image). The images of PostgreSQL, LiveKit and Caddy are their makers' and are pinned by digest in `compose.yml`, so they are not checked here. `IMAGE_VERIFY=off` in `.env` skips the check with a line that says so (an installation without a way to the Sigstore services); a development image (`latest`, a branch, a commit, a local build) is skipped with a line that names it.
- **`stable` is the default** of the installer, `.env.example`, `portainer.yml`, the README and the website (it was `latest`, undecided in `docs/PLAN.md` since 28 September 2026): the default is signed, and a new installation takes the newest published version instead of the development's state. `squorli autoupdate on` still offers the change to `stable` for installations on `latest`.
- **The Windows package's checksum file is signed with the release key.** An Ed25519 key, generated by the operator with openssl; the private half lives only in the secret `SERVER_SIGNING_KEY` of the environment `signing`, the public half ships in the package as `squorli-server-releases.pub` and in the repository. The job `sign` signs `squorli-server-<version>-windows-x64.zip.sha256` with `openssl pkeyutl -sign -rawin` into `.sha256.sig` (64 bytes), verifies the signature against the public key of the repository (a key that is not the package's would lock every installation out) and attaches zip, `.sha256` and `.sha256.sig` to the draft. `squorli update` fetches the three files and checks the signature first (`Test-Signature`: the installed `node.exe` runs the installed `verify-signature.mjs` with the installed public key, never the new package's files), then the hash; a package from an address must carry the signature (a download that fails ends the run), a local file given with `-Package` may come without one, which is said as a warning (the operator chose that file). The first installation trusts the downloaded package (the key is inside it); every update from then on is checked. A key change needs one release signed by the old key that carries the new public key.
- **Every action pinned by commit (5 October 2026, security audit M-4).** All workflows name their actions as `owner/repo@<full commit sha> # v4.4.0` instead of a moving tag: a tag moved upstream (or a compromised one) cannot run other code in CI, least of all in the jobs of the environment `signing` that hold the release key and the Certum credentials. The version behind the comment is what Renovate (in GitLab, `squorli/renovate`) reads and raises together with the commit (`pinDigests` for the manager `github-actions`). A new action goes in the same way: `git ls-remote --tags https://github.com/<owner>/<repo>.git` names the commit of a tag (`^{}` lines are the peeled ones). `cargo install ssign` in `desktop-release.yml` runs with `--locked`.
- **Build provenance.** The job `image` of `ci.yml` attests every image it pushes (`actions/attest-build-provenance`, pushed next to the image too): which workflow built this digest from which commit. It is not what installations check (an attacker with the CI's token gets one for free); it is for a person: `gh attestation verify oci://ghcr.io/danielklessa/squorli-server:v<version> --owner danielklessa`. Buildx' own provenance stays off (`provenance: false`): it would turn the image into an index around manifest and attestation, and `stable-image.yml` and the installations count on one manifest with one digest.

**Decisions (Claude, confirmed by the user on 4 October 2026):** keyless cosign bound to `server-release.yml` at tags, not a key in the secrets (nothing to steal, and the signer is readable in the certificate) and not the images of the default branch; the owner's approval through the environment `signing` as the step that turns a tag into a release (an attacker who pushes a tag gets a draft and an unsigned image, nothing an installation takes); cosign in a container pinned by digest instead of a binary on the host (Docker is there anyway, and the digest is kept current by Renovate); `stable` as the default everywhere; `IMAGE_VERIFY=off` as the only way around the check, in `.env` rather than a flag (so a run of the job behaves like the person); Ed25519 with openssl for the checksum file instead of cosign's blob format or minisign (cosign 3 writes a bundle format that only cosign reads, minisign would be one more program; the check needs nothing but the package's node.exe, and openssl is on every runner), the public key in the package (trust on first use, said in the guide); the provenance attestation without approval in `ci.yml` (it describes the build, it is no statement by the owner); Portainer and the hosting cluster pull without a check (noted in the audit as open).

**Rollout.** The operator generates the key pair (`openssl genpkey -algorithm ed25519 -out squorli-server-releases.key`, `openssl pkey -in squorli-server-releases.key -pubout -out squorli-server-releases.pub`), keeps the private key with the other signing material outside the repositories, puts its PEM text into the secret `SERVER_SIGNING_KEY` of the environment `signing` and replaces `deploy/windows/squorli-server-releases.pub` with the public key **before the first release with this change** (the key in the repository at the time of building was a stand-in made during development; the job `sign` fails when secret and file do not match). The first release with this change is the first signed one; its notes say so. Linux installations made before get the check when the installer runs again ("Update", which rewrites the helper); until then their `squorli update` pulls as before. Windows installations get the files with the first update to a version with this change and check from the next update on. The website's guide goes live with the release.

**Checked (4 October 2026):** `bash -n` and `shellcheck` of `install.sh` (the one known note); the helper's part (`declare -f` output) parses; `signed_ref` and `verify_image` driven from a test shell: 12 checks (the switch off, a development image, an image without a digest, a real keyless-signed image with another identity refused, the same image with its signer's identity accepted end to end through the pinned cosign container, German and English lines). `verify-signature.mjs`: a right signature, a tampered one, a key of another type, a short and a missing signature file, no arguments. The four PowerShell scripts parse; `Test-Signature` out of the real `squorli.ps1` (dot-sourced against a scratch installation with a copied node.exe): right, tampered, short, missing key, German text. The two workflows parse as YAML; `docker buildx imagetools inspect --format '{{.Manifest.Digest}}'` gives the digest the job waits for (the published `v0.10.1` is one manifest). Renovate's configuration loads with the new manager. **Checked with the release 0.10.2 (4 October 2026, evening):** the CI of `main` green including the acceptance test with its four new checks and the attestation step; the tag's `server-release.yml` ran through after the owner's approval (the checksum file signed and verified, cosign 3.1.3 installed, the image signed and verified, the three files attached) at the third try: the action `sigstore/cosign-installer` had to be v4 by its full version `v4.1.2` (v3 cannot install cosign 3, there is no tag `v4`; the tag was moved twice). From a developer machine the pinned cosign container verified `ghcr.io/danielklessa/squorli-server:v0.10.2` with the identity every installation checks (digest `sha256:592021ee…`, exit 0): the positive path of `verify_image` against the real release. **Not checked:** a real update of a Linux installation against a signed release, a real `squorli update` on Windows against a release with a `.sha256.sig`.

**Pitfalls:** `cosign verify` prints its JSON to stdout and the checks to stderr: `verify_image` keeps stderr only (`2>&1 >/dev/null`). A `workflow_dispatch` of `server-release.yml` must run from the tag ("Use workflow from"), or the certificate names the branch and the job's own verify step refuses it. `Get-File` dies on a failed download, so for a package from an address the `.sha256.sig` is required without a check of its own. The acceptance test replaces the installed public key with its own for one update and relies on the update putting the package's key back (`Copy-Programs` copies every file of the package's root).
