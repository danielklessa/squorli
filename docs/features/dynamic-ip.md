## Built (3 October 2026)

**The user's wish.** A customer's server on Windows behind a Nginx Proxy Manager failed every media connection ("Getrennt (UNKNOWN_REASON). Die Medienverbindung (ICE) kam nicht zustande"): a home connection (a FRITZ!Box, Telekom IPv6 addresses, a Hyper-V adapter), where LiveKit's own detection of the public address (STUN, then a check that the address reaches itself) silently fell back to a local address. With `LIVEKIT_NODE_IP` set by hand it worked, but "eine feste IP zu bekommen ist allerdings keine annehmbare Lösung". The user asked for a job of the installation that checks the address regularly, if need be through a Squorli address, and reconfigures and restarts LiveKit when it changed, and added: "oder über den router abrufen, dann bleibt die last auf die Homepage geringer".

**Why a job, not a smarter detection.** LiveKit reads `node_ip` (or asks STUN) once at its start. A home connection changes its address at every forced reconnection, so even a detection that worked would announce a stale address afterwards. Something on the host has to notice the change and restart LiveKit; the app server cannot (it has no rights over services or containers, and it must keep running).

1. **`squorli nodeip check`** finds the public IPv4 address and applies it. The order of the sources: **the router by UPnP** (`GetExternalIPAddress` of its `WANIPConnection` or `WANPPPConnection` service; Windows sends a multicast search (SSDP) and then tries the description addresses common routers use (AVM 49000, miniupnpd 5000, 1900, 49152, 49153, 8000) at the default gateway, Linux only the latter and `upnpc -s` when it is installed), then **an address on the web** that answers with the caller's address: `LIVEKIT_NODE_IP_URL` when set, else `<DIRECTORY_URL>/api/ip`, then `https://directory.squorli.com/api/ip`; asked over IPv4 on purpose (`curl -4`; Windows uses its own `curl.exe` for that, `Invoke-WebRequest` cannot be told). An address that is no public IPv4 (private, loopback, link-local, 100.64/10, multicast) does not count: a router that names one is reported (DS-Lite or CGNAT, or a second router in front) and the web decides. When the address differs from `LIVEKIT_NODE_IP` it is written into `.env` (Windows also into `config\livekit.yaml`, which LiveKit reads at its start) and LiveKit is restarted: Linux recreates the `livekit` container alone (`up -d --no-build livekit`; the app server keeps running), Windows restarts the service with the services that need it (`SquorliServer` depends on `SquorliLiveKit`, so Windows stops them along, `Stop-Services`/`Start-Services` of the command). LiveKit that is not running only gets the value. Exit code 1 when no source answered; the old value stays.
2. **`squorli nodeip on [minutes]`** (1 to 60, default 5) sets `LIVEKIT_DYNAMIC_IP=true` and registers the job: Linux a systemd timer `squorli-nodeip.timer` (`OnBootSec=1min`, `OnUnitActiveSec=<n>min`) or `/etc/cron.d/squorli-nodeip`, Windows the task `SquorliNodeIp` of SYSTEM with a repetition of n minutes. The job runs `squorli nodeip check --auto` (Windows `-Auto`): no word on the screen, one line in `nodeip.log` (Linux `<dir>/nodeip.log`, Windows `logs\nodeip.log`; cut to 2000 lines above 1 MB) for every change or failure, and the time, address and source of every run in `nodeip.last`. **`off`** removes the job and empties `LIVEKIT_DYNAMIC_IP`; the last address stays. Without a word: the state (the announced address, the job, the last check, the last changes).
3. **The installers ask.** The question "Öffentliche IP für Sprache und Video" became a choice: (1) LiveKit detects it itself (a server with a public address of its own, the default), (2) it changes (a home connection behind a router): a job checks it every 5 minutes, (3) a fixed address. The default follows the installation (`LIVEKIT_DYNAMIC_IP=true` → 2, a value in `LIVEKIT_NODE_IP` → 3). With (2) the Linux installer runs `nodeip check` before the containers start (so LiveKit announces the right address from its first start on) and `nodeip on 5` after the check; the Windows setup runs the command's `nodeip check` and `nodeip on 5` after the services are up (through `squorli.ps1` as a child process: the two scripts share the name `$S` and cannot be dot-sourced into each other). Another answer removes an existing job. An update keeps what is there. `install.ps1 -NodeIp dynamic` is the unattended form. `uninstall.ps1` removes the task.
4. **The setup check** (`docs/features/doctor.md`): with `LIVEKIT_DYNAMIC_IP` the app server's `mediaHost()` ignores the `LIVEKIT_NODE_IP` it started with (the job changes `.env` without restarting the app server, so the value in the process may be stale) and probes `PUBLIC_DOMAIN`, whose DNS record follows the address (dynamic DNS). Without the flag nothing changes.
5. **The directory's `GET /api/ip`** answers with the caller's address as plain text (`req.ip`, which honours `TRUSTED_PROXIES`; `Cache-Control: no-store`). It exists for this job only and is the fallback behind the router; nothing else uses it.

### Decisions of the user (3 October 2026)

- A job of the installation that checks regularly, determines the address through a Squorli address if need be, and reconfigures and restarts LiveKit when needed ("ich denke wir sollten direkt eine Lösung bauen").
- The router first, so the Squorli address carries less load.

### Decisions made by Claude, confirmed by the user on 3 October 2026

- The Squorli address is the directory's `/api/ip` (directory.squorli.com), not the website: the website is static. A server with its own directory asks that one first; `LIVEKIT_NODE_IP_URL` names any other service that answers with the caller's address.
- The default interval of 5 minutes, 1 to 60 allowed; the Linux timer counts from the last run (`OnUnitActiveSec`), cron takes `*/n`.
- Only changes and failures go into the log (a line every 5 minutes would drown the changes); `nodeip.last` holds the last run.
- `LIVEKIT_DYNAMIC_IP` is a flag next to `LIVEKIT_NODE_IP`, which keeps holding the address LiveKit uses (Compose and the Windows template read it as before); so an installation from before this change needs nothing.
- `LIVEKIT_ROUTER_IP` names the router when the default route is not it (a VPN on the host); the tests use it to point at a fake router on 127.0.0.1.
- IPv4 only: the media ports are forwarded for IPv4, and LiveKit's `node_ip` takes one address.
- A router that answers with a private address is reported but not used, and the web decides; a double NAT then gets an address that does not reach the host, which the browser's media check shows.
- The Windows command restarts the app server along with LiveKit because the service depends on it (an explicit `<depend>`); removing the dependency was left alone: it would reach existing installations only when their services are registered anew, and the command would have to handle both anyway. A `Stop-Services`/`Start-Services` pair handles both.
- Portainer stacks get a note only: nothing of the installer runs there.

### Checked

- `shellcheck` clean for `install.sh` and for the generated helper (the one note of the kind SC2015 in `summary` was there before).
- The helper's `nodeip` end to end in a `python:3.12-slim` container (bash, curl, iproute2; a stub `docker` that logs its arguments and reports a running `livekit` through a marker file; a fake router on 127.0.0.1:49000 that answers `igddesc.xml` and the SOAP call, a fake directory on 127.0.0.1:8081; `LIVEKIT_ROUTER_IP=127.0.0.1`): the router wins and is written, the file's rights stay, no `up` while LiveKit is not running; unchanged; a new address with LiveKit running recreates `livekit` only; a private router address falls through to the web with the note; router down → web; nothing answers → exit 1 and the old value; `--auto` logs the change and nothing else; `on 7` writes the cron file (no systemd there) and `LIVEKIT_DYNAMIC_IP=true`, `on 61` refused, `on 60` once an hour, `off` removes it and empties the flag, the state and `help`.
- `squorli.ps1` in Windows PowerShell 5.1 against the same fakes, in the test frame without administrator rights (`Test-Admin`, `Get-ServiceInfo`, `Stop-Services`, `Start-Services`, `$NodeIpTaskName` and `Get-AutoPrincipal` replaced; one child process per command): the same cases as on Linux, `config\livekit.yaml`'s `node_ip` line rewritten, the task every 7 minutes with `nodeip check -Auto -DataDir`, `LIVEKIT_DYNAMIC_IP=true` replaces the commented line, the state, `off`. The four scripts parse. `Get-RouterIp` against the developer's real network found no router by UPnP (14 s) and `Get-WebIp` an address.
- Server: typecheck, `doctor.test.ts` (12 with the two new cases of `mediaHost`); directory: typecheck.

### Not checked

- A real FRITZ!Box or another router by UPnP (SSDP and the AVM address), a real forced reconnection, `squorli nodeip` on the customer's Windows machine, the scheduled task as SYSTEM (the acceptance test `Test-NodeIp` covers the task and a check on the runner), the systemd timer on a real host, the installers' new question end to end.
- The directory's `/api/ip` on production: it is in the directory's working tree and not deployed; until then the web fallback answers nothing and the router must answer.
