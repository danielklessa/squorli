# Feature notes: A signed-in server that does not answer

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked.

Code: `apps/web/src/serverRetry.ts` (pure, tested: `sessionRejected(err)`, `retryDelayFor(attempt)`), `ServerConnection.resume()` / `retryLater()` / `retryNow()` / `cancelRetry()` / `retrySettled()` and `ServerConnState.waiting` in `serverConnection.ts`, `connectForeign()` / `markUnreachable()` / `retryServer()` in `store.ts`, `ServerOffline.tsx` (the notice of the own server), the gate in `App.tsx`, the notice in `ServerStatus` (App.tsx) for a foreign server, `rememberHomeName()` in `branding.ts`; texts `offline.*` and `status.offline`.

**The notice instead of the login (26 September 2026; user's wish: "wenn ein Server offline ist auf dem ich angemeldet bin sollte in der App kein Anmelde-Screen erscheinen sondern ein Hinweis, dass der Server grade nicht erreichbar ist").** Until then `resume()` dropped the stored session token on *any* failure of `GET /api/me`, a stopped server or a broken network included, and the client fell through to the login screen; the user then had to sign in again although the session was still good.

What was built:

- **Only a refusal drops the session.** `sessionRejected(err)` is true for an `ApiError` with a 4xx status except 408, 425 and 429 (the server's own word: signed out elsewhere, expired, account gone); a network error (`TypeError`), a proxy's 502/503, a 5xx or a rate limit keeps the token and the session.
- **The own server (the browser client, `homeHost`):** while the stored session is being tried, `ServerConnState.waiting` is `"checking"`; when the server did not answer, `"unreachable"`. As long as `waiting` is set and no `server` state has arrived, `App.tsx` shows `ServerOffline` (the start card with the server's name, "ist gerade nicht erreichbar", the note that Squorli keeps trying, "Erneut versuchen" and "Abmelden") instead of the login. `waiting` stays `"checking"` from a successful `/api/me` until the WebSocket welcome, so the login never flashes by in between; the welcome, a refusal, `clearSession()` and a member who must register first clear it.
- **Retries by the connection itself:** `retryLater(step)` runs the step again after 15 s, then 30 s for the 2nd to 5th try, then a minute each (`retryDelayFor`; the user's cadence of 26 September 2026, until then 2/4/8/15 s), at once when the device comes back online (`online` event), when the tab is shown again (`visibilitychange`) or when the user presses "Erneut versuchen" (`retryNow()`); `close()` and `retrySettled()` drop it, an answer from the server starts the cadence over. The same timer serves both the own server (`resume()` again) and a foreign server (`connectForeign()` again).
- **Foreign servers (the desktop app's rail, the multi-server client):** `connectForeign()` treats a server this device has been on (a stored session or a server account) as known: it says "checking" while `/api/health` is read, and when the server does not answer, `markUnreachable(conn, again)` sets `waiting: "unreachable"` and schedules the retry; `ServerStatus` then shows "{name} antwortet gerade nicht. Squorli versucht es weiter …" (`status.offline`) in place of the technical CORS message. A server the user is only about to join (`addServer` with an unknown address) still waits for a click, as before. "Erneut versuchen" (`retryServer`) cancels the scheduled try first, so two never run at once.
- **The server's name while it is down:** `/api/health` does not answer either, so `App.tsx` remembers the home server's name in `localStorage` (`chat.homeName.v1`, `rememberHomeName()`) whenever it knows it, and `ServerOffline` shows that name, else the address.
- **"Abmelden" on the notice** is the ordinary `store.logout()`: the session is dropped locally (the server-side sign-out is best effort and fails while it is down) and the login follows, for whoever wants another account on a server that stays down.

**The desktop app's rail server that does not answer (26 September 2026, later that day; the user reported the app "einfach blank" with the selected server down while the directory ran and the rail should have let them add or pick another server).** The blank could not be reproduced: in the client without a home server (`VITE_HOMELESS=1` against a fake directory that names one server the account has been on) the rail with "+" and "Entdecken" and `ServerStatus` were on screen in every state. What the reproduction did show and what was changed:

- **A server that accepts the connection and never answers** (a machine that is off behind a router, a firewall that drops packets) let `/api/health` hang for as long as the browser's own limit, minutes: the main area showed only "Verbinde mit <host> …" (before this feature only the host name and the join hint) for all that time. `ServerApi.request` now takes `timeoutMs` (`AbortSignal.timeout`): `/api/health` gives up after 10 s (`HEALTH_TIMEOUT_MS`), `/api/me` after 15 s (`ME_TIMEOUT_MS`); the `TimeoutError` is no `ApiError`, so the session is kept and the retries begin.
- **A retry keeps the "unreachable" notice on screen** (`connectForeign` and `resume()` switch to "checking" only from a state that is not "unreachable"), because an attempt against a silent server takes the whole time limit and a status flipping between "Verbinde …" and "antwortet nicht" every few seconds says nothing.
- **`ServerStatus` shows no join view for a known server that does not answer:** the invite field and the account forms (which said "Dieser Server arbeitet ohne Verzeichnis", because health had not answered) are left out while `waiting` is "unreachable"; the row with "Erneut versuchen", "Im Browser öffnen" and "Schließen" stands instead. The name comes from the directory's list when health did not answer.

**The view the user asked for (26 September 2026, third step; user's wish: "eine Ansicht laden in der ich meine Serverliste noch sehe … Wenn ich auf einen klicke der grade nicht erreichbar ist, soll eine Meldung im rechten Bereich horizontal und vertikal zentriert stehen … Einen Button um es nochmal zu versuchen, darüber ein Countdown wann der Client es von alleine nochmal versucht. Darunter können andere Server die grade erreichbar sind (bis zu 5) angezeigt werden. Ein Server der nicht erreichbar ist wird links in der Serverliste markiert"):**

- `ServerUnreachable.tsx` replaces the status page for a rail server with `waiting: "unreachable"`: the notice centred both ways in the main area (`.server-unreachable`), the countdown "Nächster automatischer Versuch in n s" (`RetryCountdown.tsx`, from `ServerConnState.retryAt`, which `retryLater()` sets and `cancelRetry()` clears; while the try runs it says "Wird gerade versucht …"), "Erneut versuchen" (`store.retryServer`), and below it "Gerade erreichbar:" with up to five other servers that have a live connection (`reachableServers()` in `otherServers.ts`, by name, pure and tested), each a button that switches to it like a click in the rail.
- The rail marks such a server: `RailState.unreachable`, the entry dimmed with a red "!" at the bottom right (`.rail-off`), the tooltip "Gerade nicht erreichbar". The rail itself never goes away, so any other server, "+" and "Entdecken" stay a click away.
- The own server's notice (`ServerOffline`, browser client) shows the same countdown above its buttons.
- The sidebar's placeholder header names the server from the directory's list when its health did not answer.

Checked (the third step): web tests 426 (`otherServers.test.ts`); the client without a home server in headless Chrome with two rail servers, one down: the notice with the countdown ("in 3 s", "in 1 s") and "Zweiter Server" under "Gerade erreichbar:", one dimmed rail entry with the "!" mark, the button switched to the second server's chat, a click on the marked rail entry brought the notice back, the down server started and the client came up; the screenshot looked as asked. Not checked: the real Electron shell with this view, the English texts on screen.

**Servers on the account's list without a session on this device, and the members' column (26 September 2026, fourth step; the user saw the old status page with "nicht erreichbar oder erlaubt keinen Zugriff aus anderen Clients", the invite field and the server account form for a server of their directory list, and asked for the members' area to go away or the main area to take it, "ähnlich wie bei Freunden"):**

- `Store.isMine(host)` is now the one rule for "one of the user's servers": a stored session or a server account here, added by address, or on the account's list at the directory without a pending deletion. `connectForeign` and `addServer` use it; such a server that does not answer gets the notice with retries, a first contact still waits for a click.
- A listed server this device has no session on is probed at start (`probeServer`: `/api/health` only, never a sign-in without a click, the security review of 25 September 2026), so the rail marks it right away when it does not answer, the probe repeats by itself; once it answers, the join view waits for the click as before. A click on the marked entry shows the notice; "Erneut versuchen" there is the click that signs in when the server is back.
- While no server state is on screen (`view` null: connecting, unreachable, join view), the app's grid drops the members' column (`.app.no-members`, like `.app.home`) and the main area takes its place.

Checked (the fourth step): web tests 426; the client without a home server in headless Chrome with three listed servers, two down, one of them without a session on the device: both marked in the rail after the start, the notice for the one without a session (no invite field, no account form), `no-members` set on the notice and gone in the chat; the screenshot showed the main area reaching the right edge. Not checked: the real directory's list, the Electron shell.

**Fifth step (26 September 2026; user: "die Meldung das die Verbindung versucht wird bitte auch zentrieren, den Erneut-versuchen-Button nachdem ein neuer Versuch gestartet wurde für 5 Sekunden deaktivieren, das Angebot 'Gerade erreichbar' mit Server-Icon links vom vertikal zentrierten Namen"):** `ServerStatus` hands every first contact (`waiting: "checking"`, and any `busy` state without the claim form) to `ServerUnreachable` too, which then shows only "Verbinde mit {name} …" centred the same way. "Erneut versuchen" rests for 5 s after every try that starts (`RETRY_LOCK_MS`, `retryLocked()` in `otherServers.ts`, tested): a click, or the countdown reaching its end (`retryAt` turning null, watched in the component). Each reachable server is a row (`.other-server`): the icon from the directory (`RailServer.iconUrl`, handed in through `reachableServers(…, iconOf)`) or the initials in a round mark, left of the name, both centred on the row; the list is a column of at most five. Checked: web tests 427; headless Chrome: a silent server showed the centred "Verbinde mit Testserver …", at 14 s the button was locked while the automatic try ran and free again at 19 s; against a stopped server the button was locked right after a click and free 5.5 s later; the row showed the initials "ZS" left of "Zweiter Server"; the screenshot looked as asked.

**Sixth step (26 September 2026; user: "beim ersten Mal nach 15 Sekunden, beim 2.-5. Mal nach 30 Sekunden und danach jeweils nach einer Minute. Der Button soll frühestens nach 5 Sekunden, aber immer erst wenn der bisherige Versuch durch ist, freigegeben werden"):** `retryDelayFor(attempt)` in `serverRetry.ts` (tested) replaces the doubling cadence: 15 s before the first try, 30 s before the 2nd to 5th, a minute before every later one; `ServerConnection` counts the failed tries (`retryCount`, reset when the server answers). `retryLocked(startedAt, now, tryRunning)` keeps "Erneut versuchen" locked while the try runs (`retryAt` null and no answer yet) and for 5 s at least. Checked: web tests 427; headless Chrome against a silent server: countdown "in 12 s" at 14 s, the try running from 25.5 s with the button locked at 27 s and still at 31.5 s (5 s over, the health request's 10 s limit not yet), free at 37 s with "in 29 s"; against a stopped server the button locked right after a click and free 5.5 s later, the countdown then "in 30 s"; the stopped server started and the client came up 19 s later.

**Seventh step (26 September 2026; user: "Nach 10 Versuchen insgesamt schalte die Automatik so lange aus, bis der Benutzer manuell erneut versucht hat, dann starte 5 mal alle 60 Sekunden einen neuen Versuch", confirmed as "insgesamt 10 Versuche: 1x 15 s, 4x 30 s, 5x 60 s"):** the plan of automatic tries is a small state machine in `serverRetry.ts` (`RetryPlan`, `freshPlan()` = ten tries in the cadence, `planAfterUser()` = five tries a minute apart, `nextTry(plan)` = the delay before the next try or null when the plan is used up; tested). `ServerConnection.retryLater()` keeps the step but schedules nothing once the plan is used up and sets `ServerConnState.retryPaused`; `retryNow()` (the timer, `online`, a visible tab) does nothing while paused; `retryByUser()` (the own server's notice) and `noteUserRetry()` (the store's `retryServer` for a rail server) switch to the five-a-minute plan and run the try. Both notices then show "Die automatischen Versuche sind aufgebraucht. Mit „Erneut versuchen“ geht es weiter." (`status.autoStopped`) in place of the countdown, the button free (the 5 s lock of the last try still applies). An answer from the server starts the ten over. Checked: web tests 429; headless Chrome against a stopped server for 9.5 minutes: eleven health requests in all (the first plus ten tries) in the cadence 15, 30, 30, 30, 30, 60, 60, 60, 60, 60 s, the notice paused at 436 s with the text and, once the 5 s lock was over, a free button; the press ran a try at once and the countdown said 59 s; 67 s later the first of the five minute-apart tries had run and the countdown said 53 s again. Not checked: the pause after those five (only in the unit test), the own server's notice on screen.

The installed desktop app 0.7.0 has none of this; it needs the next app release. The user's blank window turned out to be `pnpm dev:desktop` without `pnpm dev` (the web client's Vite dev server was not running, so the shell loaded nothing): see `docs/features/desktop.md`, 26 September 2026.

Not changed: a connection lost *while* the client is open still shows the client with "verbinde neu …" (WebSocket reconnect, `reconnecting`), as before; a server that refuses the session (close 4011/4012, 401) still leads to the login with its note.

Claude's decisions, confirmed by the user on 3 October 2026: that 404 counts as a refusal (an older server without `/api/me` would loop forever otherwise), that the notice offers "Abmelden" at all, and that a foreign server the device has never been on gets no retries.
