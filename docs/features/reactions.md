**Reactions and reaction roles (6 October 2026; user's wish: "wir brauchen eine Möglichkeit auf Nachrichten zu reagieren und damit auch Benutzergruppen zu geben. Viele Server möchten gerne ein Regelwerk voranstellen welches akzeptiert werden muss um eine Mitgliedsrolle zu bekommen. Ich hätte gerne die Möglichkeit generell zu reagieren und auch die Möglichkeit bei bestimmten Reaktionen auf einen Text eine Rolle zuzuteilen."):** this overturns the M2 decision of 13 September 2026 (Claude's, "no reactions"); threads stay out.

The user's decisions, asked one by one:

| Question | Decision |
|---|---|
| Who may react | A new right `ADD_REACTIONS` ("Reagieren"), channel-overridable, given by migration 0042 to every role with `SEND_MESSAGES` ("Mitglied" yes, "Gast" no; fresh servers' "Mitglied" through `DEFAULT_MEMBER_PERMISSIONS`). Exception: an emoji configured as a reaction role on a message may be added by anybody who sees the channel (that is how a guest accepts the rules). Removing one's own reaction never needs a right. |
| Removing the reaction on a reaction-role message | Per rule a switch "Rolle wieder entziehen, wenn die Reaktion entfernt wird" (`removeOnUnreact`), default off: accepting the rules keeps the role; interest roles ("Minecraft") switch it on. |
| Where to configure | On the message (the shield in a message's toolbar, only with `MANAGE_ROLES` against a server that does reactions) **and** an overview Verwaltung > Reaktionsrollen. The configured emoji show at once as chips with count 0, so everybody sees what to click. |
| Scope | Channel messages **and** direct messages (an encrypted instruction through the directory, below). |

**How it works (channels):** a reaction is a row `(message, user, emoji_key)`; the chips of a message come with every `Message` (`reactions`, always present on this server, `[]` without any) and change through the event `message.reactions` (the whole list, never a delta). `PUT /api/messages/:id/reactions { emoji }` adds, `POST .../reactions/remove` takes the own one away (always allowed), `GET .../reactions/users?emoji=` says who (oldest first, 50 at a time); the rules are `GET`/`PUT /api/messages/:id/reaction-roles` and `DELETE /api/reaction-roles/:id`, the overview `GET /api/reaction-roles` (the channels the actor sees). Every route is about one message and goes by the member's permissions in its channel (`channelGuard.ts`): an invisible channel, like a missing message, is a 404. Emoji travel in the body or the query string, never in the path (a percent-encoded family is longer than Fastify's default parameter length). A rule fires on the same path `PUT /api/members/:id/roles` takes (the row, `syncVoiceAccessOf`, `broadcastStructure(["members"])`, so the member gets their new channel list at once) and without an actor check: the rule was authorized when it was saved (`canTouchRole`, `canGrant`, never the default role, as assigning a role checks). A deleted role, message or channel takes its rules along (cascade); deleting a role broadcasts the affected messages' chips so the count-0 chip leaves live. **A message with rules takes only the configured emoji (the user's decision of 6 October 2026, after trying it: "wenn eine Nachricht Rollen-Reaktionen hat soll man nicht mit anderen Emojis reagieren können, gibt es schon andere werden sie entfernt"):** any other emoji answers 409 `reaction_roles_only` whatever the right, the picker button is not offered on such a message, the reactions it carried before go when the first rule is made, and the reactions of an emoji whose rule went go too while other rules remain (`pruneForeignReactions`, also after a role's deletion); deleting the last rule frees the message and keeps that emoji's reactions.

**Decisions of mine inside the wish (6 October 2026; the user confirmed them all the same day: "deine Entscheidungen sind OK"):**
- **Unicode emoji only**, exactly one per reaction, by the rule the text uses to find emoji (`EMOJI_SOURCE`, moved from `emoji/convert.ts` into the protocol so the server, the text and the direct messages agree on what one emoji is). A bare character of text presentation ("❤" without U+FE0F, some keyboards send it so) gets the selector in `ReactionEmoji`. There are no custom emoji in Squorli.
- **Identity without the selector:** "❤" and "❤️" are one chip (`emoji_key` = NFC without U+FE0F), skin tones and ZWJ sequences stay distinct, as on Discord. The chip shows the form the first sender typed.
- **At most 20 distinct emoji per message**, configured ones included (`REACTIONS_PER_MESSAGE_MAX`; 409 `too_many_reactions`): a rule can never push a message past the cap.
- **Order of the chips:** the configured emoji first in the order their rules were made (they say "click here" and must not jump), then the others in the order of their first reaction.
- **`me` is nobody's business:** a broadcast is one JSON for everybody and carries no viewer's flag; the client sets its own flag from `by`/`emoji`/`added` when the event is about its own doing and keeps it otherwise (`reactionState.ts`); the REST answer and the history carry the real flag. A rule's `PUT` broadcasts with `added: false`, so nobody's flag changes while the chip appears.
- **No moderation-log entry** for a role given or taken by a reaction: it is the member's own action, not a moderator's (and `ModLogAction` is a closed list older clients parse strictly).
- **No new rate limit:** every call is a write under the session's rule (180 a minute, `docs/features/rate-limits.md`).
- **No `PROTOCOL_VERSION` bump:** `Message.reactions` and `ServerState.reactions` are optional (the flag: the client offers the picker button, the shield and the admin tab only against a server that sends it), the event is one a client from before drops without harm, nothing new goes from the client over the socket.
- **The overview has no "jump to the message"** (the client cannot scroll to a message by id); it shows channel, the message's first words, its author and when the rule was made.
- **A guest who presses a chip they may not add** sees the sentence inline, nothing goes to the server; the "+" button shows only with the right.

**Direct messages:** a reaction is an encrypted instruction like the removal of a preview (`DmControl` of kind `reaction`: the message's id, the emoji, `on`), an ordinary `dm.send` the directory stores and relays without reading it; the conversation shows it as nothing, counts nothing unread and plays no sound (the `dm.message` handler treats every instruction so). What a message's chips are follows from folding the loaded thread (`dmReactions.ts`): the newest word per sender, message and emoji counts, only the two members of the pair count, either side may react to either side's messages. Who reacted comes from the fold (the two names), no request. **Accepted limits (Claude's, inside the user's decision for direct messages; confirmed with the decisions above):** (1) an app from before this release shows a reaction as an empty message with an unread mark and the cue (as it does for `preview.remove`; reactions are more frequent, so the server image and the desktop app are released together); (2) a reaction received while offline counts as one unread in the welcome's conversation list until the conversation is opened (the directory cannot tell an instruction from a message); (3) reactions cost directory capacity like messages (`DM_RATE_LIMIT` 60 a minute per account, history pages of 50, 180 days retention); (4) deleting a message leaves its reaction rows, invisible. The directory's code is unchanged; only the protocol copy (`primitives.ts`, `dm.ts`, `dm.test.ts`) moved.

**Client:** the chips sit under the message (`Reactions.tsx`): mine in the selection colour with the brand's edge, a configured emoji nobody used yet dimmed with no number, a click toggles the own reaction; hovering a chip (400 ms), holding it on a phone (500 ms) or focusing it shows who reacted and, for a reaction role, which role it gives. The toolbar of a message has a `smile-plus` button (with the right) that opens the one `EmojiPicker` of the composer, anchored at the button, and a `shield-plus` button (MANAGE_ROLES) that opens the rules dialog: the rules of that message as rows (emoji, role from the roles one may give, the switch, delete; a change of role or switch writes at once), a row to add one with the picker, and the hint that the configured emoji needs no right. Verwaltung > Reaktionsrollen lists every rule by channel with delete. The direct messages have the same chips and the same picker button; no roles there.
