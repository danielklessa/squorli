# Feature notes: Link previews

Part of the project description (entry point: root `AGENTS.md`, section 0). Dated entries: what was built, the user's wishes and decisions, consequences, and what was and was not checked. Whoever changes the feature adds or updates its entry here in the same step.

Code: the lookup itself is the package `packages/link-preview/` (address rules, guarded GET `safeGet`, page head parser, oEmbed, `lookUpPage` / `lookUpYoutubeVideo`; its own `AGENTS.md`; a byte-identical copy lives in the directory repo); protocol `packages/protocol/src/links.ts` (`previewLinks`, `readBareUrl`, `MAX_PREVIEW_LINKS`), `scan.ts` (the code-aware scanner shared with `mentions.ts`), `index.ts` (`LinkPreview`, `Message.previews`, `RemovePreviewRequest`); server `apps/server/src/previews/service.ts` (`LinkPreviews`), `routes/previews.ts` (the pictures), `routes/messages.ts` (scheduling, the remove route), `messages.previews` (migration 0024), `LINK_PREVIEWS`; client `apps/web/src/LinkPreviews.tsx`, `youtube.ts` (`youtubeChatPlayerSrc`), styles `.preview-*`; desktop `apps/desktop/src/main/playerAudio.ts` + `playerAudioScript.ts` (`playerKindOf`).

**Link previews and YouTube videos in the chat (21 September 2026).** The user's wishes: links in the chat get a preview; whoever sent the link can remove the preview on their message, by an x shown at the top right next to the preview, only to the author; YouTube links become an embed of the video so that it can be watched right in the chat; the video embed is removable by the author with an x as well; the video embeds use the same audio output as screen share audio.

- **The server makes the preview, readers never contact the linked host.** This keeps the standing decision of `docs/features/markdown-input.md` (a remote image would show every reader's address to a foreign host): title, description and site name are fetched once by the chat server, the picture is copied to `DATA_DIR/previews/<sha256 of the bytes, 32 hex>.<png|jpg|webp|gif>` and served from `GET /api/previews/:file` (no token, like attachments: an `<img>` cannot send one; `nosniff`, a closed CSP, immutable). The type is read from the bytes; no SVG. Pictures are stored as they come (no image library on the server), at most 2 MB; the client gives every picture its box before it loads, so an arriving preview never moves the chat.
- **Sending never waits.** `POST`/`PATCH` of a message answer and broadcast at once (`previews: []`), then `LinkPreviews.schedule` looks the links up in the background and the message goes out once more as `message.update` (its `editedAt` unchanged). One thing at a time per message (a queue per message id), and the write only happens while the text is still the one that was read, so an edit during a lookup wins.
- **Which links:** `previewLinks` follows the Markdown parser (the parser takes `readBareUrl` from the protocol package now, so both read an address the same way): bare http(s) addresses and the targets of `[text](address)`, outside code and not behind a backslash, each address once, at most 3 per message. **`<https://...>` is a link without a preview** (the convention people know from Discord): the author's way to say "no preview" while writing. The web test `linkPreviews.test.ts` compares the scanner with the parser, like the mention scanner.
- **No protocol bump:** `Message.previews` is optional; older clients drop the unknown field, and a server with `LINK_PREVIEWS=false` (or an older one) does not send it. The remove route is REST, and only a message that has previews offers it.
- **Fetching an address a member wrote is the danger** (the server could be made to ask itself or its private network). `safeGet` (`packages/link-preview/src/fetch.ts`) follows the radio's rules, and the address rules the radio used (`isInternalAddress`, `checkHost`, `publicLookup`) moved into the same package, so there is one implementation: http(s) only, no credentials in the address, every host and every redirect target (at most 5, followed by hand) must resolve to public addresses only, and the connection itself may only reach a public address; one deadline of 6 s; 512 KB of HTML (cut there, and reading stops at `</head>`), 2 MB for a picture (larger = none), counted after decompression; only `text/html`, XHTML and the four raster types are read at all. Limits: 4 lookups at a time for the server, 12 new links per member and minute (beyond that: no preview, nothing else), results cached for an hour (also "nothing found"), the same address looked up once at a time. The fetcher says who it is (`SquorliBot/1.0; +https://squorli.com`); sites that answer bots with a consent wall or 403 give no preview.
- **What a page says is text from a stranger:** parsed without a library from the head only (Open Graph, Twitter card, `description`, `<title>`), entities decoded, control and bidi characters removed, one line, cut to the protocol's lengths; shown as React text, never as HTML. A page without a title has no preview. A link straight to a picture shows the picture.
- **YouTube:** recognised by the protocol's `youtubeVideoOf` (also `youtu.be`, shorts, `?t=`). Title from YouTube's oEmbed address (`radio/youtube.ts`), picture from `i.ytimg.com`, both fixed addresses; a video that is private, gone or may not be embedded gets no preview and stays a link. **The player is loaded only when the reader presses play** (decision made while building, from the same privacy rule: until then the card is a picture from our server and nothing went to Google); then `youtube-nocookie.com/embed/<id>` with sound and YouTube's own controls, not steered from outside. In the desktop app the existing `Referer` fix for that host applies.
- **Removing:** `POST /api/messages/:id/previews/remove` `{ url }`, **author only** (not even an owner: a moderator deletes the message), 404 `unknown_preview` otherwise. The entry stays in `messages.previews` with `removed: true` and is never sent, so editing the message does not bring it back; a link that leaves the text takes its entry along. The x sits to the right of each preview, one per preview, also next to a video.
- **Audio of a playing video:** a page cannot route a foreign frame's sound, so in a browser it plays on the system's default device (the settings hint says so). The desktop app routes it: chat players carry the fragment `#squorli-chat` (`CHAT_PLAYER_MARK`, never sent to YouTube), the shell's `playerKindOf` tells them from the radio's players, and the new bridge member `setChatPlayerOutput` gets the label of `screenOutputDeviceId ?? outputDeviceId` (App.tsx, `tellPlayerOutput`). An app from before it has no such member and keeps putting every player on the radio's device. **Needs a new desktop app release.**
- **Housekeeping:** pictures no message names any more are swept every 6 hours (files younger than an hour stay: their message may not be written yet). `LINK_PREVIEWS=false` registers neither lookups nor the picture route. `LINK_PREVIEW_TEST_ORIGIN` exists for the smoke test only (one origin exempt from the public-address rule); never set it on a real server.
- **Direct messages (added the same day, the user: "die preview muss auch in direktnachrichten funktionieren"):** they are end-to-end encrypted through the directory and no chat server takes part, so **the sender's client makes the preview and sends it inside the encrypted message; whoever reads it contacts nobody** (`dmPreviews.ts` `buildDmPreviews`, before `sealDm`; at most 8 s, then the message goes without). The user's decisions, asked one by one: (1) who looks the link up: **the desktop app itself** (bridge `lookUpLink`, `apps/desktop/src/main/linkLookup.ts`, the same package and rules; no server learns the link), **a browser through the directory** (`POST /api/link-lookup`, signed; the directory then learns "this account has this link looked up", nothing else, and keeps nothing); (2) **the x removes the preview for both sides** by an encrypted instruction (`DmControl` `preview.remove`; `visibleDms` applies it only when it comes from the author of the message it names, shows it as nothing, and the store neither counts it as unread nor plays a sound; an app from before it shows an empty message, accepted by the user); (3) the picture: the user first chose a larger message limit, then asked whether the directory could be a proxy for the picture; built: **the directory stores the picture but cannot read it**. The client draws it small (at most 640 x 480, WebP or JPEG, `dmPreviewImage.ts`), encrypts it with a fresh key (`sealDmBlob`), uploads the ciphertext (`POST /api/dm-blobs`) and puts blob id, key and IV into the message; the reader fetches and decrypts it (`useDmBlobUrl`, object URL). Messages stay small, `DM_MAX_CIPHERTEXT_CHARS` is unchanged; a message that would still be too long goes without previews. Needs `features.dmPreviews` at the directory for the picture and for senders in a browser; against an older directory the app still sends previews, without pictures. The directory's side: `../squorli-directory/docs/features/dm-previews.md`. **The app's own lookup needs the new desktop app release too.**

Checked (the counts after the direct messages were added): `pnpm typecheck` (five packages), `pnpm test` (link-preview 8 = the parser's tests, moved with it; protocol 74 with `links.test.ts` 6 and 2 new in `dm.test.ts`; server 62; web 314 with `linkPreviews.test.ts` 3 and `dmPreviews.test.ts` 5; desktop 51 with 2 new), `pnpm build`, `docker build --target app`, migration 0024 via `pnpm db:generate`. `pnpm smoke` against :3001 (`chat_smoke`, `LINK_PREVIEW_TEST_ORIGIN=http://127.0.0.1:3198`, the script plays the website): 133 green, 12 new: the field, message first and preview as an update, decoded head fields, one preview per address, the picture byte for byte from this server with its headers, the history, only stored names served, remove (403 for another member even as owner, 404 for another address, the author for everybody), an edit looks up the new link and leaves the removed one away, no preview for angle brackets, code, a text file and a redirect to another local port (that port was never asked), YouTube with title, start and a local picture, removing the video. Without the variable the block is 1 check (122). The fetcher against real sites (GitHub, heise, Wikipedia, tagesschau, Steam, squorli.com, a direct picture; gzip/brotli, umlauts, relative picture addresses; `192.168.1.1` and `localhost` refused without a request). Headless Chrome with the built client against :3001: cards, pictures only from this server, **no request to any other host before play**, after play only `www.youtube-nocookie.com` and the video running, the x removes the video's preview, another member's message has no x, 1400 px and 420 px. The unpackaged desktop app with a harness page: the chat player's `<video>` on the chosen device ("Lautsprecher (2- RODECaster Duo Chat)"), the radio-style player on the default device, shell log `player audio (chat) ... moved=1`. Direct messages: the directory's smoke test 181 green (11 new, its notes), the chat smoke test again after the move into the package (133); **the real client in two headless browsers** (two fresh accounts, friends, chat server :3001 + directory :3101): a message with a page link and a YouTube link took under a second to send, both sides talked to the chat server and the directory only (the sender: two lookups, two blob uploads), the pictures arrived as decrypted object URLs (640 x 320 and 480 x 360), the x was there for the sender only, removing one preview worked on both sides with no new message and no unread mark, and held after the reader's reload; **the unpackaged desktop app**: `lookUpLink` found GitHub and the YouTube video with their pictures as `Uint8Array` and refused `192.168.1.1`, `localhost` and a `file:` address. **Not checked:** the sweep (time), the limits under load, a real second person, the packaged app, Firefox/Safari (WebP encoding falls back to JPEG there, untested), sites behind bot protection, a DM sent from the app end to end (its lookup and the client's sending were checked separately).

**Open:** a permission like "embed links" (today everybody who may write gets previews), a server setting in the admin area instead of the environment variable, smaller copies of large pictures in channels (needs an image library), other video hosts (Twitch clips, Vimeo), the website's texts.

## 27 September 2026: a switch for previews in direct messages

From `docs/PLAN.md` 3.3 (user's decision of 25 September 2026: a switch "no link previews in direct messages", in the sealed settings; user: "erledige alle Punkte aus 2"). Einstellungen > Ansicht, section "Direktnachrichten" (only with a directory account): "Linkvorschauen in Direktnachrichten". Off, `sendDm` makes no previews at all (no lookup by the desktop app at the linked host, none by the directory for a browser; the message goes out with its text only), and `DmView` shows no previews either, received or sent before (user, 27 September 2026: "wenn ich Vorschau ausschalte möchte ich auch bei empfangenen Nachrichten die Vorschau nicht sehen"): their encrypted pictures are not fetched from the directory and no YouTube player appears. Switched on again, they show again (they stay inside the messages).

- Stored as `VoiceSettings.dmLinkPreviews` (default true) and, with a directory account, inside the sealed settings as `SealedSettingsContent.dmLinkPreviews` (protocol; copied to the directory repo). Sync like the server order and the block list: the account's value wins when the status is read, a change here pushes, every push writes the value, so a switch back on elsewhere wins over a device's stale "off"; a blob from before says nothing and the device's value stays and is pushed.
- The hint names who would look the link up: the desktop app from this computer, or the directory for a browser.

**Decisions:** it covers sending and showing (user, 27 September 2026); it sits under Ansicht, shown only with a directory account (Claude's, confirmed by the user the same day).

**Checked:** protocol tests (the value round-trips, a blob without it or with a non-boolean says nothing), typecheck, web tests. **Not checked:** the switch in the running client and its sync between two devices (the store's code follows the server order's, which the store harness checked on 21 and 27 September 2026).
