# apps/server – App server (`@squorli/server`)

Part of the project description. The entry point is the root [AGENTS.md](../../AGENTS.md) (commands, definition of done, cross-cutting conventions, the map of all documentation in its section 0). Whoever changes the server's structure, routes, schema, configuration or pitfalls updates this file in the same step.

Read as well, depending on the task:
- New REST/WS types, `PROTOCOL_VERSION`, a new permission: `packages/protocol/AGENTS.md`.

## Conventions

- **Checking permissions:** Every protected route fetches `requireMember()` and checks `can(actor, Permission.X)`; effects on other members/roles additionally `outranks()`/`canSetRolesOf()` (PUT /api/members/:id/roles: one's own roles only as an owner, else 403 `own_roles` (user's decision, 6 October 2026: a member sees their roles, somebody above changes them); the first owner may change another owner's roles, nobody else; user's decision, 19 September 2026; the client mirrors the rules in `apps/web/src/memberRank.ts` so the menu only offers what is accepted)/`canTouchRole()`/`canGrant()` from `authz.ts` (assigning a role to a member or a reaction role needs `canGrant` over that role's whole permissions as well as its position; 2 October 2026: by position alone a helper with MANAGE_ROLES gave themselves any lower role, ADMINISTRATOR included). **Editing a role's mask or an overwrite list checks `canChangeGrant`: only the bits that change** against the stored mask or row count, a right the editor lacks stays as it is either way (6 October 2026, `docs/features/ui-admin.md`; until then the whole new mask was checked and a role holding one such right could not be touched at all, not even its name: every Discord-imported server hit that). The owner is always administrator. Structure changes end with `broadcastStructure()`. Adding a permission and the order in the role editor: `packages/protocol/AGENTS.md`.
- **Checking permissions per channel (23 September 2026, `docs/features/channel-permissions.md`):** a route that is about one channel uses `channelActor()` (`channelGuard.ts`) instead of `requireMember()` and checks the right with `canIn(ctx.perms, Permission.X)`; the WS handler uses `resolveChannel()`. **An invisible channel answers 404 `unknown_channel`, never 403** (a 403 would say it exists). Every event about a channel goes through `hub.broadcastToChannel()`, never `hub.broadcast()`; `broadcastStructure()` invalidates the visibility snapshot, so anything that changes roles, members, channels, categories or overwrites must end in it (a seat or hold change goes through `voice/sticky.ts`).
- **Media permissions twice:** camera/screen only with `STREAM_VIDEO` and without a block (`members.stream_blocked`, subtracted in `actorOf()`). The client hides the buttons, the app server writes `canPublishSources` into the LiveKit token (microphone always; camera, screen, screen audio only with the permission). LiveKit enforces it; on changes at runtime via `RoomServiceClient.updateParticipant` (`livekit/admin.ts`). **Every route that can change what a seated member may do in their channel must call `syncVoiceAccessOf` (`livekit/sync.ts`, until 23 September 2026 `syncStreamGrantsOf`) before the structure broadcast** (member roles, owner status, role permissions, role deletion, the stream block, the overwrites of a channel or category, a channel's category or `allowVideo`, the AFK channel): it re-syncs the camera/screen grants and throws out whoever may no longer see or enter the channel (`removeParticipant`; LiveKit checks a token only at the join). The token's grants are fixed at the join; without the sync the client shows the camera button (it gets the new permissions at once) and LiveKit answers "failed to publish track, insufficient permissions" until the member rejoins (user's report, 18 September 2026).
- **AFK channel takes effect server-side (17 September 2026):** who is absent comes from the clients' `activity` reports (a modified client can only keep its own user present), but the AFK channel itself is enforced: its LiveKit token carries no publish and no subscribe grant, it cannot get a radio (409 `afk_channel`), and the move is the server's `voice.moved`. Details and the user's decisions: `docs/features/afk.md`.
- **Moderation takes effect server-side:** stopping camera/screen = LiveKit `mutePublishedTrack` + WS `voice.stop`; moving = WS `voice.moved` (the client fetches a token for the target channel itself and joins, the server checks that like any join). Only with `MODERATE_VOICE`, never against the owner or oneself, rank must be higher.
- **Owners (several, 14 September 2026):** `server_settings.owner_id` = first owner (at first login, irrevocable), further ones via `members.is_owner` (`PUT /api/members/:id/owner`, owners only, not oneself). `actorOf()` sets `isOwner` from both, the bootstrap marks the first owner in `members` retroactively. Owners always have `ADMINISTRATOR`, rank above every role (`outranks`), cannot be kicked/banned/moderated and are at the very top of the member list. `Member.isOwner` in the protocol; `ServerSettings.ownerId` remains the first one.
- **Accounts required, server accounts (user requirement, 25 September 2026; replaces "only with account" of 14 September 2026):** no temporary users. A key signs in only with an account: a directory handle (`users.handle`, cached; the cached one counts while the directory is unreachable) or a server account of this server (`local_accounts`, `~name`). `hasAccount()` in `auth/session.ts`. `/api/auth/verify` answers a key without either 403 `registration_required` (with `localAccounts` in the body), also for the very first sign-in: the owner must register too; a key this server never saw gets no `users` row out of it. A **member from before** without an account gets a session with `registrationRequired: true`: `requireMember` answers 403 `registration_required`, the WebSocket hello closes with **4013** (`CLOSE_REGISTRATION_REQUIRED`), only `GET /api/me` and `POST /api/local/claim` work. Server accounts live in `src/auth/local.ts` (routes, their own stricter rate limits, avatar; every other path is limited by `src/rateLimits.ts`, `docs/features/rate-limits.md`: a new public route gets a rule there) and `auth/routes.ts` (`checkChallenge`, `admit` = ban, membership, invite, owner, session; shared by verify and registration). Whether server accounts may be registered: `server_settings.local_accounts` (admin panel > Server, `PATCH /api/settings { localAccounts }`), always on without `DIRECTORY_URL` (`localAccountsLocked`), pinned by `LOCAL_ACCOUNTS` (`setLocalAccountsConfig()` in `state.ts`, 409 `locked_by_config`). `require_account` stays as an unused column; `ServerSettings.requireAccount`/`requireAccountLocked` and `/api/health.requireAccount` are always true for clients from before. Details: `docs/features/local-accounts.md`.
- **Server directory (M6d, 14 September 2026):** the chat server sends `name`, `listed`, `description` (max 200), `openJoin` and `memberCount` with every registration (`ServerRegisterRequest`); the directory fetches the icon itself from `<proofUrl-Basis>/api/server-icon` (host is proven, raster images up to 2 MB, `iconUpdatedAt` stays when the bytes are unchanged) and serves it under `GET /api/servers/<host>/icon`. Clients therefore load server icons only from the directory (`directoryServerIconUrl()`), never from foreign servers. Public listing `GET /api/servers` = servers with `listed` that registered within 3 days. Admin panel > Server: "Im Serververzeichnis auflisten" + Beschreibung (disabled without directory). Changing name/listed/description/openJoin/icon re-registers (debounced 1.5 s, registration limit at the directory is 10/min per IP). Join via link = open the server's own origin.
- **`/api/health` says whether new members need an invite (19 September 2026):** `inviteRequired` = `!settings.openJoin`, so the login shows the invite field from the start. No secret (a sign-in without a code answers `invite_required` anyway) and no `PROTOCOL_VERSION` bump: the client treats a missing field as false (older servers). Checked by the smoke test.
- **Login splash:** server icon and server name from `/api/health` at the top of the login card (fallback: Squorli icon mark and "Squorli"), footer "Betrieben mit Squorli · Version <version>" below the card; `version` comes from `apps/server/package.json` (read at startup, `../package.json` relative to `dist`/`src`, also in the container).
- **Server name and icon:** `/api/health` returns `serverName` and `iconUrl` so that title and favicon are already correct in the login; when logged in, `settings.name`/`settings.iconUrl` apply (live update via `structure`). Icon only as PNG/JPEG/WebP/GIF up to 2 MB (no SVG: could contain scripts and is served same-origin), file `DATA_DIR/server-icon`, URL with `?v=<timestamp>` and `immutable` cache.
- **Database:** Change the schema only in `apps/server/src/db/schema.ts`, then `pnpm db:generate`. Migrations are applied automatically at server start; do not edit generated SQL files by hand.
- **Directory service (M6):** The chat server never depends on the service: handle resolution at login is best effort (timeout 2.5 s, errors only logged), display falls back to the display name or `anon-<key>`. The web client calls the service directly (URL from `/api/health`, CORS open for GET/POST). Registration = signature over the service's host + handle + nonce; one key has exactly one handle, handles are immutable (M6a). The service itself (routes, schema, account page, smoke test) lives in `../squorli-directory` (root `AGENTS.md` section 2a).
- **Devices (29 September 2026, the user's decision: a device that was signed out must not get back in with the account's key; `docs/features/devices.md`):** a sign-in names its device's key and proves it, the session stores it, and a session counts only while its device is let in (`deviceAllowed`): for a directory account the directory says which devices those are (`users.devices_enforced`, `users.device_keys`, taken only from answers to the server's token), for a server account this server does (`local_devices`). **A new way in (a route that resolves a session by itself, a new socket) must go through `lookUpSession`/`requireSession`**, which also removes a refused session's row. An account that is not enforced lets a sign-in without a device in; that is what keeps apps from before working. Signing another device out needs the password's auth key, never a session alone. No `PROTOCOL_VERSION` bump: optional fields, REST codes, the reason of close 4011.
- **Device management (M6c; the sessions under the devices):** `sessions.id` is the public identifier (the token stays secret), `label` comes from the User-Agent at login (`labelFromUserAgent`, the client cannot set it), `last_used_at` is written in `resolveSession()` at most every 5 min. Remote logout deletes the row and closes exactly its WebSocket with **Close 4011 `session_revoked`** (`hub.disconnectSession`; kick remains 4010 + `removed`). The client reacts in `store.sessionLost()`: WS close 4011, WS error `unauthorized` and REST 401 with a token set (`api.onUnauthorized`) lead to the login with a message, without reconnect. `store.logout()` calls `DELETE /api/me/sessions/current` (best effort). No `PROTOCOL_VERSION` bump: close codes are not events. Until 29 September 2026 the directory knew no devices ("whoever has the key has it") and a device that was signed out signed in again with the account's key; the entry above replaced that. The session routes stay for clients from before.
- **Suspended directory accounts (27 September 2026, the user's decision 9 of `docs/PLAN-reports.md`):** the directory tells a registered server with `DirectoryAccount.suspendedUntil`; `directory.ts` stores it in `users.suspended_until` wherever it looks an account up with its token (`refresh`, `syncAll`, `syncOne`; never from a public lookup) and calls `onSuspended` for a date that lies ahead. `requireSession` refuses such a user with 403 `account_suspended` and `until`, the sign-in and the WebSocket's hello do the same (`suspensionOf`), all only while `refusesSuspended()` says so (the setting, and a directory at all). **A new way in (a route that resolves a session by itself, a new socket) must ask `suspensionOf` too.** The session rows stay on purpose: they work again when the suspension is over. Server accounts are never concerned. Details: `docs/features/reports.md`.
- **Account deletion through the directory (15 September 2026, user's wish):** a user deletes their account on one server from the directory's account page or via right-click on the server in the rail; both sign the action `server-leave` at the directory. The directory only relays: it pushes `{publicKey}` to `POST /api/directory/leave`, and the server confirms with its own token (`confirmLeave`) before deleting anything, so an unsigned push can at most trigger a check (same principle as `/api/directory/notify`). The first owner (`server_settings.owner_id`) is refused (`founder`), other owners and members are deleted completely (`users` row with cascade, attachment files, WS close 4012, no `removed` event and no `PROTOCOL_VERSION` bump: close codes are not events); the LiveKit participant is removed too (a kick, a ban and a deletion all call `removeParticipant`, as the suspension does), and **a ban survives the deletion** (a bare `users` row with only the key carries it on, `users/deleteUser.ts`; until 2 October 2026 the ban went with the cascade and a banned account came back with the next invite). Missed pushes are fetched via `pendingLeaves()` in the 5-minute sync. There is no local "delete my account" route for a directory account; the directory is its single entry point (the user's decision). A server account (`~name`, 25 September 2026) has no directory and is deleted on its server: `DELETE /api/me` with the auth key of its password (`auth/local.ts`), the first owner refused as `founder` the same way.

## Known pitfalls

- **A rule that reads the request's path reads the route's, not the raw URL (2 October 2026):** the router decodes the path before it matches (`/%61pi/auth/verify` is `/api/auth/verify`), so a hook that compares `req.url` sees a path no rule knows. `rateLimits.ts` takes `req.routeOptions.url` (the matched pattern) and, without a route, the decoded path (`limitPath`); a new `onRequest` hook that decides by path does the same. The WebSocket plugin has `maxPayload` 64 KiB (`WS_MAX_PAYLOAD` in `ws/handler.ts`; the library's default is 100 MiB, parsed before any hello).
- **A server error says nothing of itself (2 October 2026):** a 5xx answers `{ "error": "internal" }`, the error goes to the log (`httpHardening.ts`); a route that needs a 500 with a reason sends it itself. Fastify's default put the message of a database error into the answer.
- **A template's placeholder never runs a production server (2 October 2026):** `loadConfig` refuses a LiveKit secret such as `.env.example`'s (`NODE_ENV=production` only; the compose files, the image and the Windows service set it), and logs a warning for a secret under 32 characters or the database's template password. A short secret that is private still starts, so an update never stops an installation that has one.
- **No owner yet and nothing names one:** the start logs a warning (index.ts, after the bootstrap) until the owner exists; the installer's default is a setup code, the third choice and an installation by hand are the cases.
- **Windows keeps an open file's name (28 September 2026, `docs/features/windows.md`):** a rename onto a file that is being read fails with `EPERM`, a download by this server itself is enough. Whoever replaces a file under `DATA_DIR` writes a temp file and calls `replaceFile`, never `rename`. Removing (`rm`) works under a reader of this process, not under a foreign handle without sharing (a virus scanner).
- **The server runs where no file modes and no `/tmp` exist:** no `chmod`, no fixed path with `/`, paths only through `join`/`resolve`; a parameter from the address is checked (UUID, signature, a fixed form) before it becomes part of a path, and `\` separates folders on Windows too. The job `windows` in `ci.yml` runs the tests there.
- **A PowerShell script cannot set an empty variable** (`$env:DIRECTORY_URL = ''` removes it, and the server then reads the value of `apps/server/.env`): start a test server on Windows with `node --env-file=<file> dist/index.js` and `DIRECTORY_URL=` in that file, or from Git Bash.
- **The backup's parameters of a server account must carry `bound`** (`GET /api/local/backup/:handle/params`; found 29 September 2026, released broken on 25 September): without it a client derives the keys of a host-bound backup as unbound and the right password reads as a wrong one on every other device. A smoke test that derives keys from parameters it made itself does not notice; `smoke-devices.mjs` reads the route.
- **`pnpm smoke:devices` and `pnpm smoke:suspended` run once per database:** the second run finds an owner and a registration at a played directory that is gone. `pnpm smoke` writes `scripts/.smoke-owner.json`; against a scratch database that replaces the key of the developer's own test database, so keep a copy and put it back.
- **Smoke test without a running server** fails with `ECONNREFUSED`; run `pnpm dev` or `node dist/index.js` first.
- **`GET /api/doctor` answers without a session from loopback** (docs/features/doctor.md): the dev Vite proxy forwards from 127.0.0.1 without `X-Forwarded-For`, so in development anybody who reaches the Vite server can read the report (it names the configuration, no secrets). Vite binds localhost by default; do not start it with `--host` on a shared network without that in mind. In the container the loopback caller is `docker compose exec server`, a proxy arrives from the Docker network. **Without containers that does not hold** (a proxy on the same machine is loopback): an installation on Windows sets `DOCTOR_TOKEN`, and then only the header `x-squorli-doctor` with that value opens the report (`isLocalCaller`). A text of `doctor.ts` that names a container or `squorli up` gets its second wording through `onPlatform`.
- **Rooms named `doctor-*` are the setup check's, not channels:** `roomsByIdentity()` skips them; whoever maps LiveKit rooms to channels elsewhere must do the same.
- **`PUBLIC_DOMAIN` must match the hostname in the browser address bar exactly** (dev: `localhost`; behind the proxy: `chat.example.org`; access via LAN IP: the IP). Otherwise `POST /api/auth/verify -> 401 (signature_invalid)`. `/api/health` returns `domain`; since the fix, the client shows both values in the error message. The smoke test always signs with `localhost`.
- **Session "logged out from another device" in your own browser:** after "Alle anderen Geraete abmelden" (log out all other devices) or a `DELETE /api/me/sessions/:id`, the session currently in use is kept (`current`); anyone who gets thrown out anyway has two tabs with two sessions of the same key (every login creates a new session; a second tab only shares it via `localStorage`).
- **Schema change while `tsx watch` is running:** the dev server restarts immediately after `schema.ts` is saved, i.e. before `pnpm db:generate` has generated the migration; it then runs against the old schema and queries on new columns fail (server stops responding). After `db:generate`, trigger a second restart (`touch apps/server/src/index.ts`), then the migrations are applied. Check: `SELECT count(*) FROM drizzle.__drizzle_migrations`.
- **Raw SQL with Date parameters** (`sql` + `${new Date()}`) fails in postgres-js; use `now()` in SQL.
- **Sessions (security review, 25 September 2026):** the table keeps only the SHA-256 of a token (`tokenHash` in `auth/session.ts`, migration 0034 hashed existing ones in place; look a session up by `tokenHash(token)`, never by the token). A WebSocket takes one `hello`, looks the session up again right after `hub.add` (a kick or sign-out in between) and closes with 4011 when the session ends (`expiryTimer` in `ws/handler.ts`); signing out the current session closes its sockets; a ban deletes the user's sessions. The request log shows the query secrets `key`, `s`, `sig`, `token` as `***` (`logRedact.ts`): a new secret in a query string belongs in that list.
- **The web client's pages carry a Content-Security-Policy** (`src/webHeaders.ts`, security review of 25 September 2026, with `frame-ancestors 'none'`, `Referrer-Policy: strict-origin-when-cross-origin`, `nosniff`): scripts only from the server and jsdelivr, frames only to the Twitch and YouTube players. It is the desktop app's policy (`apps/desktop/src/main/appFiles.ts`) plus `http:`/`ws:` connections for a plain-http LAN server: a new script host, frame host or other outside resource of the client must go into **both**, or the browser (or the app) blocks it with only a console message. Checked by loading the built client in headless Chrome: no violations, same-origin WebSocket, LiveKit and the directory reachable, a `javascript:` link refused.
- **Attachments are shown in place only for safe types** (`INLINE_TYPES` in `routes/attachments.ts`: png, jpeg, gif, webp, avif, video, audio, plain text, PDF; security review of 25 September 2026: an SVG opened on this origin ran its script, and in the browser client the key lies in this origin's localStorage). Every other type, SVG and HTML included, goes out as `attachment`, and every answer but a PDF carries `Content-Security-Policy: default-src 'none'; ...; sandbox` (Chrome's PDF viewer does not work under a sandbox and runs its script apart from the origin). The type itself is still the uploader's; never widen the list without that in mind.
- **Attachments need a signed, expiring link, no token** (`/api/attachments/<uuid>/<name>?e=<expiry>&s=<hmac>`, since 25 September 2026; before, the UUID alone was the secret), so that `<img src>` works. `attachmentUrl()` in `routes/messages.ts` signs with `server_settings.link_secret` (`src/attachmentLinks.ts`, migration 0033); a link lives 7 to 8 days (rounded to the day for the browser cache), a missing, changed or expired signature is a 404. Never build an attachment address anywhere else, never store one: it is made when a message is sent out. The client reloads histories older than 3 days and forgets all after a reconnect (`serverConnection.ts`, `HISTORY_MAX_AGE_MS`).
- **White screen after deploy, "Expected a JavaScript module ... MIME type text/html":** the browser had the old `index.html` with the old asset hash in its cache. Since the fix: missing files with an extension get a 404 instead of the app shell, `index.html` is served with `cache-control: no-cache`, hashed assets with `immutable`. The user must hard-reload once after the fix. Run `pnpm build` (root) after every client change, otherwise an old client sits in `apps/server/public`. Second cause (fixed): `@fastify/static` ran with `wildcard: false` and registered one route per file at startup; new assets after a build without a restart got a 404. Now `wildcard: true`, files are resolved per request.
- **`Route GET:/ not found` (Fastify 404 on `/`):** the server is running without a built web client. Since the fix, `/` answers with 503 and an explanation; the cause is a start without `pnpm build` (missing `apps/server/public`) or an old Docker image. `/api/health` works regardless.
- **Server icon gone after emptying `apps/server/data`:** the DB still had `icon_mime`, so favicon, sidebar, login and server rail showed a broken image (happened 14 September 2026). Since the fix the settings routes check at startup whether `DATA_DIR/server-icon` exists and otherwise clear the entry with a warning; upload the icon again in Verwaltung > Server. When emptying the data folder, keep `server-icon` or expect this.
- **Fresh database had only the role "Mitglied" (fixed 14 September 2026):** migration 0004 creates "Mitglied" in empty databases as well; since then the bootstrap no longer checks for "no roles" but for "no default role" and creates Gast/Admin/Mitglied individually as needed. Check the fresh-install path: recreate `chat_smoke` from scratch via `DROP DATABASE ... WITH (FORCE)` + `CREATE DATABASE` and run `pnpm smoke` (not only against an incrementally migrated DB).
- **Resetting the dev database** (new owner at the next login): `docker exec squorli-dev-postgres-1 psql -U chat -d postgres -c "DROP DATABASE chat WITH (FORCE)" -c "CREATE DATABASE chat OWNER chat"`, empty `apps/server/data/attachments`, then `touch apps/server/src/index.ts` (migrations + bootstrap run only at startup). The database `directory` in the same container is the old dev database of the directory service (before the move); leave it until the data is taken over into `../squorli-directory`.
- **Only guest after joining:** anyone who cannot write does not yet have the "Mitglied" (member) role. An admin assigns it in the member list (click on the name). This is intended (decision of 13 September 2026), not a bug.
