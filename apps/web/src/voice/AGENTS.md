# apps/web/src/voice – Voice, camera and screen share

Part of the project description. The entry point is the root [AGENTS.md](../../../../AGENTS.md) (commands, definition of done, cross-cutting conventions, the map of all documentation in its section 0). These rules also apply to the components outside this folder that show or steer media: `VoiceStage.tsx`, `VoiceDock.tsx`, `VideoWindows.tsx`, `VideoAudioControls.tsx`, `CameraPicker.tsx`, `UserVolumeControl.tsx`. The files of this folder are listed in `apps/web/AGENTS.md` (`src/voice/`).

Dated feature entries (per-person volume, `VIEW_VIDEO`, cues, pop-outs and fullscreen, voice card, screen share freezing in a pop-out, voice channel moderation): `docs/features/voice-video.md`. Web radio and the embedded players (`radioPlayer.ts`): `docs/features/radio.md`.

Blocked people (27 September 2026, `docs/features/reports.md` stage 3): App.tsx hands the voice client the blocked keys of the identity used on the voice server (`setBlocked`); `applyUserVolume` and `audioMuted` keep their voice and screen sound silent whatever the slider says, and `VoiceMemberMenu.tsx` shows a line instead of the slider. The tiles stay: blocking is a view of this user's client, not moderation.

## Conventions

- **Voice channel presence vs. media:** `voice.join`/`voice.leave` over the WebSocket are the intent ("I am in the channel", for everyone's sidebar). Whether someone actually sends, hears or speaks is known only to LiveKit; the client shows both together. Participants known only to LiveKit (bots) appear as "(extern)" (external).
- **Mute and deafen (Discord logic, user requirement 13 September 2026):** `setMuted()` = microphone muted by hand; `setDeafened()` = incoming audio muted (`<audio>.muted`) **and** microphone force-muted. Undeafening restores the microphone only if it was not muted by hand (`micMutedByUser` in the voice core). Clicking the microphone while deafened ("Ton aus") lifts both. Deafen ("Ton aus") is set as the LiveKit attribute `deafened` (token grant `canUpdateOwnMetadata`) so others see it in the sidebar and tiles. **Since 23 September 2026 both, and whether camera or screen share is on, also go to the chat server** (`voice.join` carries them, `voice.status` on every change, `App.tsx`), so the whole server and the status API see them, not only the same room; the sidebar takes LiveKit's state for the room the viewer is in and the reported one elsewhere, for all four icons (`docs/features/status-api.md`).
- **Voice codec:** always Opus in the browser (mandatory WebRTC codec, nothing better available). **The bitrate goes to LiveKit as `audioPreset: { maxBitrate }`** (`micPublishOptions()` in `voiceClient.ts`, typed as `TrackPublishOptions` and pinned by `micOptions.test.ts`); until 17 September 2026 it was passed as `audioBitrate`, which the SDK ignores silently, so every channel ran at the SDK default of 48 kbit/s whatever the admin chose. Check the real rate in the debug view ("audio send" kbit/s; with DTX it drops to almost nothing in silence, so measure while speaking). Quality per voice channel in the admin panel: `audioBitrate` (kbit/s, choice from `AUDIO_BITRATES`, default 64) and `audioStereo`. Mono = DTX + RED (silence costs nothing, redundancy against packet loss) with the browser's echo/noise suppression; stereo = `forceStereo`, capture with `channelCount: 2` and **without** audio processing (which would mix down to mono), for music. Changing the channel switches connected clients live (`setAudioProfile()`: republish the microphone).
- **Unlock audio inside the user gesture:** `client.prepareAudio()` sits in `App.joinVoice()` before the first `await`. It creates the single shared `AudioContext` (microphone gate and level meter hang off it), calls `resume()` and plays 0.1 s of silence once (`SILENT_WAV`) so that Safari/Firefox unlock `<audio>` playback for the document. Without this the context was only created after the token and `room.connect()`: level 0 (nobody heard the user) and silent playback on the first join (reported by two users on 14 September 2026). In addition, every gesture in the document (pointerdown/keydown, capture) releases blocked audio; the dock shows "Ton freigeben" (release audio, playback) or "Mikrofon freigeben" (release microphone, context not `running`), the debug view shows the "Audio" line. `MicPipeline.start()` waits for `resume()` at most 300 ms.
- **Ask for the microphone inside the user gesture too (19 September 2026):** `client.prepareMic(deviceId, stereo)` sits in `App.joinVoice()` next to `prepareAudio()`, before the first `await`, for every channel but the AFK channel. WebKit shows its microphone prompt only while the tap still counts and otherwise refuses at once with `NotAllowedError` and no prompt; `join()` opens the microphone only after the token and the LiveKit connection, seconds later. Safari with a stored permission for the site hid that, an iPhone's home screen app (no stored permission, asks on every start) could join no channel (user's report). `join()` takes the prepared capture over when device and mode match (`MicPipeline.start(..., preopened)`), releases it otherwise, and `joinVoice()` releases it when the token or the connection fails (`releasePreparedMic()`). This replaces the earlier rule "microphone only after connecting, so a connection error does not also cost a permission prompt": the capture still starts after connecting, but the prompt now comes with the tap. Every other capture that may need a prompt must start inside its click as well (microphone test, camera picker: they do). `prepareMic()` is the FIRST thing `joinVoice()` does, before `prepareAudio()`: nothing that starts audio comes before the request. A refused microphone (`NotAllowedError`) is explained by the browser's permission state (`micPermission.ts`, tested: stored refusal, refused without asking, kept back by the system), because WebKit has one text for all of them; the mobile join sheet shows the voice client's explained text, not the bare error.
- **Speaker outline:** own participant = `gateOpen && !micMuted` (immediate). Others = local RMS measurement per subscribed microphone track (AnalyserNode, 50 ms, `VoiceGate` with threshold 0.015 and 250 ms hold, `addMeter()`); LiveKit's `isSpeaking` (server notification, ~0.5-1 s later) only as a fallback when the audio context is not running. `deploy/livekit/livekit.yaml` sets `audio.update_interval: 150` for this.
- **Stereo capture: never on a phone, and a one-sided input goes on both sides (19 September 2026, user's reports):** a stereo channel captures two raw channels without the browser's echo cancellation, noise suppression and gain control. On a phone or tablet that is wrong twice: with the iPhone on its loudspeaker the others heard themselves back, and its mono microphone arrived on one side of the two-channel stream. So `VoiceClient.capturesStereo()` = stereo channel AND not `PlatformMedia.mobile`; every `mic.start()` and `prepareMic()` goes through it, never pass `audioProfile.stereo` to the pipeline directly. The channel's Opus settings (`micPublishOptions()`: `forceStereo`, no DTX/RED) stay, the mono capture is spread to both sides. On computers the same one-ear effect comes from an audio interface with the microphone on input 1: in stereo captures `micPipeline.ts` measures both channels (`oneSided.ts`, `OneSidedDetector`, tested: one channel below 1 % of the other for half a second of signal) and routes the live channel onto both sides, back again when the second channel comes alive (above 5 %). Raw level and boost hang behind that routing (the `bus`), so the automatic does not see half the level. The debug view names the case.
- **Microphone boost sits before everything else (18 September 2026):** `micPipeline.ts` runs the capture through `micBoost.ts` (gain, then a soft clipping guard) and only then into the level meter, the gate and the published track; the automatic (`AutoGain`) measures the RAW input through its own analyser. Keep that order: a gate or meter in front of the boost would never see the quiet microphones the boost is for. **It runs in stereo channels too, and that is where it matters:** stereo captures without the browser's processing, so without its gain control, and the microphone arrives at its raw level (the user's report: level bar low, threshold at the far left, everyone quiet; reproduced: gate never open). Never exclude stereo from the boost again. In mono channels Chromium's own gain control already normalizes a quiet capture, so the automatic ends near x1 there. The learned gain is remembered per microphone and capture mode (`chat.micBoost.v1`, key `<device>` or `<device>|stereo`). The setting (`VoiceSettings.micBoost`) is per device and not part of the directory account. Measurements: `docs/features/voice-video.md`.
- **Phones and tablets (19 September 2026, user's wish: recognise mobile devices and adapt audio and video):** the DEVICE is told by `platform/mobile.ts` (`isMobileDevice`: user agent, an iPad that calls itself a Mac by its touch points, `userAgentData.mobile`; tested) and reaches components as `platform.mobile` and the voice core as `PlatformMedia.mobile`. It is not the narrow layout (`App.tsx` decides that by window width, a small desktop window has it too); never use one for the other. What follows from it: the boost's limits (`boostLimits(mobile)` in `micBoost.ts`: x40 and speech from a raw level of 0.0006 instead of x12 and 0.003, because an iPhone's capture never reached the voice activation threshold and the automatic never even started), the defaults applied once per device (`withDeviceDefaults()` in `settings.ts`: camera 360p, marked by `VoiceSettings.mobileDefaults`, the user's later choice stays), the own rear camera is not mirrored (`mirrorsOwnCamera()` in `videoDisplay.ts`, from the track's `facingMode`). What a device CAN do is asked from the browser, not derived from "mobile": `VoiceClient.supportsScreenShare()` (no `getDisplayMedia` on phones: the stage shows no button), `supportsBlur()`, the empty output device list. The phone limits are an assumption, not a measurement; the debug view shows the raw level ("Eingang") next to level and boost to check them on a device.
- **Microphone test (19 September 2026):** `VoiceClient.startMicTest()` / `stopMicTest()` (Einstellungen > Sprache und Audio) play the own microphone back through `MicPipeline.setMonitor()`, a second output behind the boost and BEFORE the gate, so it sounds whatever voice activation and push-to-talk do; the monitor output survives a restart of the capture (device change). In a channel it listens to the running capture and the published track is LiveKit-muted for as long as it runs (`applyMic()`: by hand OR deafened OR `state.micTest`; user's requirement: nothing of the test reaches the channel), muted first, monitor second; afterwards the mute returns to what it was. In no channel (and in the AFK channel) it opens a capture of its own (`testMic`). `join()` and `leave()` end it. Never play the published track itself back: LiveKit's mute disables exactly that track.
- **Speech gate is local:** voice activation and PTT switch a GainNode in `micPipeline.ts`, not the LiveKit track. The track stays published and "unmuted"; only the mute button uses LiveKit mute (visible to others). This avoids signaling on every word, and switching back on is instant.
- **Per channel since 25 September 2026:** the lists below come from `channelVideoAccess()`, which takes the server's per-member `VoiceMember.viewVideo` of the voice channel (the channel's overwrites resolved) and falls back to `videoAccessOf()` (server-wide roles) for servers without the field; `mayViewIn()` uses my mask in the channel (`docs/features/channel-permissions.md`).
- **Watching camera/screen (`VIEW_VIDEO`, 17 September 2026, user's requirement):** a member without the permission receives only microphones, no camera, screen or screen audio. LiveKit has no per-source subscribe grant in the token (`canSubscribe` is all or nothing, `livekit-server-sdk` 2.19), so the restriction is set by the **senders**: every client calls `setTrackSubscriptionPermissions` for its own tracks and LiveKit enforces it, so a modified receiver cannot get around it. `voice/videoAccess.ts` computes the list from the server state exactly like `actorOf()` (OR of the member's roles and the default role, owners = administrators; `streamBlocked` plays no part): if the default role carries `VIEW_VIDEO` everyone is allowed (`allParticipantsAllowed`, nothing is sent per member); otherwise (the default, guests lack it) all members are listed, viewers with `allowAll`, the others with `allowedTrackSids` = the sender's microphone track ids (always set, because a missing list means "everything"; empty before the microphone is published). "Open" is decided by the default role and not by an empty list, so a member who joined seconds ago cannot slip through; participants who are no members (bots) get the microphone only. The list is re-sent when roles/members change (`App.tsx` effect -> `client.setVideoAccess`), when a local track is (un)published (republishing the microphone changes its id) and when an unknown participant connects; identical lists are skipped, the SDK repeats it after a reconnect. Receiver side: without the permission the client unsubscribes from video and screen audio (`applyVideoSubscriptions`), shows no remote tiles and the stage explains why. Limit: a sender running a client older than this change does not restrict its tracks; then only the honest receiver client holds back. The app server has no part in this beyond the bit in roles and `me`.
- **One voice connection per account and server (22 September 2026, user's wish):** joining a voice channel from a second device or tab ends the account's voice elsewhere on that server. The server does it at `voice.join` (`presence.othersOfUser`, `voice.moved` with `reason: "elsewhere"` to the other client, `LivekitAdmin.removeParticipant` when it sits in another room; in the same room LiveKit's duplicate-identity rule has already replaced it). The client asks first: `joinVoiceAsked` in App.tsx shows a confirm when `voiceElsewhere()` (`voice/elsewhere.ts`, pure, tested) finds the account in the server's presence and the seat is not this client's; without anything to ask the join stays synchronous in the click (microphone gesture). On a phone the sheet closes before the confirm and comes back on cancel or with the error. Details: `docs/features/voice-video.md`.
- **AFK channel (17 September 2026):** joining the server's AFK channel (`settings.afkChannelId`) passes `JoinOptions.afk`: its token allows neither publishing nor subscribing, so the client requests no microphone, shows microphone and audio as off (`VoiceState.afkRoom`, attribute `deafened` for the others) and refuses mute, deafen, camera and screen until another channel is joined; dock and stage disable the buttons and hide the radio control. A move there for inactivity (`voice.moved` with `reason: "afk"`) keeps the view as it is and the dock offers the way back (`joinVoice` option `auto`, `afkReturn` in App.tsx); when the admin changes which channel is the AFK channel, App.tsx joins again for a fresh token. `docs/features/afk.md`.
- **Watching others' video is the user's choice (19 September 2026, user's requirement):** a screen share is never received by itself, the user turns it on; a camera is received by itself and can be turned off; both per feed and for yourself only (`VoiceClient.setVideoWatching(tileId, on)` / `isVideoWatching`, rules in `videoWatch.ts`, tested). Not watching = not subscribed (`applyVideoSubscriptions()`: `VIEW_VIDEO` AND watching; a share's audio follows its picture) and no tile in `VoiceState.tiles`; that the feed exists is still known from `VoiceParticipant.cameraOn` / `screenOn`, from which the stage builds the tile that offers to watch. The choice lives in memory only and ends with the feed (`TrackUnpublished`: a share started again is off again; a camera that is merely switched off stays published and keeps the choice), with the participant and with the connection. The offer tile depends on the participant list being current: `TrackPublished` and `TrackUnpublished` must call `refreshParticipants()`, because an unwatched share causes no subscription event. Never store it, and never auto-subscribe a share again (no focus, pop-out or fullscreen path may turn one on without the user's click).
- **Background blur:** `@livekit/track-processors` (`BackgroundProcessor` in mode `background-blur`, MediaPipe segmentation in the browser). **Self-hosted since 27 September 2026** (user's decision of 25 September 2026): `assetPaths` point at the client's own origin (`blurAssets()` in `voiceClient.ts`: the chat server, or `app://squorli` in the desktop app). The WASM (`vision_wasm_internal.*` and the `nosimd` variant, ~19 MB) is copied by the plugin `mediapipeWasm` in `vite.config.ts` from the `@mediapipe/tasks-vision` version `@livekit/track-processors` depends on (served from `node_modules` in dev, into `dist/mediapipe/wasm/` on build), so it always matches the library's code; raising `@livekit/track-processors` raises it with it. The model `public/mediapipe/selfie_segmenter.tflite` (selfie segmenter float16, Apache-2.0, 249537 bytes, sha256 `191ac952…658b`, from `storage.googleapis.com/mediapipe-models/image_segmenter/selfie_segmenter/float16/latest/`, Last-Modified 7 May 2023) is committed. No request leaves the origin any more, so both CSPs dropped `https://cdn.jsdelivr.net` from `script-src`. Checked in headless Chrome with a fake camera under the server's CSP: frames processed, only the three own files requested. Check support via `supportsBackgroundProcessors()`; Firefox/Safari show the option disabled.
- **Separate output for screen audio (26 September 2026):** Chromium plays EVERY remote WebRTC track of a page through one shared renderer with ONE output sink (`WebRtcAudioRenderer`; `setSinkId` on any of their elements replaces that sink, the last call wins), so a share's audio on another device cannot go through its element. With a separate device chosen, `applyShareAudio()` plays it through its own `AudioContext` with `setSinkId` (`screenCtx`: the track's source into a gain, which carries the share's volume and 0 for deafen and "not listening", into the context's destination) while LiveKit's element keeps playing at volume 0 (Chromium hands the frame to Web Audio before the element's volume; checked with two peer connections in headless Chrome, `docs/features/voice-video.md`). Until then `setSinkId` per `ScreenShareAudio` track was the way, and it moved every voice to the screen device (user's report). **Never call `setSinkId` on a remote track or its element with anything but the voice device.** Without a separate device, while the context is suspended (no gesture yet) or when the browser refused the device, the element plays on the voice device as before; the route is checked again after subscription, device changes and settings changes. The share's volume lives in the client (`shareVolumes`), not in the element. The debug view shows device, track count, the path ("eigener Audiokontext" / "über das Element") and errors ("Bildschirm-Ton Ausgabe"); without a track (0) there is simply no remote share with audio yet.
- **Video (M3):** camera 720p with simulcast (180p/360p/720p, VP8), `adaptiveStream` + `dynacast` in the room: receivers get the layer that matches the size of the `<video>`. The stage only has to render the `<video>` at a suitable size. Screen share: 1080p30 (`ScreenSharePresets.h1080fps30`, up to 5 Mbit/s), **without simulcast** (otherwise adaptiveStream fetches the coarse layer for small tiles, text becomes unreadable), `contentHint: "detail"`. The own tab can be picked too (`selfBrowserSurface: "include"`, 18 September 2026, user's wish); `restrictOwnAudio` (Chromium 141+, ignored elsewhere) keeps this tab's playback (the others' voices, the radio) out of the captured audio, for the own tab and for "entire screen" with system audio alike, so nobody hears themselves back; never drop it while the own tab stays pickable. It always requests audio and publishes the audio as its own track (`ScreenShareAudio`), never mixed with the microphone; whether audio arrives is reported by `screenAudio` in the state, `explainScreenAudio()` provides the hint text (a browser: its dialog's options; the desktop app, second argument: the app's own picker, or that audio exists on Windows only). Cancelling in the browser dialog (NotAllowedError/AbortError) is not an error.
- **A received video's statistics come from the receiver's raw report (22 September 2026):** LiveKit's `getReceiverStats()` has no freezes, jitter buffer, decode time, round trip or `powerEfficientDecoder`; `VoiceClient.videoReceiveSample(tileId)` reads `track.receiver.getStats()` and `voice/videoStats.ts` turns two samples into the interval's rates and a diagnosis (the thresholds are a first guess, see `docs/features/voice-video.md`). Firefox fills fewer fields; missing ones show as "?", never as 0.
- **A share's audio is opt-in per listener:** `setScreenAudioListening(tileId, reason, on)`; silent (element muted, publication disabled) unless the user watches that share in the stage (every share turned on with "Ansehen", pinned or not; 26 September 2026), shows it in fullscreen, or popped it out. Every place that mutes elements goes through `audioMuted()` (deafen OR not listening); never set `element.muted` directly. **LiveKit's `room.startAudio()` unmutes every attached audio element** (24 September 2026), and LiveKit runs it by itself on `ParticipantEvent.AudioStreamAcquired` (every local audio publish, the own share's audio too); `VoiceClient.startAudio()` and a listener on that event put `applyAudioMuted()` back right after it. Whoever calls `room.startAudio()` anywhere else does the same. A share on its separate device is silenced in its gain, not in its element: `applyAudioMuted()` ends with `applyShareAudio()`, which asks the same `audioMuted()`.
- **A share's audio may come from the platform (desktop app on Windows):** after `setScreenShareEnabled(true)` the client asks `media.takeScreenAudio()`; a track it gets is published as `ScreenShareAudio` (stereo, no DTX/RED, 128 kbit/s), and `media.stopScreenAudio()` ends the capture when the share ends, also by itself (`LocalTrackUnpublished`, where the client unpublishes that audio too, because LiveKit only does so for a share it ended itself). In a browser both are no-ops and the browser's own audio track applies.
- **No platform import in the voice core:** what differs between browser and desktop app reaches `VoiceClient` as its second constructor argument (`PlatformMedia` from `src/platform/types.ts`: `blocksInsecureMedia`, `screenSharePublishOverrides()`); tests leave it out. The overrides are spread into the screen share's publish options after the capture: the codec the user chose in the desktop app's picker. What follows from that codec is decided in `screenShareOptions.ts` (pure, tested), not by the platform.
- **A share is captured and published in two steps (21 September 2026):** `setScreenShareEnabled(true)` calls `createScreenTracks()`, then asks `media.screenSharePublishOverrides()` and publishes each track itself, because the desktop app's picker (which runs inside the capture) also chooses the codec: VP8, or for moving pictures H.265 where the computer can send it and else H.264 (`ScreenPick.codec`, remembered by `platform/desktop.ts`; `movingCodec` in `screenPick.ts`; "Quick Share" always the latter). Never go back to LiveKit's `setScreenShareEnabled(true, ...)`: it takes the publish options before the picker. With LiveKit, H.264 means the constrained baseline profile, which Chromium on Windows encodes in software (measured; `docs/features/voice-video.md`), so never promise hardware encoding for it. H.265 is encoded by the graphics unit (measured; Chromium offers it only then).
- **A share of moving pictures is tuned the other way round (21 September 2026):** H.264 and H.265 shares get the hint "motion" (set on the captured track before publishing), "maintain-framerate", a higher limit and VP8 as the backup codec (`screenSharePublish`). Never send a game with "detail": Chromium then runs OpenH264 in its screen content mode at 13-14 frames per second (measured). **The limit of a screen share goes to LiveKit as `screenShareEncoding`; `videoEncoding` is ignored for that source.**
- **Video codec stays VP8 by default (user's decision, 18 September 2026; H.264 or H.265 is the user's choice per share in the desktop app since 21 September 2026):** AV1 with a VP8 backup for the screen share is to be tested later, do not switch without that test; what is known and what to measure: `docs/features/voice-video.md`, "Screen share codec" (an open decision in `docs/PLAN.md`).
- Server side of the media permissions (`canPublishSources` in the token, `members.stream_blocked`, moderation through `livekit/admin.ts`): `apps/server/AGENTS.md`, "Media permissions twice" and "Moderation takes effect server-side".

## Known pitfalls

- **An AudioContext has a fourth state on iOS, "interrupted" (19 September 2026):** WebKit sets it when the microphone prompt shows, when the capture starts and on a phone call. Whoever checks `state === "suspended"` before `resume()` never resumes it, and the microphone runs through a standing context: level 0 and silence for the others, while the others are still heard (their audio plays through `<audio>` elements). Always ask `contextNeedsResume(state)` (`gate.ts`: everything but "running" and "closed"; tested). `MicPipeline.start()` resumes after the capture opened, `prepareAudio()` and every gesture resume, and the context's `onstatechange` asks for it back while a microphone runs (a capturing page may start audio without a gesture in WebKit).

- **Browser autoplay:** audio from other participants may be blocked until the user clicks once; the client then shows "Ton freigeben" (unblock audio) (`room.startAudio()`).
- **Choosing an output device** (setSinkId) exists only in Chromium; Firefox/Safari show an empty list.
- **Screen share without audio:** only Chromium delivers audio, and there only with "Tab" (tab audio) or on Windows with "entire screen" with system audio enabled; individual windows never. Firefox/Safari never. The stage shows a yellow notice in both cases. The matrix (`docs/features/voice-video.md`, "Screen share audio: browser and system matrix") is checked with `/test/screenshare.html` per browser/operating system and recorded there.
- **The stage can live in another window (`StageWindow.tsx`), and so can everything it renders:** never reach for the global `window`/`document` in `VoiceStage.tsx` or in what it shows (menus, dialogs, observers, key listeners). Take them from the element: `el.ownerDocument`, `el.ownerDocument.defaultView` (also for `ResizeObserver`); never test `instanceof HTMLElement` on an event target (another window's element is none); open further windows from the window of the click (`onPopout(tile, opener)`). The radio's player iframe stays in the main window. Details: `docs/features/voice-video.md`.
- **Views in pop-out windows (Firefox):** attach a video only through `attachVideoView()` (`videoDisplay.ts`). For an element in another window it registers a `PopoutElementInfo` with LiveKit first; LiveKit's own `IntersectionObserver` lives in the main window and Firefox never sees a pop-out's element through it, so adaptiveStream paused the track and the pop-out froze (18 September 2026). A Firefox check without an installation: nightly win64 zip from archive.mozilla.org unpacked into the scratchpad, `firefox.exe -headless -no-remote -profile <dir>` with `user.js` (`dom.disable_open_during_load=false`), the page posts its result to a small node server.
- **Opening a camera on Firefox:** Firefox releases a stopped camera asynchronously and cannot share it with another process, so open right after stop fails with `AbortError: Starting videoinput failed`. Release a preview track BEFORE asking LiveKit for the camera (`CameraPicker.pick()`), and open cameras through `retryCameraBusy()` (`cameraRetry.ts`, one retry after 600 ms). `AbortError` is a device failure for the camera, a user cancel only for the screen picker (18 September 2026).
- **Switching the camera on with another device: LiveKit ignores the options when a track exists (19 September 2026, user's report: the camera picked in the dialog was never taken):** `setCameraEnabled(true, options)` only unmutes an existing (switched-off, so muted) track and reopens it with the constraints it was created with. `VoiceClient.setCameraEnabled()` therefore asks `cameraSwitch()` (`cameraSwitch.ts`, tested) first, with what the published track was opened with (`cameraOpened`): same camera and resolution = LiveKit's unmute (the publication and the receivers' choice stay); another one while off = unpublish, then a fresh track; another one while running = `restartTrack()` (also makes a changed send resolution take effect at once, which was ignored before). Keep `cameraOpened` current wherever the device changes (`setCameraDevice()`, `LocalTrackUnpublished`, `leave()`).
- **Camera off = muted track, not unpublished:** LiveKit's `setCameraEnabled(false)` mutes the camera and keeps it published; `refreshTiles()` skips muted cameras and must run on `TrackMuted`/`TrackUnmuted` too, otherwise the receivers keep a black tile (18 September 2026).
- **A microphone error is no connection error:** `join()` reports a failing `mic.start()` as `voice.errMic`, everything else through `explainConnectError()` (LiveKit URL, proxy hint). "Constraints could not be satisfied" / `OverconstrainedError` means the stored microphone is gone; `openMic()` in `micPipeline.ts` then falls back to the default microphone and keeps the stored choice (18 September 2026). Request devices only through `openMic()`, never with a bare `deviceId: { exact }`.
- Connection problems ("could not establish signal connection", drop after ~15 s, LiveKit URL, `--node-ip`, dev secret): `deploy/AGENTS.md`, "LiveKit connectivity".
