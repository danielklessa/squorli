# apps/web – Web client (`@squorli/web`)

Part of the project description. The entry point is the root [AGENTS.md](../../AGENTS.md) (commands, definition of done, cross-cutting conventions, the map of all documentation in its section 0). Whoever adds, removes or repurposes a file of the client, or changes a convention or pitfall, updates this file in the same step.

**After every client change:** `pnpm build` from the repo root and tell the user to reload (root `AGENTS.md` section 4, item 7); after a new `<Icon name>` run `pnpm icons`; after a dependency change `pnpm run licenses`. `tools/icons.mjs` collects only literal `<Icon name="...">` occurrences: an icon name kept in a record or variable never reaches the font subset and renders as nothing (found 26 September 2026 with the setup check's warning triangle); write the JSX literally per case.

- **One key per server account (25 September 2026, user's requirement: directory account and server accounts side by side, docs/features/local-accounts.md):** `State.identity` is the main identity (directory account or this device's key; friends, direct messages, synced settings). A server account has a key of its own, made at its registration or fetched with name and password, kept with its session token in `chat.serverAccounts.v1` (identity.ts) and never used anywhere else; `Store.identityFor(host)` is the key a server signs with, `storedToken`/`storeToken` read and write the server account's token for such a host. Switching the main identity (`loginDirectoryAccount`, `loginWithHandle`) keeps servers with a server account (`closeAllForeign(true)`); signing out of a server account forgets its key; the desktop app's full sign-out forgets all of them. Friends and direct messages are not offered on a server shown with a server account.
- **Devices (29 September 2026, docs/features/devices.md):** whatever the account's key signs, the device signs along: a new signed request to the directory goes through `directoryAction`/`directorySigned` in `api.ts`, a new sign-in path through `signBoth`, never through `sign` alone (an enforced account refuses a request without the proof). A device key is made only at an enrolment (`newDevice` where an account is made or its key is fetched with the password) and dropped when that fails. The account's key is wiped only on the directory's word (`Store.wipeAccount`); a chat server's refusal makes the client ask the directory first. Code that reacts to a lost session must tell the reasons apart (`sessionEndReasonOf`, `onUnauthorized(code)`): an expired session keeps "Weiter als", a device that was signed out does not.
- **Multi-server client (14 September 2026, user's requirement):** the web client of one server talks to other Squorli servers directly (`ServerApi` with `base` = their origin, WebSocket `wss://<host>/api/ws`, LiveKit URL from their `/api/rtc-token`). The rail switches the shown server without leaving the page; the voice connection stays on its server until the user joins a voice channel on another server, which disconnects the previous one. Login at a foreign server = the same browser key, signature over that server's `/api/health` domain, no invite (the rail only lists servers the handle is a member of); its session token is kept per host. Consequences: every chat server answers CORS for **all origins** (`@fastify/cors` `origin: true`, auth is Bearer-only, no cookies, so a foreign origin cannot act without the token; the signature stays bound to `PUBLIC_DOMAIN`), relative server URLs (attachments, icon) are resolved through `api.abs()`, older servers without CORS show "nicht erreichbar oder erlaubt keinen Zugriff aus anderen Clients" with a link to open them directly. The admin panel, settings dialog (sessions, name on this server; the mini profile too), member list and chat always act on the active server. Not multi-server: the login screen, the directory account and the friends/DM view (they belong to the own server's directory).

## Known pitfalls

- **`@types/dom-mediacapture-transform`** is a peer dependency of `@livekit/track-processors` (types for MediaStreamTrackProcessor); as a devDependency in the web package, otherwise `tsc` breaks.
- **A harness that runs twice against the same directory instance fails with 429** (29 September 2026): key fetches and the backup's parameters count per address (`BACKUP_RATE_LIMIT`); start fresh instances per run. The sign-in forms' fields (`.auth-login input`: full width, 44 px) also catch a radio button or checkbox placed inside the login; give such a control its own rule (`.device-choice`).
- **No hook below an early `return` (28 September 2026):** a component whose early return depends on props or state runs a different number of hooks from one render to the next; React throws and the whole client is gone (until 28 September 2026 only the window's background was left; since then `ErrorBoundary.tsx` shows a notice with "Neu laden"). Found in `RadioControl.tsx`, where it hit exactly the members without `CONTROL_RADIO` (`docs/features/radio.md`). All hooks first, then the return. `src/hookOrder.test.ts` checks every `.tsx`; it knows the repo's style only (`function` at the start of a line, statements indented by two spaces), so a component written as an arrow function is not covered.
- Old client after a change, white screen after a deploy, `Route GET:/ not found`: `apps/server/AGENTS.md` pitfalls (static serving). Browser audio, output devices, screen share without audio: `src/voice/AGENTS.md`.

## Mobile navigation (19 September 2026)

At widths up to 700 px, App.tsx owns the navigation/content state. The rail and channel/friend list fill the height; text/DM content slides over them with a back button. MobileVoicePreview.tsx is a native bottom dialog showing server voice presence before an explicit join. Voice stays in the existing VoiceClient when the stage is minimized; VoiceDock restores it. Hanging up on the stage returns to the channel list (`hangUp` in App.tsx), never to the text channel under it. The member list is a button at the right end of the server head (`onOpenMembers` of Sidebar.tsx, only at narrow widths): the list slides in from the right over rail and navigation (`.mobile-members` on `.app`, `mobileMembers` in App.tsx) with a header and close button of its own (`onClose` of MemberList.tsx); it closes by itself when content opens, the home view toggles or another server is shown (22 September 2026). Keep desktop rendering and direct voice-channel joining unchanged. Layout and animation use existing brand tokens; respect reduced motion.

Mobile zoom policy (19 September 2026, user request): index.html fixes the viewport scale; styles.css allows panning without pinch zoom up to 700 px and keeps form controls at least 16 px to prevent focus zoom. Desktop CSS is unchanged.

Mobile settings (19 September 2026): settings-backdrop/settings-modal scoped rules make the settings full-viewport at <=700 px. Categories stay on the left as icon/label buttons; navigation and body scroll independently. Keep mobile changes scoped so desktop and admin dialogs retain their layout.

Mobile administration (19 September 2026): admin-backdrop/admin-modal share the mobile settings layout at <=700 px. Categories remain left with icons and labels, both columns scroll independently. Roles, channel creation and channel editor actions stack within the content column; keep desktop grids unchanged.

Dialog opening focus (19 September 2026): SettingsDialog and AdminPanel focus their close button on narrow viewports (<=700 px) or coarse primary pointers; never autofocus a mobile text input. Settings retain desktop profile-input autofocus. Evaluate this policy when the dialog mounts.

Categorized modal layout (23 September 2026): settings, admin and channel dialogs share the mobile rules, always with navigation on the left. `.settings-body > *` and nested `.stack > *` must not shrink vertically: otherwise long tabs overlap. Keep navigation labels wrappable, navigation/body independently scrollable, and specific modal width selectors stronger than `.modal`. Modal window bounds: the categorized backdrops use minmax(0, 1fr) grid tracks. Modal max-width/max-height refer to that available area, so title bars and padding are respected even in short windows. Width caps are 64rem for user settings and 76rem for administration/channels.
