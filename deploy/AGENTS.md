# deploy – Containers, proxies, CI, LiveKit connectivity

Part of the project description. The entry point is the root [AGENTS.md](../AGENTS.md) (commands, definition of done, cross-cutting conventions, the map of all documentation in its section 0). This file also covers the root files `Dockerfile`, `.dockerignore`, `.gitlab-ci.yml`, `.env.example` (described in the root file's section 2). Whoever changes Compose files, the image, CI or the operator documentation updates this file in the same step. Definition of done for these changes: `docker build` runs through (root section 4).

## Structure

```
deploy/                compose.yml (prod, profiles bundled/external; services app, postgres, livekit, caddy), compose.dev.yml (Postgres + LiveKit), caddy/Caddyfile (/rtc* -> livekit, rest -> app), livekit/livekit.yaml
deploy/install.sh      Interactive installer for a Linux host (bash, root): asks de/en, installs Docker via get.docker.com on request, downloads the deploy files from raw.githubusercontent.com into /opt/squorli, writes .env, starts and checks the stack, writes the Compose wrapper <dir>/squorli (+ /usr/local/bin/squorli; `squorli doctor` = the setup check, docs/features/doctor.md); section "Interactive installer" below
deploy/portainer.yml   Self-contained Portainer stack (external mode, image from the GitHub Container Registry by default, LiveKit config inline via LIVEKIT_CONFIG, all variables under "Environment variables"); README section "Portainer". Keep the LiveKit block in step with livekit/livekit.yaml
deploy/proxies/        external mode: README (instructions for nginx, Nginx Proxy Manager, Plesk, Traefik), nginx.conf, nginx.ports.yml (overlay: 3000/7880 only on 127.0.0.1), npm.network.yml (overlay: app/livekit into the proxy network), remote-proxy.ports.yml (overlay: 3000/7880 on PROXY_BIND_IP for a proxy on another host), traefik.labels.yml
deploy/proxies/Caddyfile.external   site block for a Caddy the operator already runs (installer downloads it)
deploy/proxies/test/   run.sh + overlays: the reference proxies (nginx, Traefik, Caddy) against the real stack, CI job "proxies" (docs/features/proxy-tests.md); not downloaded by the installer
```

## Published image and the standard installation

**Published container documentation (15 September 2026):** The official image is `ghcr.io/danielklessa/squorli-server:latest`, listed at https://github.com/danielklessa/squorli-server/pkgs/container/squorli-server. README and website guides document APP_IMAGE, profile/overlay-aware pull and up --no-build, image pinning and the local-build alternative. Portainer users must explicitly set APP_IMAGE to override the stack's legacy default. This documentation update does not change runtime defaults.

The default user installation requires no Git clone, Node.js or application build. Download only .env.example, deploy/compose.yml, Caddyfile, livekit.yaml and the optional nginx port overlay into a fresh squorli directory. Configure .env with APP_IMAGE and the matching proxy mode, then run Compose pull and up --no-build from squorli/deploy. Updates pull the image without git pull; never overwrite existing secrets by repeating the initial download. Source cloning and --build belong only to a separate optional developer workflow at the end of both public guides. Both languages must stay equivalent.

**Logs (27 September 2026, `docs/features/logging.md`):** every service of `compose.yml` and `portainer.yml` carries `logging: *logging` (the `x-logging` anchor, `json-file`, 3 × 10 MB); a new service gets it too. `livekit.yaml` and the `LIVEKIT_CONFIG` of `portainer.yml` log at `warn` (keep both in step); `info` writes every participant's IP addresses. Changes to these deploy files reach existing installations only when the installer runs again, so the server release notes must say so.

## Interactive installer (`deploy/install.sh`)

Built on 23 September 2026 (user's wish: an interactive install script for Linux). It automates the standard installation above; it does not replace the documented manual steps. Decisions made by Claude, not confirmed by the user: root only; default directory `/opt/squorli`; questions in German or English (`SQUORLI_LANG`, else from `LANG`); three HTTPS setups (`bundled` = Caddy, `local` = proxy on the host with `proxies/nginx.ports.yml`, `remote` = proxy on another host with `proxies/remote-proxy.ports.yml` bound to a LAN/VPN address, because Docker bypasses ufw/firewalld for published ports; the proxy's IP is appended to `TRUSTED_PROXIES`); Docker from get.docker.com only after a yes; ufw/firewalld opened only after a yes; `LIVEKIT_API_KEY=squorli`; `SERVER_NAME` asked only on a fresh install (it only names a new database); the wrapper `squorli` with `update|status|logs|restart|down|backup|restore`, the backup = `pg_dump` + a tar of `/app/data` from the app container + a copy of `.env`.

**Owner (27 September 2026, `docs/features/local-accounts.md`):** the step "Einstellungen" asks "Wer wird Besitzer?": the Squorli account's key (`OWNER_PUBLIC_KEY`, only offered with a directory), a server account with a setup code (`OWNER_SETUP_CODE`, 24 hex characters from `secret`, an existing one kept) or whoever signs in first; the code is printed at the end with the address. The website's installation guide lists this question (both languages).

**Restore (25 September 2026, user's wish during the plan cleanup):** `squorli restore <folder> [--yes]` asks for `yes` on the terminal, stops `app`, drops and recreates the database `chat` (`DROP DATABASE ... WITH (FORCE)` as the superuser `chat`, so the target's `POSTGRES_PASSWORD` may differ from the source's), loads the dump with `ON_ERROR_STOP`, empties `/app/data` and unpacks the archive through `docker compose run --entrypoint sh app` (user `node`), then `up -d`. `.env` is never touched; the backup's copy is only named. The server key lives in the database (`server_settings`), so the directory registration moves with it. A backup from a newer server version than the image is not refused (migrations only go forward): restore with at least the version that wrote it. Checked in a `docker:27-dind` container with the published image: marker row and file came back, a file added after the backup was gone, the server key was the same, health ok; the cancel path through `/dev/tty` was not run. The website documents it and the manual equivalent (`../squorli-website`, installation guide section 6).

Rules for changes:
- **The website's installation guides lead with this script** (user's decision, 23 September 2026: the simplest installation; `../squorli-website`, section 2 `#install` and the `squorli` commands in section 6, both languages). A change of the questions, their order, defaults, `/opt/squorli` or the wrapper's commands updates both translations there in the same step.
- **The script downloads its files from `main` of the public repository** (`SQUORLI_REF`, `SQUORLI_RAW_BASE`), so a new file in the standard installation goes into `DEPLOY_FILES`, and a renamed or moved file under `deploy/` breaks installers of older checkouts: keep the paths stable.
- **`.env` is never sourced and never replaced:** `env_get`/`env_set` read and change single lines of the file, the first installation starts from `.env.example`. Values outside `[A-Za-z0-9._:/@+,=-]` are written in single quotes, which Compose reads literally (no `$` interpolation). Secrets are kept on every rerun; a fresh install over an existing volume `squorli_pgdata` asks for the old `POSTGRES_PASSWORD` (Postgres reads it only on its first start).
- **Ports (23 September 2026, user's wish: install on a host whose standard ports are taken):** `compose.yml` and the overlays read `LIVEKIT_TCP_PORT`/`LIVEKIT_UDP_PORT` (media, default 7881/7882) and `APP_PORT`/`LIVEKIT_HTTP_PORT` (what a proxy forwards to, default 3000/7880; only in the overlays and `portainer.yml`). The media ports are published on the same number inside and outside, and LiveKit gets them as `--rtc.tcp_port`/`--udp-port` (checked: these flags override `livekit.yaml` and `LIVEKIT_CONFIG` at run time; LiveKit's own `ports` command ignores them, do not trust its output). The installer's step "Ports" shows the ports it needs, replaces those another service holds by the next free one from default + 10000, and lets every port be typed; the ports of this installation's own containers (from `.env`, depending on the old setup) never count as taken. 80/443 of the bundled Caddy stay fixed (Let's Encrypt's HTTP-01 check needs 80, the whole server's origin logic assumes 443); when one of them is taken the installer steers to the setup with an existing reverse proxy, a second choice of Caddy goes ahead anyway.
- **Look (23 September 2026, user's wish):** a banner with `docs/brand/squorli-icon-small.svg` as half-block characters in Squorli blue (ASCII fallback without a UTF-8 locale; regenerate it from the SVG when the icon changes), a blank line and a blue `?` before every question, a blue rule before every step.
- **Reruns:** the wrapper's line `# setup: <bundled|local|remote>` records the setup. Leaving `bundled` removes the Caddy container explicitly (it belongs to the profile `bundled` only, `--remove-orphans` does not touch it). Changed deploy files are kept as `<file>.bak`, the old `.env` as `.env.bak.<time>`.
- **Input:** questions read from `/dev/tty` when stdin is not a terminal (`curl ... | sudo bash`), else from stdin (scripted tests).
- **`squorli doctor` (26 September 2026, docs/features/doctor.md):** the wrapper lists the containers, resolves `PUBLIC_DOMAIN` on the host and asks the app container's `GET /api/doctor` over loopback (`docker compose exec -T app node -e ...`, no session needed from 127.0.0.1); the texts come from the server in the installer's language, recorded as `# lang: de|en` in the wrapper next to `# setup:`; exit 1 when a check fails. The JS inside the wrapper sits in single quotes: no single quotes in it. `compose.yml` passes `LIVEKIT_TCP_PORT`/`LIVEKIT_UDP_PORT` to the app too, so the report names the right ports.
- **Test:** `shellcheck` clean (`docker run --rm -v <deploy>:/mnt:ro koalaman/shellcheck:stable /mnt/install.sh`, from Git Bash with `MSYS_NO_PATHCONV=1`); end to end in a privileged `docker:27-dind` container with the repo mounted at `/src`, `apk add bash curl openssl iproute2 musl-utils`, `SQUORLI_RAW_BASE=file:///src`, answers piped into `bash /src/deploy/install.sh`; the piped path with a real terminal through `script -qec "cat install.sh | bash" /dev/null` (package `util-linux-misc`). Its own Docker daemon keeps the dev stack's ports and volumes untouched. The bundled mode can only be checked up to Caddy's certificate request there.

## Known pitfalls: image and Compose

- **LiveKit is pinned (25 September 2026, user's decision):** `compose.yml`, `portainer.yml` and `compose.dev.yml` name `livekit/livekit-server:v1.13.7`, not `latest`, so a LiveKit release never reaches operators untested (PLAN.md, risks). Raising it: change all three files together, run the dev stack and a voice/screen-share test, name it in the server release notes. Installations that downloaded `compose.yml` before this keep `latest` until they download it again.
- **Docker build from Windows:** without `.dockerignore`, the host `node_modules` end up in the build context; do not delete the file. `tools/` is deliberately excluded: the Dockerfile must not call `tools/icons.mjs`; the generated icon files under `apps/web/src/icons/` are in the repo and are sufficient.
- **Server release (25 September 2026, user's wish):** the skill `server-release` (`.claude/skills/server-release/SKILL.md`) prepares one like `desktop-release` does for the app: what changed since the last `v*` tag (from `docs/MILESTONE-LOG.md`), what operators must know first (migrations, variables, deploy files, the desktop app version needed), a proposed version, `version` in `apps/server/package.json` (login footer, `/api/health`) and `apps/server/release-notes/<version>.md`; it never tags or pushes. The tag `v<version>` then publishes `:v<version>` (ci.yml `image`) and `.github/workflows/server-release.yml` writes a **draft** GitHub release from the notes plus a standing text about updating; it refuses a tag that does not match `apps/server/package.json`. Every push to the default branch still publishes `:latest`.
- **Tags:** `v*` = server image (GitLab `build-tag`, GitHub `image`); `desktop-v*` = desktop app, built only by `.github/workflows/desktop-release.yml` on GitHub (installers into a draft release). Keep the tag rules of `.gitlab-ci.yml` and `ci.yml` in step.
- **Every workspace package needs its `package.json` copied before `pnpm install --frozen-lockfile`** (Dockerfile, cache-priming block), also the ones the image does not build (`apps/desktop`): otherwise the lockfile does not match the workspace. `ELECTRON_SKIP_BINARY_DOWNLOAD=1` keeps Electron's binary out of the build; the CI test jobs set it too (they typecheck, test and bundle `apps/desktop`, never start it).
- **`pnpm deploy` under pnpm 10** aborts without `--legacy` with `ERR_PNPM_DEPLOY_NONINJECTED_WORKSPACE` (the flag is in the Dockerfile).
- **Testing the image locally:** `docker run --rm -p 3000:3000 --network squorli-dev_default -e PUBLIC_DOMAIN=localhost -e DATABASE_URL=postgres://chat:chat@postgres:5432/chat -e LIVEKIT_URL=http://livekit:7880 -e LIVEKIT_API_KEY=devkey -e LIVEKIT_API_SECRET=<32 characters> squorli/app:local`, then run the smoke test.
- **Compose project is called `squorli-dev` since 14 September 2026 (previously `community-chat-dev`):** if old containers are still running, they occupy 5432/7880-7882 and the new stack does not start. Run `docker compose -p community-chat-dev down` (without `-v`) once, then `pnpm dev`. The data volume is pinned in `compose.dev.yml` to the old name `community-chat-dev_pgdata-dev` and declared as `external: true` (Compose requires this for volumes from another project); `tools/dev.mjs` creates it via `docker volume create` before `compose up`, so that a fresh machine starts as well. Anyone using `pnpm docker:dev` directly must create the volume once themselves. The dev DB is preserved this way (verified on 14 September 2026: users and handles present after the switch). Containers are now called `squorli-dev-postgres-1` / `squorli-dev-livekit-1` (in all `docker exec` commands). For an already running prod stack (`community-chat`), the same applies to `deploy/compose.yml` (network `squorli_internal`, volumes not pinned: back up data first).
- **Production compose always with `--env-file ../.env`:** `env_file:` in the service only covers the container environment; the `${POSTGRES_PASSWORD}`/`${LIVEKIT_API_KEY}` placeholders in `compose.yml` are filled by Compose only from `deploy/.env` or the `--env-file`. Without the flag: empty DB password, `LIVEKIT_KEYS: ": "`. Check with `docker compose --env-file ../.env ... config`.
- **external mode publishes no HTTP ports.** A proxy on the host needs the overlay `proxies/nginx.ports.yml`; a proxy in a container attaches to the network `squorli_internal`.

## LiveKit: why, bandwidth, proxy limits (moved from PLAN.md 3.1 and 4.1-4.5 on 25 September 2026)

- **Why LiveKit and not an own SFU:** writing an SFU in TypeScript (e.g. on mediasoup) is not realistic for one person with the goal "15 cameras, stable" next to everything else. LiveKit brings simulcast, SVC, TURN, speaker detection, selective subscription and a JS client SDK; the price is a Go dependency we cannot fix ourselves, a deliberate trade of control for feasibility. Hence the pinned version above and a thin LiveKit layer in the server. The app server never transports media, it only issues short-lived LiveKit tokens (root `AGENTS.md` section 6).
- **Subdomain only, no sub-path:** `chat.example.org` yes, `example.org/chat` no. A sub-path creates special cases in client routing, asset paths and LiveKit signaling that are not worth the effort; a deliberate limit, told to operators in `proxies/README.md`.
- **TURN:** LiveKit's built-in TURN is off by default (`livekit/livekit.yaml`: needs a certificate and 5349/tcp). In proxy mode TURN/TLS cannot sit on 443 because the proxy holds it; the way to 443 is SNI-based TCP passthrough at the proxy (Traefik TCP router, nginx `stream` with `ssl_preread`, Caddy `layer4`) for a subdomain like `turn.chat.example.org`, an advanced path, never a requirement. When to build it: `docs/PLAN.md` (open work).
- **Bandwidth: measurement and projection.** Operators need a rented server or VPS for big video channels, a home connection is usually too weak; `README.md` ("Requirements") and the website's installation guide (section 1, both languages) say so. Keep the three in step when the numbers change. First measurement on 13 September 2026, locally (Docker Desktop, Windows; `docs/VERIFIED-STATE.md`): `pnpm bots --video 15 --audio 0 --subscribers 1`, 15 simulated cameras (LiveKit preset "high", VP8, simulcast with three layers), one listener with a 4x4 tile layout, 60 s.

| Where | Direction | Measured | Projection |
|---|---|---|---|
| Client | Download (15 tiles) | **4.1 Mbit/s** total, 236-309 kbit/s per track, packet loss 0.03 % | about 4 Mbit/s |
| Client | Upload (camera 720p, simulcast 180/360/720) | client default: max. ~1.7 Mbit/s (720p) or ~0.4 Mbit/s (360p setting); the debug view shows the layers live | 1-2 Mbit/s |
| Server | Download (ingest) | not measured (the bots run in the network namespace of the LiveKit container, `docker stats` does not see the traffic) | 15 x ~1.5 Mbit/s = about 20 Mbit/s |
| Server | Upload (distribution) | one listener = 4.1 Mbit/s | 15 listeners = about 60 Mbit/s |
| Server | CPU / RAM (LiveKit) | ~9 % of one core, ~135 MB with 15 cameras + 1 listener | linear with listeners, no transcoding |

Thanks to `adaptiveStream` the tile view only fetches the simulcast layer that matches the tile size; a speaker focus with a large tile pulls the 720p layer (~1.5 Mbit/s) for that one track and 180p for the small tiles. CPU stays moderate as long as media is only forwarded; recording and server-side transcoding would tip that over and are not planned. Open (`docs/PLAN.md`): the measurement with 15 real cameras on a target server over the internet, including the ingest (`docker stats` on the host); its result replaces this projection.

## Known pitfalls: LiveKit connectivity

- **LiveKit dev container** runs with `--dev` (keys `devkey`/`secret`); `.env.development` deliberately uses a longer secret only for token signing; a real media connection is not yet part of the client in M0.
- **"could not establish signal connection" / Safari "Load failed":** the client cannot reach the LiveKit URL issued by the server. Usually `apps/server/.env` still contains `LIVEKIT_PUBLIC_URL=ws://localhost:7880` from `.env.development` while the server runs publicly. Remove the variable (default `wss://PUBLIC_DOMAIN`, the proxy forwards `/rtc`). The server warns about this combination at startup; the client names the URL in the error message and in the debug view. Second cause: `LIVEKIT_PUBLIC_URL=wss://domain:7880` (port 7880 does not speak TLS and is not exposed; correct is without a port via the proxy). Third cause: the proxy does not forward `/rtc` (`/rtc/validate` must return 401).
- **Participant drops out of the channel after ~15 s:** the signal connection is up, media (ICE) never gets established, LiveKit disconnects with CONNECTION_TIMEOUT/UNKNOWN. Causes: 7882/udp + 7881/tcp not forwarded to the chat host, LiveKit does not know its public IP (`LIVEKIT_NODE_IP`), or the dev stack is running with `--node-ip 127.0.0.1`. The client shows the disconnect reason as an error and logs room events in the debug view; on the server, set `level: info` in `livekit/livekit.yaml` for a while (production runs at `warn` since 27 September 2026, `docs/features/logging.md`), restart livekit and search `docker logs <livekit>` for "ice" / "connection timeout". SIGNAL_CLOSE, by contrast, = WebSocket closed (proxy timeout, network switch, phone in the background).
- **LiveKit URL for clients without `/rtc`:** livekit-client appends `/rtc` itself. `wss://domain/rtc` would result in `/rtc/rtc` and fails. The server delivers `LIVEKIT_PUBLIC_URL` or `wss://PUBLIC_DOMAIN`.
- **LiveKit in Docker on Windows/macOS:** without `--node-ip`, LiveKit offers the internal container IP as ICE candidate, and browsers on the host then get no media. `compose.dev.yml` sets `--node-ip ${LIVEKIT_DEV_NODE_IP:-127.0.0.1}`; `tools/dev.mjs` loads `apps/server/.env` for this. For a second device in the LAN set `LIVEKIT_DEV_NODE_IP=<host LAN IP>`, for tests from outside the public IP, and open the client from that device via the LAN IP (then `localhost` is no longer a secure context: microphone only with HTTPS; mkcert for LAN tests is open work in `docs/PLAN.md`, `docs/DEVELOPMENT.md`).
- **LiveKit dev secret:** `--dev` sets `devkey`/`secret`; the container receives the longer secret from `.env.development` via `LIVEKIT_KEYS`, because `config.ts` requires at least 16 characters. Token check without a browser: `GET http://localhost:7880/rtc/validate?access_token=<jwt>` must return 200.
