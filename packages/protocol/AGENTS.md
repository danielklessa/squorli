# packages/protocol – `@squorli/protocol`

Part of the project description. The entry point is the root [AGENTS.md](../../AGENTS.md) (commands, definition of done, cross-cutting conventions, the map of all documentation in its section 0). Whoever adds a schema file, changes the version rule or the permission rules updates this file in the same step.

**Six files here are the source of a byte-identical copy in `../squorli-directory`** (`primitives`, `directory`, `backup`, `useragent`, `friends`, `dm` and their tests): sync in the same work step, root `AGENTS.md` section 2a.

## Conventions

- **Protocol version:** Bump `PROTOCOL_VERSION` in `@squorli/protocol` on incompatible changes (currently 4; new permission bits are not an incompatible change; a new server event is one when clients must understand it, because the client parses events strictly with zod and drops what it cannot parse. An event that older clients may safely miss, such as `read.update`, needs no bump, and a bump is costly: the multi-server client cannot connect to servers of another version); the server rejects other versions with WS code 4002. The constant is also in `apps/server/scripts/smoke.mjs`, update it there too. Precedent (23 September 2026): the channel permissions needed no bump although every client's channel list changed, because `structure` kept its wire shape (whole lists, filtered per recipient on the server) and every new field carries a default or is optional; new error codes went on REST answers only (`ServerError.code` is a fixed enum that older clients would drop).
- **Feature flags instead of a version bump:** a field the server only sends when it knows a feature (`ServerSettings.radioAutoStop`, `afkChannelId` with null for "none"; the directory's `DirectoryHealth.features.*`) tells the client whether it may use the matching client event or route. A new **client** event needs such a flag, because servers answer unknown client events with `bad_message` (`ClientActivity` is only sent when `afkChannelId` is present, `DirectoryClientActivity` only with `features.afk`).
- **Measures of the directory's operator reach the clients and the chat servers through the copied files (27 September 2026, docs/features/reports.md):** `directory.ts` has `DirectoryAccount.suspendedUntil` (only an answer to a server's token or the account's own status fills it), the notices (`AccountNotice`, `AccountNotices` = a list that drops what this version cannot read, so a kind of a later version never breaks the account's status; `AccountStatus.notices`/`suspendedReason`, `NoticeReadRequest`/`Response`, action `notice-read`), the reports of accounts and chat servers (`AccountReportContent`, `ServerReportContent`, `ServerReportEvidence`, `DirectoryReportRequest`, `directoryReportPayload`, `reportKindsOf`; `features.reportKinds` is a list of strings for the same reason) and the refused hosts (`RefusedServersResponse`, `refusedHostHash`, `directoryRefusedServersUrl`, `features.refusedServers`; the account's own among them in `AccountStatus.refusedServers` with `AccountServer.refused`, a list of its own because a client from before it connects to every entry of `servers`); `friends.ts` has the socket's error code `account_suspended` (sent before an `unauthorized`, which is what clients from before it stop on) and the event `notices.changed`. `index.ts` (not copied) has `ServerSettings.refuseSuspended` (optional = the feature flag) and the close code 4014 with `suspendedCloseReason`/`suspendedUntilOf`. No version bump: new fields carry defaults, the events are safe to miss, the error code rides on REST answers and in an event's message.
- **Devices (29 September 2026, docs/features/devices.md):** the shared part lives in `directory.ts`, section "Devices" (copied): `DEVICE_MAX`, `DEVICE_PAGE_MAX`, `DEVICE_IDLE_MS`, `deviceProofMessage(accountKey, message)` = what a device signs next to the account's key, over exactly the message that key signed, `deviceEnrolMessage(host, handle, deviceKey)` = the proof where a device is enrolled with the password, `DeviceProofFields` (`deviceKey`, `deviceSignature`, both optional) on `SignedActionRequest` and on every request that builds its fields by hand (`DirectoryRegisterRequest`, `BackupUploadRequest` with `oldAuthKey`, `BackupFetchRequest` with `ticket`/`replaceDevice`/`deviceKind`/`remember`, `FriendsActionRequest`, `DirectoryClientAuth` in `friends.ts`), `DeviceInfo`, `DESKTOP_APP_ORIGIN` and `signInOrigin` (what a sign-in's `origin` holds: a site's host, or `app://squorli` whole for the desktop app, shown as "über die Desktop-App"; the user's decision of 30 September 2026), `TooManyDevicesResponse`, `DEVICE_REFUSALS`/`isDeviceRefusal`, `DirectoryAccount.devicesEnforced`/`deviceKeys` (defaults false and empty), the action `device-revoke`, `AccountStatus.devices`, `features.devices`/`deviceRevoke`; `friends.ts` has the close code 4015 and the socket's error codes. The chat server's part is not copied: `localAccounts.ts` (the proof on the four requests of a server account, `LocalDeviceRevokeRequest`, `DevicesResponse`) and `index.ts` (the proof on `VerifyRequest`, `DEVICE_REFUSED`, `WS_CLOSE_SESSION_ENDED`, `SESSION_END_REASONS`, `sessionEndReasonOf`), tested in `devices.test.ts`. **A new request the account's key signs carries `DeviceProofFields`**, or an enforced account cannot use it. No version bump. **Sessions bound to the device (4 October 2026, security audit S10, `index.ts` section of that name):** `bindDevice` on `VerifyRequest`, `LocalRegisterRequest`, `LocalClaimRequest`, `VerifyResponse.deviceBound`, `SESSION_PROOF_HEADER`, `SESSION_PROOF_MAX_SKEW_MS`, `DEVICE_PROOF_REQUIRED`, `sessionProofMessage(domain, at, method, path)`, `sessionProofHeader`/`parseSessionProofHeader`, `SessionProof`/`SessionProofSchema`, `ClientHello.deviceProof`; all optional, no version bump.
- **Report reasons live in `primitives.ts`** (26 September 2026), one of the copied files: the chat server's reports (`reports.ts`) and the directory's reports of direct messages (`directory.ts`: `DmReportRequest`, `DmReportContent`, `directoryDmReportPayload`, action `report`, `features.reports`) share `ReportReason` and `REPORT_TEXT_MAX`; `index.ts` re-exports them next to the other primitives.
- **Order and grouping of permissions (user's requirement, 17 September 2026, applies to every permission added from now on):** the role editor shows permissions in groups sorted by meaning (`PERMISSION_GROUPS` in `permissions.ts`: `admin` "Verwaltung" first with `ADMINISTRATOR` at its top (user's decision), then `text` "Kanäle und Nachrichten", `voice` "Sprachkanäle" (until the web radio: "Sprache und Video"), `members` "Mitglieder"; apart from `ADMINISTRATOR` a group runs from everyday to powerful; group titles from the `permGroup.*` keys, rendered as `fieldset.perm-group` in `AdminPanel.tsx`). The bit order is history and never the display order. Whoever adds a permission must sort it into the group and position where it belongs by meaning (next to related ones, e.g. watching before sharing), never simply append it, and must re-check the whole arrangement each time: does a group get too long, does a new group make more sense, are the group titles still accurate. A test in `index.test.ts` fails if a permission is in no group or in two. **Channel permissions (23 September 2026):** a new bit that makes sense per channel goes into `CHANNEL_OVERRIDABLE` and into `CHANNEL_PERMISSION_GROUPS` (the channel dialog's own grouping per channel kind, with `chanPerm.*` labels in both catalogs: "Kanal sehen", not "Kanäle sehen"); a second test pins that the groups cover `CHANNEL_OVERRIDABLE` exactly once per kind and name nothing server-wide. New permissions: append the bit in `permissions.ts`, add the label (`perm.*` in both catalogs), sort it into `PERMISSION_GROUPS`, and for existing servers write it into the appropriate role via a custom migration (`drizzle-kit generate --custom`) (see 0003/0004 as examples); the bit values are pinned in `index.test.ts`.
- **Key backup (M6b):** The private key leaves the client only encrypted. `packages/protocol/src/backup.ts`: PBKDF2-SHA256 (600,000 iterations, 16-byte salt) -> HKDF into two keys: AES-256-GCM (encrypts the 32-byte seed, stays in the client) and auth key (is sent, the service stores only its SHA-256 in `key_backups.auth_hash`). Storing: `PUT /api/backup`, signed over "community-directory-backup\n<host>\n<nonce>\n<ciphertext>", upsert (= change password). Fetching in two steps: `GET /api/backup/:handle/params` (salt, iterations) -> client derives -> `POST /api/backup/fetch` with auth key -> blob with iv + ciphertext. Wrong password = 401 `auth_invalid`; rate limit `BACKUP_RATE_LIMIT` per IP **and** per handle (default 10/min), uploads have their own window. Password at least `BACKUP_MIN_PASSWORD` (8) characters, checked client-side only; no reset possible (the directory does not know it). **No recovery by mnemonic words (user's decision, 25 September 2026; moved from PLAN.md 3.2):** the original plan was a recovery code of mnemonic words stored locally; it was dropped, the password-encrypted key backup at the directory and server accounts with a password (`docs/features/local-accounts.md`, same backup format) replace it. The directory's recovery codes are a second factor, not a key recovery.
- **Reconnect: the welcome resends the full state (moved from PLAN.md 3.3 on 25 September 2026):** the design planned reconciliation by sequence numbers; built is the simpler way: after every (re)connect the server's `welcome` carries the complete `ServerState`, and `voice.state` and `structure` are whole states, never deltas. The client (`apps/web/src/serverConnection.ts`) replaces its state, reloads the open channel's history and announces its voice seat, idle state and read states again; the directory socket's `welcome` does the same for friends and conversations. The user decided on 25 September 2026 that this is enough for now; sequence numbers stay a low-priority open item (`docs/PLAN.md`). Keep new server state reconnect-safe the same way: whole states in the welcome or a follow-up event, not deltas the client could miss.
- **Scanner for mentions and link previews:** `src/scan.ts` (`scanOutsideCode`) reads a message text the way `apps/web/src/markdown.ts` does as far as code and escapes go; `mentions.ts` (who is mentioned) and `links.ts` (`previewLinks`: which links get a preview; `readBareUrl`, which the Markdown parser itself imports) are built on it. Whoever changes how the parser reads fences, code spans, escapes or bare addresses changes `scan.ts` / `links.ts` too; the web tests `mentions.test.ts` and `linkPreviews.test.ts` compare both with the parser (`docs/features/mentions-unread.md`, `docs/features/link-previews.md`).

## Known pitfalls

- **`@squorli/protocol` has no build:** its entry is `src/index.ts`. The server therefore bundles it into `dist/index.js` via `noExternal`. Anyone who introduces further workspace packages as runtime dependencies of the server must add them to `tsup.config.ts` as well.
